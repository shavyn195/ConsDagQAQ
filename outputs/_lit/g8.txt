35:Abstract
36:For repository-grounded coding agents, a functionally correct patch is not necessarily an acceptable one:
37:developers also constrain how the task must be carried out—modification scope, workflow order, validation,
38:tool use, and reporting. This capability, which we call engineering constraint following, remains largely
39:invisible to current evaluations. We introduce ANCHOR (Assessing Naturalistic Constraint Hierarchies
40:and Ordering in Repository-Grounded Agentic Coding), a benchmark built on naturalistic, multilingual
41:repository tasks spanning eight language groups. ANCHOR combines (i) a hierarchical taxonomy of
42:10 categories and 78 leaf types distilled from real developer interactions, (ii) an automated pipeline that
43:instantiates task-grounded atomic constraints and composes them into typed AND/THEN/PRIORITY relations,
44:and (iii) a trajectory-grounded evaluation framework that checks both the code diff and the execution
45:trajectory with rule-based and LLM judges. Across 19 agent configurations spanning 2 scaffolds and 10
46:foundation models on 358 tasks, the strongest measured system, Claude Opus 4.8 under Cline, reaches
47:70.1% atomic compliance and 63.7% relation compliance, while 19.0% of tasks pass every scored checklist
48:item under the strict all-item FCCR criterion. A five-engineer audit of constraints from 50 instances
49:reports 94% feasibility, 94% repository consistency, and 96% realism. In the primary paired set (14
50:configurations), the mean signed change in task completion after adding constraints is +0.7 percentage
51:points; individual changes vary in both directions. These results distinguish functional success from
52:constraint compliance, with failures concentrated in workflow ordering, tool-use discipline, and reporting,
53:and substantial interactions between models and scaffolds.

16:Embodied agents are increasingly capable of perceiving, planning, and acting au-

20:tasks are more common: the need for cooperation only becomes apparent after
21:an agent observes and interacts with task-related targets. In this paper, we first
22:present HiddenCoop, a benchmark for effectively evaluating agent cooperation in

73:Across nine proprietary and open-weight agent models, our evaluator reports a highest subtask

77:rubric. These findings highlight the importance of evaluating completion throughout a conversation

239:PROBLEM DESIGN
240:A ToolTurns problem is a triple (qi, Ti, Gi), where qi is the user’s initial natural-language query, Ti
241:is a fixed set of callable tool endpoints and their schemas, and Gi = {(sij, vij)}mi
242:j=1 is the unseen
243:user’s goal, represented as a set of slot–value constraints. Each slot sij corresponds to an argument in
244:a tool schema, and vij is the value that the user has in mind but does not initially specify in qi.
245:The dialogue begins with qi. At each step t, conditioned on the dialogue history and the schemas
246:of Ti, the agent selects an action at ∈A(Ti) that either (1) invokes an endpoint and receives a tool
247:observation ot, (2) sends a message to the user and receives a user response ot, or (3) completes the
248:current request with a final answer yt. In response to a clarification request, the user simulator reveals
249:relevant slot values from Gi.

383:EVALUATION DESIGN
384:We evaluate each generated dialogue along two axes: dialogue quality, measured by a five-aspect
385:LLM-judged rubric, and task success, a per-subtask binary judgment of whether the user’s informa-
386:tion need for that query was fully resolved. Both rely on LLM judges with structured function-calling
387:outputs and a fixed prompt set across conditions.
388:3.4.1
389:DIALOGUE QUALITY RUBRIC
390:The dialogue quality rubric scores each generated dialogue across five aspects, one LLM call per
391:aspect: consistency, factual coherence between the assistant’s claims and tool outputs; relevance,
392:whether assistant turns address the user’s request; efficiency, economy of tool calls and turns; cor-
393:rectness, whether the final answer is factually right with respect to tool evidence; and adaptability,
394:handling of clarifications, corrections, and underspecified inputs. Each aspect is scored on a discrete
395:[0, 1] scale with five levels (0, 0.25, 0.5, 0.75, 1.0) and the judge additionally returns a brief justifica-
396:tion. Aspect scores are combined into a single weighted aggregate (correctness 0.30; consistency,
397:relevance, efficiency 0.20 each; adaptability 0.10). Because scores take only five discrete values,
398:mean differences at the second decimal place correspond to a one-level shift on a small fraction of
399:dialogues, so we do not read small second-decimal gaps as meaningful differences.
400:3.4.2
401:TASK SUCCESS
402:Task success is determined by a hybrid evaluator that applies a deterministic hard-fail gate before
403:invoking an LLM judge. It scores each subtask of the dialogue (the initial query and each follow-up
404:query, §3.2) independently, rather than issuing a single judgment for the dialogue as a whole. The
405:gate handles failure modes that can be identified cheaply and with certainty, so the LLM judge is
406:reserved for cases where the outcome is uncertain.
407:Subtask segmentation. Each dialogue is split into its three main queries (one initial query and
408:num_follow_up_queries = 2 follow-ups), and the gate and LLM judge below are applied separately
409:to each subtask’s slice of the dialogue (its query, turns, tool calls, and tool responses).
410:Deterministic gate. A subtask fails without an LLM call when every substantive tool observation
411:is StableToolBench documentation-placeholder prose, a description of the API rather than live data
412:(for example, “The API call to . .. is designed to provide .. .”), and none of the observations yields
413:data-shaped output such as structured fields, lists, or typed scalars beyond bookkeeping keys like
414:status, success, or code. The gate is rarely decisive: it applies to only 20 of the 70,740 subtasks
415:across the nine agents in §4.1 (0.03%; at most five per agent), placeholder prose appears at all in
416:only 154 (0.2%), and no pooled subtask pass rate in Table 3 moves by more than 0.03 points with or
417:without it, so cache coverage does not account for the failure rates we report.
418:LLM judge. If the gate passes, a single LLM call decides semantic task completion for that
419:subtask via structured function-calling. The judge receives the subtask’s query and its slice of the
420:dialogue (turns, tool calls and their responses, and the assistant’s answer) and must return a boolean
421:task_succeeded with a brief justification. The system prompt instructs the judge to be strict on
422:wrong or missing answers; a subtask passes only if the user’s information need for that query was
423:fully met by the final outcome.
424:Dialogue-level score. A dialogue’s task-success score is the fraction of its subtasks that succeed,
425:success_count / total_subtasks (e.g. 2/3 if the initial query and one of the two follow-ups
426:succeed); a dialogue counts as fully successful only if every subtask succeeds. We report both
427:quantities in §4.1: the pooled subtask pass rate as the headline figure, and the stricter all-subtasks-
428:pass rate alongside it.

432:(§4.1), and a validation of the simulated user’s turn quality (§4.2).
