14:Abstract
15:As LLM agents increasingly select tools au-
16:tonomously, their choices among tools with dif-
17:ferent privileges become safety-relevant. How-
18:ever, prior tool-selection studies focus on
19:safety-agnostic metadata preferences, leaving
20:privilege-sensitive choices underexplored. To
21:address this gap, we study over-privileged tool
22:selection, in which an agent selects or esca-
23:lates to a higher-privilege tool despite a suf-
24:ficient lower-privilege alternative. We intro-
25:duce TOOLPRIVBENCH to evaluate whether
26:agents choose higher-privilege tools despite suf-
27:ficient lower-privilege alternatives, measuring
28:both initial selection and escalation after tran-
29:sient tool failures. Across eight domains and
30:five recurring risk patterns, we find that over-
31:privileged tool selection is common among
32:mainstream LLM agents and is further ampli-
33:fied by transient failures. We further find that
34:general safety alignment does not reliably trans-
35:fer to least-privilege tool choice, while prompt-
36:level controls provide only limited mitigation
37:under transient failures. We therefore intro-
38:duce a privilege-aware post-training defense
39:that teaches agents to prefer sufficient lower-
40:privilege tools and escalate only when neces-
41:sary. Our mitigation experiments show that
42:this defense substantially reduces unnecessary
43:high-privilege tool use while preserving gen-
44:eral capabilities.

249:Evaluation Protocol
250:We design each evaluation case based on the formu-
251:lation above. In our specific setting (Figure 2(a)),
252:each case consists of a user task together with six
253:available tools: three lower-privilege and three
254:higher-privilege. All tools are constructed to be
255:sufficient for completing the task within the given
256:scenario, which removes the capability confound
257:that a lower-privilege tool might be unable to solve
258:the task, allowing us to attribute higher-privilege
259:use to the agent’s tool-selection behavior rather
260:than to functional limitations of lower-privilege
261:tools.
262:We evaluate agents over multiple turns to capture
263:both forms of over-privileged behavior: direct high-
264:privilege selection at the initial decision point, and
265:escalation after lower-privilege attempts encounter
266:execution friction(Figure 2(b)). To model such
267:friction without making lower-privilege tools gen-
268:uinely insufficient, we inject transient, privilege-
269:unrelated failures into lower-privilege tool calls,
270:such as connection errors. After receiving such
271:feedback, the agent can retry the same lower-
272:privilege tool, switch to another lower-privilege
273:tool, escalate to a higher-privilege tool, or stop if
274:the task has been completed. We cap each interac-
275:tion at k = 5 turns. Since each case contains three
276:lower-privilege tools, this horizon gives the agent
277:enough room to explore multiple lower-privilege
278:alternatives before escalating, while avoiding an
279:open-ended retry process.
280:Under this protocol, we report the Over-
281:Privileged Tool Use Rate@k (OPUR@k), de-
282:fined as the proportion of cases in which the agent
283:uses any higher-privilege tool within k turns while
284:lower-privilege sufficient alternatives remain avail-
285:able. We also report the Pre-Escalation Explo-
286:ration Depth (PED), defined as the number of dis-
287:tinct lower-privilege tools attempted before the first
288:higher-privilege tool use. Among over-privileged
289:cases, PED = 0 corresponds to aggressive selec-
290:tion, while PED ≥1 corresponds to premature
291:escalation, lower PED indicates more aggressive
292:escalation.

1050:Limitations
1051:While this study provides valuable insights into
1052:tool selection in LLM agents, several limitations
1053:should be acknowledged. For safety and controlla-
1054:bility, we evaluate agents in simulation rather than
1055:granting access to real production tools or live ex-
1056:ternal services, and we use task instances in which
1057:a small set of substitutable tools are independently
1058:sufficient for completion. These choices support
1059:clear attribution of over-privileged selection, but
1060:they do not cover the full complexity of deployed
1061:agent environments. Future work can extend this
1062:setting with sandboxed executable tools, larger tool
1063:inventories, partially overlapping tools, and multi-
1064:tool workflows, which may require longer-horizon
1065:trajectory analyses beyond the five-turn protocol
1066:studied here. Moreover, the mechanisms behind
1067:over-privileged selection under uncertainty offer a
1068:valuable direction for deeper analysis.
