## Symbolic Constraint Agents: Mining Formal Tool-Call Constraints to


## Prevent Agent Errors

### Abstract

Symbolic constraints (programmatic, determin-
istic checks for tool calls) enable deterministic
verification of LLM agents’ tool calls, but ex-
isting approaches primarily enforce predefined
safety policies rather than tool dependencies
in complex tool environments. We explore
whether symbolic constraints can be mined
from environments and observations beyond
predefined policies, and whether they can im-
prove end-to-end task performance. We present
Symbolic Constraint Agents (SCA), a frame-
work that mines symbolic constraints from API
documentation, refines them against execution
traces, and checks the agent’s tool calls with
an SMT solver at runtime. A violation triggers
a natural-language warning or, when the valid
replacement is uniquely determined, an auto-
matic repair. On AppWorld, refinement raises
error-detection F1 from 37.0 to 58.3 on GPT-
5.5 traces and from 39.3 to 61.9 on Qwen3.5-
27B traces. At runtime, repair raises GPT-5.4-
mini’s task success by 5.4 points under a 40-call
budget and 9.8 points when environment errors
are hidden, while removing 59–87% of failed
calls across models, and transfers to τ 2-bench
with gains of up to 5.6 points. These findings
show that automatically acquired symbolic con-
straints can improve tool-calling reliability and
task completion, particularly when failures are
costly or difficult to diagnose.

### Introduction

Large language model (LLM)-based agents are
increasingly used to automate real-world tasks,
from customer service to complex workspace du-
ties (Trivedi et al., 2024; Gao et al., 2025; Fang
et al., 2026). A critical component of these agents
is tools, or external functions that allow agents to
read information from the environment and update
the environment state (Schick et al., 2023). As
*Work done during an internship at Microsoft Research.
agents interact with increasingly complex environ-
ments, how can we ensure that their tool calls are
valid?
Previous work primarily focuses on formalizing
predefined safety policies into symbolic constraints
and enforcing them on all tool calls by blocking vi-
olations for better policy adherence (Kamath et al.,
2025; Zwerdling et al., 2025). However, complex
tool-calling environments impose many rules that
are not explicitly codified as policies. These in-
clude dependencies between tool calls, argument
provenance requirements, and restrictions on the
current environment state (Trivedi et al., 2024; Shi
et al., 2025). Although some of these conditions
can be inferred from API documentation, others
become apparent only through successful or failed
interactions with the environment.
This raises two questions: How can we gener-
ate executable tool-call constraints without man-
ually specified policies, and can these constraints
improve agents’ ability to complete tasks rather
than merely enforce compliance? Addressing these
questions requires a coherent system that mines
constraints from diverse sources like policy and
tool documentation, refines inaccurate rules us-
ing observed execution behavior, and translates
detected violations into runtime interventions.
We propose Symbolic Constraint Agents (SCA),
which generate tool dependency constraints as
first-order logic rules and verify agents’ tool
calls with SMT (Satisfiability Modulo Theories)
solvers (de Moura and Bjørner, 2008) when each
call is executed in complex tool environments.
First, an initializer agent mines candidate rules
from the API documentation. Since relying solely
on API documents yields constraints that do not
reflect the real environment, a second refiner agent
removes overly strict rules and adds missing rules
using sample agent traces. At runtime, the agent re-
ceives information about violated constraints each
turn, guiding the agent to retry. Furthermore, for

We make three contributions. First, we introduce
an environment-grounded constraint mining frame-
work that mines executable tool-call rules from API
documentation and iteratively refines them against
execution traces, even without requiring manually
specified task-success criteria. Second, we develop
solver-based interventions that translate detected
violations into natural-language feedback, or au-

through experiments on AppWorld (Trivedi et al.,

diagnose, while reducing failed calls and inference
costs.

### 2


### Related Work

Tool-calling environments.
Tool-calling envi-
ronments evaluate agents’ ability to manage per-
sistent state, cross-application dependencies, and
long action sequences. Benchmarks like τ 2-Bench
(Barrès et al., 2025) focus on evaluating policy
adherence and user intent clarification via con-
versation, while benchmarks like AppWorld and
TheMCPCompany focus on tool planning and ex-
ecution for completing complex real-world tasks
(Trivedi et al., 2024; Esfandiarpoor et al., 2025;
Wang et al., 2025c). We evaluate on both kinds: Ap-
pWorld, whose large tool catalog, cross-application
tasks, and executable evaluator make tool depen-
dencies both necessary and measurable, and τ 2-
bench, where the dependencies come from a writ-
ten policy and many violations go unreported by
the environment.
Symbolic constraints for tool-calling agents.
Agent-C (Kamath et al., 2025) and ToolGuard (Zw-
erdling et al., 2025) translate safety policies into
first-order constraints, symbolically check whether
each tool call violates the constraints, and ap-
ply constrained generation or resampling to pro-
duce safe tool calls. Recent systems vary in what
a human must supply: AgentSpec (Wang et al.,
2025a) prompts an LLM with developer-written
seed rules, AgentLTL (Elkoussy and Perez, 2026)
instantiates constraints from a gold trace per task,
and AutoSpec (Ma et al., 2026) refines an expert-
authored guardrail against safety-labelled traces.
Instead, ours dynamically learns executable con-
straints from the environment’s response, minimiz-
ing human intervention and generalizing beyond
preexisting policies.
These works do not scale to environments with
hundreds of tools and no compliance criterion
(Trivedi et al., 2024; Esfandiarpoor et al., 2025),
because each still requires a constraint artifact au-
thored by hand for the target environment. None
evaluates whether constraints improve task com-
pletion either; for instance, Agent-C reports gains
only when a policy violation counts as a failure.
Memory for complex tool-calling environments.
With many tools, agents typically retrieve what they
need from API documentation on the fly (Qin et al.,
2024), so nothing learned in one episode carries to
the next. This motivates treating tool knowledge
as a reusable memory rather than as a per-query
retrieval problem. Initial work (Gao et al., 2025;
Lee et al., 2025) represented tool dependencies
as directed graphs and used them as memory to
augment relevant tool retrieval. However, these
graphs are obtained by expert annotation or a fine-
tuned classifier, and remain static between episodes.
This prevents the agent from actively updating and

### 3


### Symbolic Constraint Agents

3.1
Expressing tool calls in formal logic
Tool calls are sequential activities, which we model
using first-order logic. Specifically, we define the
sequence of tool calls using three predicates (unin-
terpreted functions).
call(t, c, f)
tool f is invoked at time t, with
unique call ID c,
params(c, k, v)
argument k of c has value v,
returns(c, k, v)
return field k of c has value v.
Values v are of primitive types including strings,
integers, reals, Booleans, and null. Complex data
structures, including maps and lists, are unrolled so
each primitive value is attached to the closest key.
Tool and field names are finite symbolic domains.
We introduce closed-world assumption state-
ments to prevent the SMT solver from inventing
unasserted facts about the tool-calling history. First,
we assume that for each timestep t, there exists a
unique call(t, c, f). Then, we assume that for all
past tool calls, parameters, and return values are
final; that is, for every call ID c, no params or
returns predicates with c exist other than the con-
junction of existing predicates. Appendix A gives
the full sorts, predicates, and axioms. Rules over
the call history or the call’s outcome account for
98% of flagged calls.
Under this formulation, constraints are formu-
lated as universally quantified rules. For example,
the constraint “If REGISTER tool was called, a sub-
sequent LOGIN must use the same id as used for
REGISTER" can be expressed as
∀t1, c1, v1, t2, c2, v2.
call(t1, c1, LOGIN) ∧params(c1, ID, v1)
∧call(t2, c2, REGISTER) ∧params(c2, ID, v2)
∧t2 < t1 →v1 = v2.
If the constraint is unsatisfiable (UNSAT) under
the current tool call facts, it indicates a violation.
For instance, the example above is unsatisfiable
if the LOGIN tool uses a different ID parameter
than what the previous REGISTER call returns. A
naive cumulative check can repeatedly report a con-
tradiction caused by an earlier call. We therefore
compute an unsatisfiable core and intervene only
when at least one rule in the core is instantiated by
the current call. Since solvers do not guarantee a
minimal core, this attribution is approximate rather
than exact. However, we observe that multiple
constraints being violated together is rare.
3.2
Constraint generation
The constraint generation process mines constraints
across different tools, including parameter value
dependencies and environment state dependencies.
Initialization from documentation.
The initial-
izer agent generates constraints for one target API
at a time. Since the full tool collection cannot fit

same id as used for REGISTER.”
Constraint generation proceeds incrementally
across target APIs rather than processing each API
independently: the model can attach a tool to an
existing parameter-level rule, create a new rule,
edit a rule shared across related tools, or remove
one found to be invalid, retrieving additional API
definitions whenever a dependency is unclear. Be-
fore entering the catalog, every candidate expres-
sion is parsed and type-checked. (Prompts in Ap-
pendix C).

3.3
Constraint application to agents
After refinement, we apply the symbolic constraints
to the agent runtime to improve performance.
Warning.
In
warning
mode,
SCA
checks
whether any constraint was violated after the en-
vironment returns the tool execution result, allow-
ing constraints to process both parameter-side er-
rors and return value-based recommendations. It
leaves the call unmodified and appends the violated
natural-language constraints to the agent context.
The model can then revise its plan or arguments.

Warnings preserve agent autonomy and are appro-
priate when corrections or alternative plans may be
valid; Figure 4 shows a recorded instance.
Repair.
Some invalid arguments have a unique
correct value already present in the trajectory, es-
pecially service-specific access tokens and entity
identifiers. In repair mode, SCA first detects an
unsatisfiable constraint before the tool call is made,
treats each argument leaf as a candidate change,
and uses MaxSMT (Bjørner et al., 2015) to find
a minimum-change assignment that satisfies the
previously violated constraints. Figure 5 shows a
recorded repair of a mistyped access token.
Repairs are applied conservatively only when
the replacement is unique, to prevent malformed
repairs that do not preserve user intent. After ob-
taining a candidate value v⋆via MaxSMT, SCA
asserts v ̸= v⋆and runs the solver again. If v ̸= v⋆
is unsatisfiable, v⋆is the only possible replacement
and is then passed to the environment. If more
than one value remains possible, SCA falls back
to a warning rather than silently choosing among
valid alternatives. If the constraints’ verdict was
UNSAT but without a unique repair, it behaves as
in warning mode, appending violated constraints
to the agent’s context.

### 4


### Experimental Setup

Benchmark.
We evaluate SCA on two tool-
calling benchmarks with different error structures.
AppWorld (Trivedi et al., 2024): we use the
test-challenge set (417 instructions). The App-
World environment exposes 457 APIs across nine
diverse stateful applications, including email, mu-
sic, notes, and contacts. Using these tools, the
agent should complete users’ tasks such as ac-
cepting Venmo transactions and sending emails
to friends. The default environment provides an
informative error message whenever the tool call
fails due to incorrect parameter values, authentica-
tion error, etc. (Standard) However, an agent can
often recover from a rejected call by reading the er-
ror message and retrying, so a prevented error may
only save cost. We therefore introduce two chal-
lenging variants of AppWorld that make tool errors
increasingly expensive: 40-call budget, where the
agent may make at most 40 tool calls instead of the
Standard setting’s 300, so every call spent on an
error is lost to the task; and silent errors, where the
environment rejects erroneous calls with an empty
response, which are harder for agents to recover
from failures (Zhang et al., 2026). For the silent
errors setting, the constraint generation/refinement
stage also does not access the full error message.
τ 2-bench (Barrès et al., 2025): we use the airline
and retail domains with 20 and 40 held-out tasks,
respectively. The agent serves an LLM-simulated
customer through booking and order-management
tools while following a written company policy,
and the official evaluator checks the final database
state and the required actions. Unlike AppWorld,
the environment does not reject malformed tool
calls, including ones that violate the policy (e.g.,
cancelling a reservation that the policy does not
allow to be cancelled), making it difficult for agents
to detect their own errors.
For tool navigation, the AppWorld environment
provides a default BM25-based search tool as a sep-
arate app. Initializer and Refiner agents in SCA’s
constraint generation stage utilize this endpoint to
search for relevant tools when generating/editing
constraints. τ 2-bench domains have few tools (14
in airline, 16 in retail), so the initializer and refiner
receive all tool definitions along with the full policy
in its context.
Constraint refinement data.
Refinement uses
the training set of AppWorld and τ 2-bench, con-
taining 90 and 104 prompts, respectively. We use
plain tool-calling LLM agents’ tool-calling histo-
ries to identify discrepancies between the current
constraint catalog and the actual environment, then
freeze the refined catalog before applying it to the
test set. We use GPT-5.5 for both initializer and
refiner agents. The refined catalogs contain 295
constraints for AppWorld, 51 for airline, and 63
for retail (Appendix D). We do not use the oracle
grader’s task-success evaluations to ensure SCA’s
generalizability when such graders are unavailable.
Models and conditions.
We evaluate GPT-5.5
and GPT-5.4-mini (OpenAI, 2026), Sonnet 5 (An-
thropic, 2026), Qwen3.5-9B and Qwen3.5-27B
(Qwen Team, 2026) as agent models; Qwen3.5-
27B is evaluated in Appendix F.1. For each model,
we compare standard tool-calling mode, SCA with
warnings, and SCA with automatic repair. Runs
share the task evaluator, agent harness, and tool
infrastructure (Appendix B); only the symbolic in-
tervention mode changes.

### 5


### Results

5.1
Quality of Generated Constraints
Tool-call error detection.
First, we evaluate
whether SCA can detect faulty calls that the en-
vironment will reject. The AppWorld environment
returns an error message whenever a tool call is
invalid for any reason, e.g., authentication errors,
an empty cart when submitting an order, etc. SCA’s
proposed constraints can therefore be evaluated via
binary classification: the ground truth is whether
a tool call returns an error, and the prediction is
whether a constraint is violated at the given step.2
Table 1 reports precision, recall, and F1 on tra-
jectories generated by GPT-5.5 and Qwen3.5-27B,
capturing both a strong proprietary model and a
weaker open-weight model. The results show that
using tool definitions alone (Initialize) produces
noisy constraints. Refinement with a small number
of traces raises precision by 28.9 points on GPT-
5.5 trajectories and 25.1 points on Qwen3.5-27B
trajectories in the test set, while recall increases by
16.6 and 19.5 points, respectively. This shows the
necessity and effectiveness of the refinement stage.
Maximum recall remains lower than precision,
primarily because some errors depend on environ-
mental conditions that cannot be inferred from
tool documentation or agent trace alone. For in-
stance, in AppWorld, whether a file actually exists
in the environment cannot be determined in ad-
vance. Consequently, the constraints cannot (and
should not be expected to) detect tool calls that
reference nonexistent files. Such calls are rejected
by the environment and counted as false negatives,
limiting achievable recall.
We further audit the constraint catalogs mined
from AppWorld and τ 2-bench using LLMs as a
judge. The results show that around 92% of the

5.2
Task Success and Efficiency
We compare three agents that differ only in how
the constraints are used: no constraints (the vanilla
tool-calling agent), warning (after each call, vio-
lated constraints are reported to the agent in the tool
response), and repair (before each call, a violating
argument is replaced by the value that satisfies the
constraints, when a unique such value exists in
the call history). All constraint runs use the same
refined catalog per benchmark, built once with
GPT-5.5 and frozen. We evaluate three proprietary
models (GPT-5.5, GPT-5.4-mini, Sonnet-5) and the
open-weight Qwen3.5-9B. We present single-run
results for Qwen3.5-27B in Appendix F.1, which
follows similar performance improvement trends.
Table 2 reports mean task success for every
(model, setting, mode) combination, along with
the standard deviation over three independent runs.
Table 3 reports the per-task cost of the same runs.
Constraints improve task success, most when
steps are limited. Constraints improve task suc-
cess for GPT-5.4-mini, Sonnet-5 and Qwen3.5-9B
in the standard and budget-limited AppWorld set-
tings with at least one of the two modes (Table 2);
for GPT-5.5, which already solves most tasks, suc-
cess rates remain stable. In the standard setting
with up to 300 calls, agents can usually recover
from a rejected call by retrying. This gives rela-
tively small gains: repair raises success rate from
73.5% to 75.1% for GPT-5.4-mini and from 77.3%
to 78.1% for Sonnet-5. Warnings can even cost
here: they lower GPT-5.4-mini and Sonnet-5 by
1.5–2.3 points, since a false alarm makes an agent
retry a valid call. Therefore, in the unrestricted
setting, preventing an error mainly saves cost (Ta-
ble 3). Under a tight 40-call budget, calls cannot
be wasted recovering from errors, so preventing
errors leads to higher success. Constraints improve

### 6


### Conclusion

SCA mines tool-call constraints in formal logic
from tool definitions and corrects them against
agent traces. Checked by a solver at runtime, these
constraints detect faulty calls and raise task suc-
cess while cutting failed calls and tokens through
warnings and repair. We demonstrate that these im-
provements generalize to realistic settings without
explicit domain policies or informative error mes-
sages, highlighting the potential of our approach for
building more controllable and trustworthy agents.

### Limitations

Constraints are built once with a strong proprietary
model (GPT-5.5) and refined on execution traces
of training tasks, which requires access to such
traces and incurs a one-time cost. Our constraints
check each tool call against the call history, so they
detect errors that are visible in that history: wrong
or miscopied arguments, calls in the wrong state,
missing prerequisites. They cannot detect failures
that depend on hidden environment state (e.g., a
credit limit the agent has not queried), and they
cannot detect omissions, where the agent never
makes a necessary call. This is why recall is much
lower than precision (Table 1), and why constraints
help little for agents whose failures are mostly of
these kinds, such as Qwen3.5-9B.
Improvements in task success are largest when
tool errors are costly or invisible and when the
agent makes many call-level errors. In the standard
AppWorld setting, success gains are small, and a
strong model that rarely makes these errors (Claude
Sonnet-5) benefits little. Warnings can also mis-
lead: a false alarm may cause an agent to retry a
call that was valid.

### Ethical Considerations

Symbolic constraints make tool-use agents more
reliable, but they are not a safety guarantee: mined
rules can be wrong or too strict, and a too-strict
rule can flag or alter a legitimate action. More reli-
able agents can also be used to automate harmful
actions, which our checker does not prevent. All
experiments run in simulated environments (App-
World, τ 2-bench) with synthetic users and no per-
sonal data. Constraint mining is a one-time cost per
environment, and repair reduces failed tool calls
and, for the weaker models, LLM calls and tokens
per task (Table 3).

### Formal Definition of SCA

This section describes the formal logic machinery
for detecting and repairing constraint-violating tool
calls under SCA.
A.1
Sorts and Predicates
SCA introduces four sorts: a unique ID for each
tool call, an enumeration of possible tool names
and field names, and parameter/return values. Ev-
ery concrete parameter or return value observed in
a trace is lifted into exactly one of the five construc-
tors.
CallID : String
ToolName : enumerated sort
FieldName : enumerated sort
Value ::= v_str(String) | v_int(Z) | v_real(R)
| v_bool(B) | v_null
Using these sorts, we define four predicates (unin-
terpreted functions) to express tool-call events.
call : N0 × CallID × ToolName →B
params : CallID × FieldName × Value →B
returns : CallID × FieldName × Value →B
finish : N0 →B
Here call(i, c, T) states that step i is call c of tool
T; params(c, f, v) states that call c was invoked
with parameter f = v; returns(c, f, v) states that
call c returned field f = v; and finish(i) states that
step i is the trace’s terminal action.

### B


### Implementation details

SCA is implemented as an agent in Open-
Hands (Wang et al., 2025b). It subclasses the Code-
Act agent (Wang et al., 2024), so the underlying
LLM agent, its prompts, and its tool handling are
unchanged. The environment’s tools are served to
the agent over a Model Context Protocol (MCP)
server. SCA operates by intercepting each MCP
observation before it reaches the LLM. It observes
the called tool, its arguments, and response, and
appends them to a running set of trace facts which
are then passed to the constraint checker.
Constraint checking uses Z3 (v4.16) through its
Python API. Tool and field names are Z3 enumer-
ation sorts, and argument and return values are an
algebraic datatype covering strings, integers, re-
als, booleans and null; lists and maps are unrolled
into their primitive leaves. For each check, the
trace facts are substituted into the uninterpreted
predicates call, params, returns and finish of
the scoped rules. Z3 then checks the result with
tracked assertions, and the unsat core identifies the
violated rules. To keep checks fast, SCA lifts trace
facts into Z3 terms incrementally and caches them
across steps. It asserts only the rules scoped to
the called tool, and each check has a 5 s timeout.
A warning is appended in place to the text of the
MCP observation. A repair runs as a dry-run check
on the proposed MCP action before dispatch, us-
ing a snapshot of the trace and cache that is rolled
back afterwards. When the repair is unique, SCA
rewrites the action’s arguments in place, so the en-
vironment executes only the corrected call. Repairs

are computed with Z3’s Optimize (MaxSAT with
soft constraints on the original values), followed
by a second solver call that checks uniqueness. Ev-
ery check, warning, and repair is logged with its
verdict and the rules involved.

### Constraint Catalogs

Each constraint pairs a natural-language rule with
an SMT formula over the call history. The for-
mula quantifies over calls call(i,
c,
tool)
(position i, call c), their parameters params(c,
field, value), and the fields of their responses
rfield(c, field, value), the returns predi-
cate of Section 3.1; __TARGET__ stands for each
tool the rule applies to. We group rules by what
their formula refers to: argument rules check only
the arguments of the call itself (e.g., value ranges
and formats); history rules relate the call to other
calls in the history, e.g., that an access token was
returned by a prior login to the same app; outcome
rules read the response of the call itself, e.g., that
an order did not fail because the payment card has
expired, and can therefore only be checked after the
call returns (warning mode). Table 4 summarizes
the catalogs used in our experiments, and Table 5
shows one example from each type.

### E


### Detailed Audit on Constraints

We audit every rule of the five catalogs used in
our experiments (500 rules; Table 4). Three LLM
judges from two model families (GPT-5.6 Sol, GPT-
6 Astra, and Claude Opus 5.5) label each rule in-
dependently. Each judge sees the natural-language
rule, its corresponding Z3 formula, the definitions
of the tools mentioned in the formula, and the do-
main policy (for τ-bench). The judge answers two
questions: faithful – does the formula express the
same condition as the natural-language rule? – and
validity – is the rule correct (violating calls would
fail or break a domain rule, and valid calls satisfy
it), too strict (it also rejects some legitimate calls),
wrong, or unsure. We take the majority label; there
was a majority for every rule. All three judges
agree on 87% of rules for faithfulness and 78% for
validity.
To validate the LLM judge evaluations, one au-
thor labeled 50 rules without seeing the three LLM
judges’ labels: 35 rules flagged by 2 or more judges
and 15 rules accepted by all three. The author
agreed with the judges on 94% of rules for faithful-
ness and 90% for validity, showing strong human-
LLM agreement. There were 5 cases where the au-
thor judged the rule as valid, but the judges did not;
for example, the judges called “task_comment_id
must come from an earlier call that created or listed
comments” too strict because an ID could come
from the task, but in AppWorld such IDs can only
come from those calls.
Table 6 summarizes the results. The ratios of
faithful and valid rules are both measured around
92%. While argument rules and outcome rules
are almost always correct (99% and 100%, re-
spectively), history rules remain only 67% correct.

F.2
Ablation
In Section 5.1, we show that refinement is essential
for improving the error detection performance. We
next examine whether refinement is necessary for
end-to-end performance. In the warning mode on
AppWorld, we compare agents using the catalog
produced by initialization alone against agents us-
ing the refined catalog. As Table 10 shows, remov-
ing refinement lowers task success by 3.5 points
for GPT-5.5 and 2.4 points for Qwen3.5-27B. In-
specting the trajectories, we find that agents given
spurious warnings often retry, and sometimes loop
on, tool calls that were in fact valid: the low preci-
sion of the unrefined catalog (Table 1) propagates
directly into lower task success.
