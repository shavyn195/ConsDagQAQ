Capability-Grounded Agentic Planning
Shikha Shrestha
William Yeoh
Ning Zhang
Yevgeniy Vorobeychik
Washington University in St. Louis
Abstract
LLM agents serve natural-language requests
through tools, data sources, and other agents,
and even simple requests often need several in-
terdependent calls. Typically, the LLM picks
these calls by trial and error, with no guarantee
of an executable plan. We present Capability-
Grounded Agentic Planning (CGAP), which in-
stead reasons about what a request requires and
what tools provide. CGAP compiles the tool
catalog deterministically into a PDDL model,
uses an LLM to turn the request into goals,
and solves the model with a classical planner.
Since tool outputs are unknown in advance, the
model is abstract, tracking which inputs are
available, not their values. During execution,
an LLM adds entity-specific calls that abstract
plans omit, and deterministic checks reject any
that break the plan. Every argument is drawn
from a cited source, such as a conversation span
or an earlier tool response, and each requested
result counts as delivered only after an LLM
verifier checks it against the request. With three
LLMs on ToolSandbox, ComplexFuncBench,
BFCL multi-turn, and τ 2-bench retail, CGAP
outperforms a standard tool-calling agent by up
to 28.9 points.

Introduction
LLM agents are increasingly used to retrieve infor-
mation and act on behalf of users through external
tools (Yao et al., 2023; Qin et al., 2024). How-
ever, both the tasks to solve and the tools that solve
them are described in natural language (NL), which
is imprecise and highly flexible. The LLM that
drives the agent must therefore both understand the
request and construct an executable plan for it, and
even simple requests require several interdependent
operations. For example, with basic forecasting,
date-lookup, and geolocation tools, a request for
the “weather in Paris and Nice next Monday, and
in Nice on Tuesday” takes seven calls: two city
lookups, two date resolutions, and three forecasts,
with the outputs of some calls supplying the inputs
of others.
ReAct-style agents address such problems by in-
terleaving reasoning with tool calls, choosing one
call at a time (Yao et al., 2023), while plan-first
systems such as HuggingGPT, ReWOO, and LLM-
Compiler write out a task decomposition or depen-
dency graph before acting (Shen et al., 2023; Xu
et al., 2023; Kim et al., 2024), a strategy that Plan-
and-Solve also applies to reasoning tasks (Wang
et al., 2023). However, both classes of approaches
use the LLM for both request interpretation and
planning, so nothing guarantees that a call’s in-
puts will be available when it runs. LLMs also
have documented limitations on formal planning
problems (Valmeekam et al., 2023), and intrinsic
self-correction can fail without external feedback
(Huang et al., 2024). LLM-based agentic workflow
planning therefore remains unreliable, particularly
with smaller (and cheaper) LLMs.
Hybrid (neuro-symbolic) alternatives combine
LLMs with formal planners.
Many, such as
LLM+P, use an LLM to translate a planning prob-
lem or action model into PDDL (McDermott et al.,
1998) for a classical planner (Liu et al., 2023; Guan
et al., 2023; Tantakoun et al., 2025), while LLM-
Modulo frameworks pair LLM proposals with ex-
ternal critics (Kambhampati et al., 2024). These
approaches start from actions that are described
formally or that the LLM writes down, and a plan
is only as valid as that model. Tool-using agents
instead work from NL specifications of requests
and tool capabilities, in an open world: the values
that their tools take and return are unknown until a
call returns, and they do not come from a finite set
that a symbolic planning model can enumerate.
We propose Capability-Grounded Agentic Plan-
ning (CGAP), a framework for agentic workflow
planning. CGAP reads the NL request together
with the catalog of capabilities available to the
agent, such as tools, data sources, or other agents,

each with an NL description and the input schema
that function-calling interfaces require; the LLM’s
own abilities, such as summarizing, are not mod-
eled as capabilities. CGAP compiles the catalog de-
terministically into a PDDL planning model, with
required inputs as preconditions and outputs as ef-
fects (§2.2), and an LLM parses the request into
one goal per requested result (§2.3). For open-
world inputs and outputs, the model abstracts away
values: it tracks only which named inputs and out-
puts (fields) are available, a finite set fixed by the
catalog. A classical planner solves this model, and
LLMs then turn the abstract plan into executable
calls and verify that their results match the request.
Our experiments test whether deriving the depen-
dencies between calls from this model improves
tool use over having an LLM generate them. We
instantiate the planner with state-space search, and
we also evaluate a deterministic dependency-graph
planner that ignores delete effects, to see how much
of the gain remains without them. Figure 1 shows
one user turn of this process.
In the weather example, the planner cannot pre-
dict what the tools will return, so the planning state
records only whether a value is available for a field
such as latitude, an output of the city lookup
and a required input of the forecast, and not which
city it describes. Each requested forecast is a sep-
arate goal, but one city lookup makes coordinates
available for every forecast, so the planner returns
a five-action abstract plan for a request that takes
seven calls (Figure 2). An execution LLM pro-
poses the entity-specific calls the plan omits, here a
lookup for Nice and a second date resolution, and
a deterministic runtime, which checks every call
before it runs, accepts such a proposal only if the
remaining plan stays valid. Every argument must
cite its source, so each coordinate can be traced to
the lookup that produced it, and a forecast counts
as delivered only after deterministic checks and an
LLM verifier accept the call that produced it.
We make three contributions:
• Neuro-symbolic agentic planning. CGAP, a
hybrid approach that compiles tool catalogs de-
terministically into an abstract, field-level PDDL
model that can be solved before tool outputs are
known, uses an LLM to turn the request into its
goals, and solves the model with classical plan-
ning (§2.2, §2.3).
• Checked execution with provable guarantees.
A runtime that validates the entity-specific calls
LLMs add, instantiates arguments from cited
sources, and verifies each requested result; every
execution it admits maps onto a valid abstract
plan, so exhaustive search failure certifies infea-
sibility for the compiled catalog (§2.5).
• Experiments on four tool-using agentic bench-
marks. With three LLMs on ToolSandbox, Com-
plexFuncBench, BFCL multi-turn, and τ 2-bench
retail, CGAP outperforms a standard tool-calling
agent in all 15 model–metric comparisons and,
with gpt-oss-20b, four further baselines.
Re-
placing deterministic dependency planning with
LLM-generated plans costs up to 16.8 points, less
with GPT-5 mini; a deterministic graph planner
retains most of the gain, and search adds to it
where actions have delete effects (§3).
Related work.
A common way to organize tool
use is a graph of tool dependencies. TaskBench and
ToolNet build such graphs explicitly (Shen et al.,
2024; Liu et al., 2024), Wu et al. (2024) plan on
them with graph neural networks, and NaviAgent
and GRAFT add execution feedback and learned
dependencies, respectively (Jiang et al., 2026; Gao
et al., 2026). CGAP instead derives dependencies
deterministically from capability interfaces and lets
them govern execution through validated entity-
specific refinements, source-grounded arguments,
and per-operation completion records. Our graph-
planning variant shares this model and runtime,
so comparing it with search isolates the value of
reasoning about delete effects, such as a call that
switches off a setting a later call needs (§3.3). The
planners closest to ours are the lifted regression
methods LLM-Regress and NL-PDDL, which use
an LLM to supply commonsense knowledge dur-
ing planning (Liu et al., 2025, 2026); they keep
entities as variables, whereas CGAP drops entity
distinctions and leaves them to execution. Agent+P
likewise pairs a UI transition graph with a sym-
bolic planner (Ma et al., 2025). Appendix F relates
CGAP to service composition, API synthesis, ex-
ecutable request representations, attribution, and
prompt-injection defenses.

The catalog C lists capabilities, such as tools,
data sources, API operations, or other agents. Each
has an NL description and an input schema, which,
as in function-calling interfaces, names its parame-

servation rules, transformations, and authorization
rules. For a capability c, we distinguish its ac-

2.2
Compiling the catalog into a planning
model
To order calls, the planner must know which ca-
pabilities produce the inputs of others; CGAP
reads this off the parameter names in the catalog’s
schemas, so the catalog needs no planning syntax.
Facts.
Let X be the set of fields, the names of
the inputs and outputs that the catalog’s schemas
declare (e.g., city, lat, date), after a fixed nor-
malization (Appendix A.1). Function-calling cata-
logs always name their inputs; outputs are named
by return schemas where given and are otherwise
inferred, as described next. The fact Available(p)
holds when some value for field p has a source,
that is, a span of a user message or an expected
output field of a successful response (R1, §2.4).
Application-supplied domain predicates describe
other conditions, such as the observed state of a de-
vice setting, and Success(i) records that requested
operation i is complete. We write F for the set of
facts; a state s ⊆F is the set of facts that hold.

Domain predicates capture prerequisites and

not express. CGAP takes these rules as application-

them from natural-language descriptions is outside
our scope. The annotations describe reusable capa-

action sequence for each request. In ToolSandbox,

Abstract plans.
The state records that a latitude
is available, not whose latitude it is: coordinates for
Paris and for Nice both establish Available(lat),
and the values and their sources stay in the con-
versation history. This is deliberate: values are
unknown before a call, so a value-indexed state
would force the planner to predict responses, and
catalogs say what a capability returns, not which
request a returned value will serve. It also keeps
the fact vocabulary independent of the number of
entities, as in generalized planning, which seeks
plans that hold for any number of objects (Silver
et al., 2024), although CGAP still plans for each
request. Following the principle of planning ab-
stractions (Sacerdoti, 1974; Knoblock et al., 1991),
we call a plan over this model an abstract plan;
its actions are capabilities without arguments, not
composite tasks as in HTN planning. It fixes which
requested results must be produced, which kinds of
prerequisites each needs, and in what order, but not
how many copies of a supporting call distinct enti-
ties require. This is why the weather plan has three
forecasts but one lookup: each requested result is a
goal of its own (§2.3), whereas one lookup makes
lat available for every city. Execution supplies the
missing copies under validation (§2.4), and Sec-
tion 2.5 shows that every compliant execution still
maps onto a valid abstract plan.

2.4
Planning and grounded execution
Within a turn, search and execution alternate (Algo-
rithm 1) under three budgets: B state expansions
per search, L actions per refinement, and N execu-
tion decisions per turn. These are hyperparameters,
fixed in advance and shared by all benchmarks and
LLMs (B = 2,048, L = 4, N = 32).
Search and execution decisions.
Breadth-first
search solves Pt,k (Algorithm 2) and returns a
shortest abstract plan, NOPLAN if it has expanded
every reachable state without reaching Gt, or
LIMIT if it has expanded a predefined number B
of states first. In the running example, the plan has
one city lookup, one date resolution, and three fore-
casts (Figure 2(a)). Execution then works through
this plan; after k calls, the remaining plan ¯πt,k is
the part of it not yet executed. Given ¯πt,k, an ex-
ecution LLM Eϕ proposes one of three decisions,
each counting toward N: 1) EXECUTE, which sup-
plies argument sources for the first planned action;
2) REFINE, which proposes supporting actions ρ to
prepend when the plan needs an input for which no
source exists; and 3) STOP, which asks the user for
clarification or reports work that cannot be done.
We describe EXECUTE and REFINE next.
The LLM never writes an argument value. Each
argument of an EXECUTE decision cites a source,
a span of the conversation or a field of a successful
response, and a resolver from a fixed set that the
LLM cannot extend: a decoder copies the cited text
or converts it to the schema’s type (e.g., "2" to the
integer 2), and a transformation is a deterministic
function supplied by the application, such as a date
converter. Application defaults are also allowed.
Before calling, the runtime checks the action’s
preconditions in It,k, the argument schema, the
sources, and the application’s authorization rules.
Whether a sourced argument refers to the intended
entity is assessed after the call by the completion
verifier, so for tools with side effects this check
cannot undo a wrongly targeted action.
Refinement (REFINE) is how an abstract plan
becomes a concrete one. After the Paris forecast,
Available(lat) still holds, but no source contains
the coordinates of Nice. Eϕ therefore prepends
a lookup for Nice, and later a date resolution for
Tuesday, so that five planned actions become seven
calls (Figure 2(b)). A refinement holds at most L
actions, each a recursive achiever of a precondi-
tion of a pending terminal action, and no terminal
actions. It is kept only if ρ ∥¯πt,k, the prepended
actions followed by the remaining plan, is valid
from It,k (Appendix A.5). A refinement can there-
fore add supporting calls, but it cannot add, re-
move, or reorder the terminal actions of the current
plan; only search can reorder them. Validation also
cannot tell whether a refinement is needed: a re-
dundant second lookup for Paris passes as easily
as the lookup for Nice, so necessity is left to the
LLM. Without delete effects (ComplexFuncBench,
BFCL, τ 2-bench retail), added facts cannot break
the remaining plan, so only the prefix is checked.

2.5
What the planner and the runtime certify
Proposition 1 follows from the runtime checks
alone, so it also holds for the planner ablations
(§3.3), as does Proposition 2(b); only exhaustive
search, however, certifies that no plan exists.
Proposition 1 (Runtime invariants). In every turn
t of Algorithm 1 and for every k:
(i) Applicability. Every called action’s precondi-
tions hold in It,k at the time of the call, and
the terminal actions of the remaining plan
are, in order, a suffix of those in the plan last
returned by search.
(ii) Provenance. Every argument value is com-
puted by a decoder or an application-
supplied transformation from user spans or
successful-response fields in Ht,k, or is a de-
fault the application configured for that argu-
ment.
(iii) Completion accounting. Every Success(i) ∈
Dt,k is backed by an accepted completion
record for a successful call of ci, made in turn
t or inherited from an unchanged operation,
and distinct markers by distinct calls.
These structural invariants are proved in Ap-
pendix B. A cited source, transformation, or de-
fault may still yield a wrong value, the verifier that
accepted a record may be wrong, and the free-form
final reply is not constrained.
Proposition 2 (Executions refine abstract plans).
(a) Every plan that Algorithm 2 returns on Pt,k is
valid and has the fewest actions among valid plans.
(b) Map each successful call of c to aterm
i
if it yields
an accepted completion record for oi, and to ac oth-

the runtime enforces R1–R3 against arbitrary LLM
proposals. Through (c), NOPLAN, unlike LIMIT,
certifies that no call sequence passing the runtime’s
checks can complete the request, but only for the
compiled model: an undeclared output cannot en-
able an action (R1). The count in (b) is loose on
multi-entity requests, and we do not use it.

Experimental setup
Benchmarks.

4
Conclusion
We presented CGAP, a neuro-symbolic approach in
which LLMs interpret requests, ground arguments,
and judge results, while a classical planner orders
calls over an abstract model compiled from the tool
catalog. On four benchmarks, it outperforms plain
tool calling with all three LLMs; LLM planning in
place of its deterministic planner lowers 14 of 15
model–metric scores (clearly with the open models,
slightly with GPT-5 mini), a dependency-graph
planner retains most of the benefit, and search adds
to it where actions have delete effects.
Limitations
Our guarantees hold only for the compiled model
and runtime rules: NOPLAN certifies infeasibility
only for the catalog as compiled, and because the
abstraction merges entities, the call count of Propo-
sition 2(b) is loose on multi-entity requests. How
often turns end in NOPLAN rather than LIMIT, and
hence the certificate’s practical value, is unmea-
sured. Request parsing can misread an operation,
a cited source can be wrong or tied to the wrong
entity, and the verifier can accept an incorrect result

and, running after the call, cannot undo a wrong
side effect; we have not audited how often these
errors, or unnecessary refinements, occur. Name-
based field matching can miss or conflate connec-
tions, and breadth-first search is exponential in the
number of facts, so its budget can stop it before
a plan is found. We evaluate on subsets of three
English benchmarks and on τ 2-bench retail with
three LLMs, under a majority-of-three protocol
not comparable to single-run leaderboard scores,
and our planner ablations exclude specialized plan-
ning systems.
State-dependent planning needs
application-supplied domain rules when the catalog
does not expose prerequisites and effects, which
adds a modeling burden, and evidence that handling
delete effects helps beyond access to this informa-
tion comes from one domain and one model. The
advantage of deterministic over LLM planning is
model-dependent: with GPT-5 mini, only the Tool-
Sandbox interval excludes zero, and the ablation’s
INVALIDPLAN rate partly reflects its one-repair
budget. The additional baselines use only gpt-oss-
20b (the dependency-notes agent only ToolSand-
box), our ReWOO adaptation adds replanning and
an ask-or-decline step, and another LLMCompiler
adaptation might beat the plain agent outside Tool-
Sandbox. Finally, CGAP uses 1.3–1.6 times the
plain agent’s tokens per task with gpt-oss-20b (Ta-
ble 9); we report tokens only with that model, on
τ 2-bench retail only as a ratio, and do not measure
latency.
Ethical Considerations
Tool calls can affect external systems. Argument
provenance records where each value came from;
authorization, privacy, and the decision whether an
action is appropriate remain the application’s job,
so applications must enforce access controls and,
where appropriate, ask for confirmation before con-
sequential calls. Retained source spans and tool
responses can contain sensitive information and
need suitable access and retention controls. Our
experiments use public benchmarks and involve no
human subjects. We do not evaluate resistance to
adversarial prompt injection or deployment safety,
and we do not claim that the planning and account-
ing invariants provide such protection.

A
Construction and execution details
This appendix fills in the details of Section 2. Algo-
rithm 1 gives the full loop of one turn, and Table 3
collects the notation. The search subroutine (Algo-
rithm 2) and the proofs of Propositions 1–3 are in
Appendix B.
Formal assumptions.
Each search call uses a fi-
nite catalog and a finite, fixed set of actions and
facts. Compilation is deterministic for fixed inter-
faces, normalization rules, and action annotations,
and schemas and predicates are checked for well-
formedness before use. Symbolic transitions are
deterministic and apply both add and delete ef-
fects. Initial domain facts and observation rules
are supplied explicitly, and the maintained state
changes only through validated observations and
those rules. The budgets B, N, and L are finite,
so the procedure terminates as long as every LLM
call, validator, and invocation terminates or times
out.
A.1
Action construction
In(c) contains the fields listed as required at the
top level of the input schema. We do not expand
oneOf/anyOf input branches into separate actions;
branch-specific requirements are instead checked
against the full schema before invocation. Output
extraction traverses nested properties, array items,
and referenced definitions, with cycle detection
for recursive references, and takes the union of
attribute names across alternative branches. Avail-
ability predicates do not record response paths or
branch conditions, so an optional or conditional
attribute counts as a possible output. The return
schema itself is kept for use as evidence.
For scalar or uninformative return types, nam-
ing rules apply to capability names that begin
with find, get, identify, lookup, resolve, or
search.
The tokens after the verb and before
an optional by clause name an output field, and
generic endings such as details and results are

A.5
Execution decisions and validation
To find the supporting actions allowed for a pending
operation, we trace the preconditions of its terminal
action backward through the catalog. Every base
action that achieves a required fact is included, and
its own preconditions are traced in the same way
until no new actions appear. A refinement prefix
may contain at most L actions from the union of
these sets and no terminal actions, and the prefix
followed by the remaining plan must satisfy Equa-
tion 2. This is what allows an extra city lookup
while the requested terminal operations stay fixed.
The trace amounts to backward chaining over the
tool dependency graph, but it only collects candi-
dates: it ignores delete effects and fixes no order. In
CGAP, the order of every plan comes from forward
search, or from a refinement that is checked against
the full model, delete effects included.
An EXECUTE proposal must select the first ac-
tion of the validated plan. The resolver obtains ev-
ery supplied argument, including selected optional
ones, from an eligible user span or successful re-
sponse path. Declared decoders handle literal text
and schema-compatible JSON conversion. Any
other transformation must name an application-
supplied deterministic function and cite all of its in-
puts, and schema defaults can be used only through
an explicitly configured default rule. The LLM
cannot register transformations or invent response
paths. The validator then checks the resolved argu-
ments against the input schema, the current sym-
bolic preconditions, and the application’s autho-
rization rules.
For completion verification, the verifier receives
the operation requirement, its user evidence, the ar-

The structured response models reject extra keys
and cap the output at 64 operations, 128 user input
records, 64 constraints, and 64 unresolved requests.
An output that exceeds a cap fails validation in-
stead of being truncated, so every accepted turn has
|Gt| ≤64. No request in our evaluation reached
these caps.

D.1
Why LLM planning fails
Two effects separate LLM planning from search.
LLM-written plans often fail validation: 23% of
LLM-planning turns with gpt-oss-20b end in IN-
VALIDPLAN after the repair, against 19% with
Qwen3-32B and 4% with GPT-5 mini, an ordering
that matches the ToolSandbox and BFCL multi-
turn gains in Figure 3; CGAP’s search ends in NO-
PLAN or LIMIT in 11% of turns. Valid LLM plans
also do worse: on tasks where LLM planning never
produced an invalid plan, CGAP leads by 9.8 points
[5.1, 14.4], a descriptive comparison since these
tasks are not a random sample. State-dependency
scenarios show the second effect most clearly: they
have the largest gap but only 17% INVALIDPLAN
turns, so much of that gap comes from plans that
pass validation but take extra or misordered state-
changing steps. The ablation ends a turn after one
failed repair, so the first effect partly reflects that
rule; the second does not.

LLMCompiler.
In LLMCompiler (Kim et al.,
2024), the LLM writes a dependency graph of
calls instead of a sequence: a planner emits num-
bered tasks with their dependencies, a scheduler
dispatches each task once its inputs are available,
and a joiner decides whether to reply or replan. We
start from the authors’ implementation (commit
a00c9d3) and keep its planner, plan parser, depen-
dency scheduler, and join-and-replan loop, extend-
ing them through wrappers and subclasses. The
benchmarks required five changes. (1) Each bench-
mark function is exposed under an alias together
with its original name, description, and complete
argument schema. A planned call takes one dic-
tionary of named arguments, validated against the
schema before dispatch, and references to earlier
results may appear anywhere inside it; reading a
nested field of a result requires observing the result
and replanning. (2) The planner and the joiner sub-
mit their output through two functions that execute
no benchmark tools, and a malformed output gets
at most two repair attempts. (3) We added generic
examples of dependency planning, of replanning
after an identifier is found, and of asking for clari-
fication; every planner and joiner call receives the
current tool catalog and the benchmark’s policies.
(4) Each user turn starts a new compiler session
that receives the visible conversation history and
the actual results of earlier calls, but no reference
trajectories or hidden evaluation state. (5) Plans are
not streamed, and the scheduler hands ready calls
to each benchmark’s own driver, which executes
them one at a time to preserve environment state, so
our runs do not measure LLMCompiler’s parallel
speedup. Changes (1), (2), (4), and (5) adapt the in-
terface, while (3) is our addition. Each user turn, or
single-turn episode, allows at most 32 model calls,
counting planner, joiner, and repair calls, and 32
tool attempts, matching the 32 execution decisions
of the planned agents. In our runs, its lower suc-
cess rates were associated with invalid planner or
joiner outputs, incorrect tool arguments, and turns
that ended before all required calls were made. It
also uses more tokens per task than CGAP on every
benchmark in Table 9, 1.1–1.5 times as many.
