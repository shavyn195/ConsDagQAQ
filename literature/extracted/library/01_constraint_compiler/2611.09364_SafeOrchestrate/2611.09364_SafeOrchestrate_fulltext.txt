Abstract. Modern cyber-physical systems (CPS) integrate heteroge-
neous sensors, actuators, controllers, and services, composed at run-
time rather than at design time. Orchestrating such systems through
natural language (NL) is attractive, but unconstrained large language
model (LLM) tool use is risky because actions must respect device ca-
pabilities, runtime state, and safety constraints. We present SafeOrches-
trate, a reference architecture for runtime-checked, intent-driven CPS
orchestration. Given an NL intent, it derives atomic goals, generates a
runtime-checkable specification for each, grounds the specifications to
device affordances, and verifies candidate actions against runtime state
and safety constraints before execution. In a Web of Things (WoT) in-
stantiation, the architecture produces Linear Temporal Logic-style spec-
ifications from the NL intent, grounds them to Thing Description (TD)
affordances exposed through the Model Context Protocol (MCP), and
checks candidate actions against satisfiability modulo theories (SMT)-
backed guardrails. We evaluate this instantiation on simulated smart
home, greenhouse, and industrial automation tasks against a direct LLM-
to-MCP baseline. SafeOrchestrate maintains 100% required-action accu-
racy on every task and 100% MCP Execution Similarity (MCP-ES) on all
but one, where MCP-ES is 92%. By contrast, the baseline degrades on
multi-device, event-triggered, and ordered tasks, with MCP-ES falling
to 13%. Because the tasks are largely single-rule with an empty con-
straint set, the SMT layer’s cross-rule and safety-constraint checking is
demonstrated on a worked example, not quantified; within that scope,
the results suggest that combining LLM-based specification generation
with role-aware grounding and runtime constraint checking improves re-
liability for open CPS orchestration without enriched TD annotations or
planning-domain expertise.

Introduction
Cyber-physical systems (CPS) are increasingly assembled from independently
developed constituent systems (CSs), such as sensors, actuators, controllers, and
cloud services. Composed at runtime, these CSs can support systems-of-systems
(SoS) behavior that no individual CS provides [16,3]. For example, a smart
building can coordinate lighting, ventilation, and occupancy sensing; an agri-
cultural setup can jointly react to temperature, humidity, and soil moisture;
and an industrial cell can coordinate perception, manipulation, and material
handling. Historically, composition logic was fixed at design time: closed-world
deployments rely on known CSs, fixed formats, and hard-coded rules. Open SoS
deployments, by contrast, operate in dynamic environments and must adapt to
unanticipated CSs, behaviors, and events [19]. Their required behavior depends
on the current deployment, available devices, and operator intent rather than on
a workflow known in advance, so composition must happen at runtime.
Realizing runtime composition is difficult [1] because CSs are highly heteroge-
neous, differing in communication protocols, data schemas, interaction patterns,
and operational assumptions. To reduce this heterogeneity, different domains
describe CSs with standardized, machine-interpretable capability descriptions:
OpenAPI for web and software-intensive SoS [14], OPC UA and AutomationML
in industrial automation [5,4], and URDF in robotics [15].
The Web of Things (WoT) is one such standard, aimed at cross-domain in-
teroperability for connected devices [20]. In WoT, Thing Descriptions (TDs)
describe physical or virtual Things using JSON-LD metadata and expose in-
teraction affordances as properties, actions, and events, while protocol bindings
abstract away the underlying communication mechanisms (e.g., HTTP, MQTT,
or CoAP) [21]. However, TDs mainly state what each Thing can sense or do;
they do not determine how multiple Things should cooperate, how a natural-
language (NL) goal should be operationalized, or whether a proposed action is
safe in the current state.
Prior work approaches this gap along three lines: WoT mashup generation
composes Thing affordances into higher-level behavior, typically as reusable
design-time artifacts [6,8,7]; LLM-assisted mashup synthesis turns NL intent into
planning artifacts or executable flows [17,22,18]; and verified LLM tool execu-
tion gates individual tool calls against pre-existing contracts [10]. None provides
the intervening orchestration layer: one that derives coordination logic from NL,
binds it to affordances discovered at runtime, and enforces safety before any
physical action.
In this paper, we present SafeOrchestrate, a reference architecture for
runtime-checked, intent-driven CPS orchestration, where an intent is an NL
goal. Instead of prompting an LLM to generate workflows directly or invoke
device interfaces freely, SafeOrchestrate grounds NL-derived specifications to
executable affordances and checks candidate actions before execution. Our
WoT instantiation realizes the architecture through Linear Temporal Logic
(LTL)-style specification generation, TD affordances exposed as Model Context
Protocol (MCP) tools and resources, and satisfiability modulo theories (SMT)-

We investigate the following research question (RQ): How does grounding NL-

1. We propose SafeOrchestrate, a reference architecture for LLM-driven CPS

and SMT-backed runtime guardrails over MCP-exposed affordances.
2. We introduce MCP Execution Similarity (MCP-ES), an alignment metric be-

Background and Related Work
In the WoT literature, a mashup is an application-level composition of multiple
Thing affordances, such as reading a sensor property and invoking one or more
actuator actions in response. WoT mashup research has long used intermediate
artifacts to represent and validate such compositions. System Descriptions (SDs)
encapsulate sequence-diagram-based atomic mashups as reusable affordances [6],
while DyST mines device interactions to reconstruct sequence diagrams and SDs
for validation [7]. A-MaGe reduces manual design effort by generating candi-
date atomic mashups from TDs and user options [8]. These approaches support
reuse, generation, and validation, but remain tied to sequence diagrams, SDs,
templates, rules, or user selection rather than to guarded execution over live
affordances.
Several recent systems use LLMs to reduce the manual effort of creating IoT
and WoT workflows from NL intent. LLM-MaGe translates user intent and TDs
into Planning Domain Definition Language (PDDL) artifacts [17], but its TD-
to-planning conversion depends on enriched annotations such as affects and
isAffectedBy, limiting compatibility with ordinary TDs. IoT Whisperer gener-
ates Node-RED workflows from NL descriptions and TDs [22]. AmI HMAS maps

SafeOrchestrate differs from all three: WoT mashup generation, LLM-assisted
synthesis, and verified tool execution. Unlike template-, rule-, or selection-driven
mashups, it derives coordination logic from NL rather than from design-time ar-
tifacts; unlike planning- and workflow-generation systems, it grounds that logic
to affordances discovered at runtime over MCP, without the enriched TD anno-
tations that systems such as LLM-MaGe require; and unlike per-tool contract
verification, it checks candidate actions against the grounded current state at
execution time rather than against pre-authored contracts.

Proposed Method
3.1
Architectural Overview
SafeOrchestrate takes device capability specifications and an NL intent g as
input. The proposed reference architecture, shown in Fig. 1, is defined as:
A = ⟨Bmcp, Dam, Gf, Gm, Tr, Vg, Or⟩
where Bmcp is the MCP Bridge (device abstraction layer); Dam the Atomic
Goal Decomposer (compound goal →atomic mashup candidates); Gf the For-
mula Generator (NL →runtime-checkable specification); Gm the Grounding
Mapper (symbolic →executable mapping); Tr the Temporal Resolver (formula
→reactive rules); Vg the Guardrail Verifier (constraint enforcement); and Or
the Runtime Orchestrator (execution coordination).
3.2
MCP Bridge (Bmcp)
Bmcp transforms device capability descriptions into MCP-compatible runtime
affordances. Actions, properties, and events become executable tools and observ-
able resources. At runtime, Bmcp exposes the executable tools Tt = {t1, . . . , tn}
and observable resources Rt = {r1, . . . , rm} available at time t. These affordances
form the substrate for grounding, guardrail checking, and execution, and they
hide device protocols from subsequent components. In the WoT instantiation,
TDs are converted into MCP tools and resources; in general CPS contexts, de-
vice APIs, URDF robot descriptions, or other specifications undergo analogous
transformations.

3.3
Atomic Goal Decomposer (Dam)
A compound NL goal often bundles several independent behaviors. Dam splits g
into atomic goals Dam(g) = {am1, am2, . . . , amk}, where each atomic goal ami is
a single, indivisible unit of intended behavior: one observed condition paired with
the action it should trigger. Each ami is treated as an atomic mashup candidate
(in the WoT sense, hence the subscript am) with input and output interactions.
Inputs are observable conditions (property reads, sensor values, events, or status
checks); outputs are executable effects (action invocations or property writes) [6].
This separation prevents command-like symbols from serving as state predicates
and supports sequential execution of multi-sentence goals.
3.4
Formula Generator (Gf)
Gf converts each atomic goal ami into a runtime-checkable specification. We rep-
resent generation as Gf(ami) ⇝ϕi, where ϕi is the resulting LTL-style formula
over symbolic propositions.
We use an LTL-style syntax because it provides a compact notation for im-
plications, conjunctions, and reactive intent, and because existing NL-to-LTL
tools can generate such specifications.

3.5
Grounding Mapper (Gm)
The generated formula ϕ contains symbolic proposition labels that must be
mapped to executable CPS affordances. Gm aligns these labels with MCP tools
and resources in two stages.
Stage 1: Role-Aware Proposition-to-Tool Mapping. Symbolic proposition labels
from ϕi are mapped to MCP affordances using LLM-based semantic match-
ing over the tools and resources first discovered from Bmcp. Although these
labels are formula atoms, they are usually generated from NL phrases (e.g.,
lamp_is_on), so Gm uses both their lexical meaning and their formula role.
Precondition propositions are grounded to observable affordances such as prop-
erty reads, sensor tools, or event resources; action propositions are grounded to
executable action invocations or property writes.
For a proposition p and role r ∈{precondition, action}, the atomic grounding
map returns a subset of available MCP affordances Γi(p, r) ⊆Tt ∪Rt, where p ∈
Prop(ϕi). In most cases, this subset contains a single affordance; for composite
propositions such as “all ZigBee lamps,” it may contain several actuator tools.
Stage 2: Numeric Enrichment. For propositions containing numeric compar-
isons (e.g., “temperature exceeds 26◦C”), Gm enriches tool IDs with comparison

3.6
Temporal Resolver (Tr)
The grounded specification ϕg is transformed into reactive precondition-action
rules evaluated over the current runtime state st:
Tr(ϕg) = {(pre1, act1), (pre2, act2), . . . , (prek, actk)}

sitional formula: (A →B) yields (A, B), and (A ↔B) yields (A, B) and (B, A).

Implementation and Design Choices
MCP Bridge. We use WoT-MCP5 as Bmcp, which translates TDs into MCP tools
and resources using two strategies: (i) Explicit, creating separate tools for prop-
erty access and actions while exposing events as resources, and (ii) Generic,
providing unified tools for discovery, property access, and invocation.
Specification Generation. We adopt nl2spec [2], which most reliably produced
parseable outputs in preliminary trials. It is exposed via an API for Gf. We
extend its prompt to enforce role-consistent propositions, mapping observable
conditions to state propositions and effects to action propositions, while keeping
few-shot examples domain-agnostic.
Grounding Mapper. Gm performs LLM-based mapping and validation, produc-
ing atomic mappings Γi(·) and applying Γ ∗
i to obtain grounded formulas. Action
propositions map to actuator commands (e.g., turnOn_lamp), while state propo-
sitions map to sensor resources (e.g., get_isOn_lamp). Numeric constraints (e.g.,
get_temperature > 26) are extracted using regex-based detection of thresholds
and comparison keywords.
Temporal Resolution and Precondition Extraction. Tr removes temporal opera-
tors (G, F, X, U) to obtain propositional formulas evaluated over the current
state st. For example, G(A →B) reduces to (A →B). Operators are dropped
rather than semantically encoded; the appendix tabulates the per-operator han-
dling and the constructs for which the prototype provides no temporal guarantee.
The resulting formulas are parsed using a Lark-based grammar into an AST, tra-
versed by an ImplicationExtractor to identify implication and biconditional
patterns.
Guardrail Verifier. Vg uses the Z3 SMT solver6 for constraint checking. Tool
IDs are aliased to variables (v0, v1, . . . ) and typed as Bool or Real depending
on usage in numeric comparisons. Expressions are translated into Z3 calls via
a shunting-yard-inspired algorithm, e.g., A ∧B →C becomes Implies(And(A,
B), C).
Robustness to malformed LLM outputs. Only Gf, Gm, and argument synthe-
sis invoke an LLM; Bmcp and Dam are deterministic (schema transformation;
rule-based splitting, with a non-decomposable prompt passed through). Each
LLM stage has a deterministic check or a hard failure behind it. Gf output is

Experimental Setup
System configuration. We compare SafeOrchestrate against a VanillaOrches-
trate baseline that directly maps atomic goals to MCP tool calls, bypassing
runtime verification. To prevent runaway behavior under non-convergence, the
baseline is capped at three reactive tool-calling steps. SafeOrchestrate executes
the full pipeline after decomposition, including role-aware grounding, constraint
formulation, MCP invocation, and guardrail verification. For fairness, we disable
human-in-the-loop intervention and iterative refinement for SafeOrchestrate.

Model and execution settings. All components use GPT-4.1 except nl2spec,

Evaluation protocol. We reconstruct oracle action sequences from execution logs

5.2
Evaluation Metrics
We use two metrics that capture complementary aspects of orchestration quality.
Required-action accuracy. Following prior work [17], we measure whether all or-
acle actions are correctly executed at least once. This metric captures functional
correctness but is insensitive to ordering and extraneous calls.
MCP Execution Similarity (MCP-ES). To capture full trace fidelity, we pro-
pose MCP-ES as the normalized Levenshtein similarity between expected and
executed MCP call sequences E and A:
MCP-ES = 1 −Dedit(E, A)
max(|E|, |A|).
MCP-ES penalizes insertions, deletions, substitutions, and ordering errors.
Before computing distance, we remove read-only state queries (e.g., get_*) and
internal guardrail inspection calls that do not affect system state or execution
order. All state-changing actions (tool invocations and property writes) are re-
tained. The same filtering is applied to both SafeOrchestrate and VanillaOrches-
trate to ensure comparability. For composite instructions, oracle actions are ex-
panded to all required actuations, while unintended additional actuations are
counted as insertions.

5.4
Discussion
Baseline failure modes. Purely LLM-driven orchestration is adequate for simple
tasks but unreliable under event-driven control, ordered execution, and multi-
device coordination—exactly where explicit grounding and runtime checking
help most. The taxonomy (Table 3) highlights systematic VanillaOrchestrate
13

============================================================
=== PAGE 14 ===
============================================================

weaknesses: missing precondition checks, premature termination, invalid argu-
ments, state-query/action confusion (turnOnAC vs. getIsOnAC), and—in event-
triggered settings like Coming/Leaving Home—trigger indiscipline, where ac-
tions fire regardless of the active event. Role-aware grounding and guardrail
filtering mitigate these. SafeOrchestrate reaches full required-action accuracy
without iteration on these tasks, consistent with structured grounding plus run-
time guardrails helping beyond prompt-level planning alone.
Scope of the safety claims. We scope the safety interpretation of these results
accordingly. In our evaluation, the deployment-constraint set C is empty, so
guardrail enforcement primarily ensures precondition satisfaction and trigger
discipline rather than explicit safety policies. Phase 2 can resolve cross-rule con-
flicts at runtime, but the reported evaluation does not exercise any—the behav-
ior is shown only in the worked example (Section 3.9)—and Phase 2 is in any
case bypassed for rules whose consequent bundles multiple actions (e.g., Com-
ing/Leaving Home), which are admitted on the satisfied precondition alone. En-
forcement is also entirely pre-execution: the orchestrator does not inspect action
results, re-check state after acting, or recover from actuation faults, so hazards
arising during or after physical execution are outside the current design. This
reflects a runtime verification model rather than full offline assurance.
Limitations of the metrics. Required-action accuracy is insensitive to traces;
MCP-ES captures trajectory fidelity but penalizes benign non-oracle behavior
(e.g., extra device deactivation in leaving-home). We read MCP-ES as a trace-
conformance metric, not a semantic-correctness measure: a system can score high
on accuracy yet still emit extraneous actions.
5.5
Threats to Validity
Internal Validity. Stochastic execution and the lack of component-wise ablation
threaten internal validity: ten repetitions per task do not guarantee exhaustive
coverage of stochastic execution paths.
External Validity. The evaluation suite covers condition-action rules, event-
triggered actions, ordered event reactions, and multi-device coordination. It ex-
cludes long-running cyclic workflows and dynamic branching where later actions
depend on intermediate execution outputs [6]. Broader evaluation in robotics
and industrial CPS domains is therefore needed. An empirical head-to-head
with LLM-MaGe or IoT Whisperer is a comparability limitation, not just fu-
ture work: they emit different artifacts (PDDL plans, Node-RED flows) with
no shared execution-trace metric, and LLM-MaGe further requires enriched TD
annotations absent from our tasks; Sections 2 and 5.4 give the conceptual dif-
ferences. We therefore restrict our empirical claims to the VanillaOrchestrate
baseline and treat LLM-MaGe and IoT Whisperer as conceptual comparisons
only. Broader model coverage beyond GPT-4.1 and additional baselines are fur-
ther gated by the current manual reconstruction of oracle traces and MCP-ES

============================================================

scores, which the automated trajectory scoring planned in Section 6 would re-
lieve. Finally, the evaluation focuses on required-action accuracy and MCP-ES,
leaving latency, runtime efficiency, and scalability unevaluated.
Construct Validity: Semantic Grounding. SafeOrchestrate relies on semantic
alignment between NL inputs, generated proposition labels, TD affordances,
and MCP tool names. MCP gives a uniform execution interface but enforces
no shared semantic model across these, so ambiguity or inconsistency can cause
grounding errors. Role-aware grounding, parser-based normalization, and run-
time guardrails mitigate this; mission-critical deployments would still need hu-
man review, stronger domain models, or deployment-specific validation.
Construct Validity: Runtime Checking, Concurrency, and Interleavings. Vg per-
forms reactive per-action constraint checking in the current state, not temporal
model checking over traces—low-latency decisions without long-horizon guar-
antees, between online trace monitors (e.g., RV-Monitor [11]) and offline model
checking (e.g., TLA+ [9]). It also does not reason about concurrent interleavings:
within an atomic goal, all precondition-action pairs are checked against one state
snapshot (plus a one-step hypothetical for the action under test), not re-sampled
per pair or searched over execution orders, so an action inadmissible under that
snapshot is not retried in the pass. Ordering is handled by decomposition—Dam
emits single condition-action units run as a sequence of atomic goals that each
re-sample state—and a subsequent external invocation (next event, next poll)
re-checks a blocked action against a fresh snapshot, so a rejection is not per-
manent. Goals with runtime data dependencies between pairs, external state
mutation mid-evaluation, and preemption of an ongoing sequence [6] are out of
scope. Re-sampling state before each pair would remove the within-goal case and
is a small, self-contained refinement; it, and integrating per-action checks with
trace-level and offline verification, are future work.
Construct Validity: Temporal Specification Limitations. For timed tasks, the
NL-to-specification stage may emit unsupported or partially formed temporal
expressions (bounded eventualities, incomplete until). Duration-based require-
ments are then handled only when expressible as parameters of executable af-
fordances, not when they require trace-level temporal reasoning.
6
Conclusion and Future Work
This paper presents SafeOrchestrate, a runtime-checked framework for LLM-
driven CPS control that combines MCP-based tool execution with guardrails.
The results show improved reliability over purely LLM-driven orchestration, es-
pecially on event-triggered, ordered, and multi-device tasks. The evaluation exer-
cises precondition satisfaction and trigger discipline; because its tasks are largely
single-rule with an empty constraint set C, the SMT layer’s cross-rule and safety-
constraint enforcement is shown only on the worked example (Section 3.9) and
remains to be assessed at scale.

Future work will make generated orchestrations reusable through structured
workflow representations, such as SDs [6] or graph-based models, building on
prior work on IoT workflow serialization [22] and potentially grammar-based
generation [13]. We also aim to decouple the orchestration logic from the MCP-
specific backend by supporting direct TD consumption, where actions, prop-
erties, and events are discovered from TDs and invoked through their native
protocol bindings. Finally, we plan component-wise ablation to isolate the con-
tribution of role-aware grounding versus guardrail checking, and automated tra-
jectory scoring to replace manual log inspection. We also plan to evaluate safety-
constraint enforcement and multi-rule conflicts across deployments at scale.
Broader evaluation across long-horizon, concurrent, and cyclic CPS scenarios,
additional LLMs and small language models, and larger deployments remains
necessary to assess generality and scalability.
