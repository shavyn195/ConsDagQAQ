Abstract
For repository-grounded coding agents, a functionally correct patch is not necessarily an acceptable one:
developers also constrain how the task must be carried out—modification scope, workflow order, validation,
tool use, and reporting. This capability, which we call engineering constraint following, remains largely
invisible to current evaluations. We introduce ANCHOR (Assessing Naturalistic Constraint Hierarchies
and Ordering in Repository-Grounded Agentic Coding), a benchmark built on naturalistic, multilingual
repository tasks spanning eight language groups. ANCHOR combines (i) a hierarchical taxonomy of
10 categories and 78 leaf types distilled from real developer interactions, (ii) an automated pipeline that
instantiates task-grounded atomic constraints and composes them into typed AND/THEN/PRIORITY relations,
and (iii) a trajectory-grounded evaluation framework that checks both the code diff and the execution
trajectory with rule-based and LLM judges. Across 19 agent configurations spanning 2 scaffolds and 10
foundation models on 358 tasks, the strongest measured system, Claude Opus 4.8 under Cline, reaches
70.1% atomic compliance and 63.7% relation compliance, while 19.0% of tasks pass every scored checklist
item under the strict all-item FCCR criterion. A five-engineer audit of constraints from 50 instances
reports 94% feasibility, 94% repository consistency, and 96% realism. In the primary paired set (14
configurations), the mean signed change in task completion after adding constraints is +0.7 percentage
points; individual changes vary in both directions. These results distinguish functional success from
constraint compliance, with failures concentrated in workflow ordering, tool-use discipline, and reporting,
and substantial interactions between models and scaffolds.

Introduction
Software engineering tasks are rarely unconstrained objectives. Developers ask agents not only to fix the bug, but also
to preserve APIs, reproduce before patching, run specific tests, avoid prohibited tools, and report what was actually
executed. For coding agents, success is therefore not merely to solve the task, but to solve it under explicit engineering
constraints.
We argue that this is not simply generic instruction following with code context. In repository-grounded agentic
coding, many requirements are trajectory-grounded: they constrain tool use, workflow order, validation, and reporting

and composes them into structured AND/THEN/PRIORITY relations, and a trajectory-grounded evaluation framework
with rule-based and LLM judges. Across 19 constrained configurations, including a full-benchmark Claude Opus
4.8 evaluation under Cline, the highest strict all-item FCCR is 19.0%. The primary paired set (14 configurations)
shows a mean signed completion change of +0.7 percentage points after adding constraints, with gains and losses
across systems. This calibration does not establish joint satisfiability or equal task difficulty; the direct evidence is
that functional completion and checklist compliance differ within each evaluated configuration. Our contributions are
to define engineering constraint following, operationalize it in a benchmark, and characterize the resulting failures,
supported by human audits of both generated constraints and judge decisions.

Related Work
Repository-grounded coding benchmarks such as SWE-bench, SWE-Compass, and SWE-Rebench V2 measure whether
an agent can resolve real software engineering tasks in real repositories, typically through final-patch correctness under
an executable test harness (Jimenez et al., 2024; Xu et al., 2025; Badertdinov et al., 2026; Zan et al., 2025; Deng
et al., 2025; Thai et al., 2026; Yu et al., 2026; Zhou et al., 2026; Li et al., 2024). These benchmarks have driven rapid
progress in coding agents, but they primarily measure task completion. They therefore provide limited visibility into
whether an agent respected task-specific engineering requirements on scope, workflow, validation, or reporting during
execution. Complementary evaluations assess repository-level completion (Yang et al., 2024; Liu et al., 2025b), visual
and interactive artifact quality (Lei et al., 2026; Zhang et al., 2025b), and code critique (Zhang et al., 2025a). Trajectory
diagnosis and process feedback further expose intermediate agent failures (Li et al., 2026; Xu et al., 2026).
Constraint-aware instruction-following benchmarks establish the importance of explicitly verifiable requirements, both
in natural language and in code generation (Zhou et al., 2023; Jiang et al., 2024; Pyatkin et al., 2025; Wu et al., 2025;
Wen et al., 2024; Chen et al., 2024; Qin et al., 2024; Zhang et al., 2025e; Zhuo et al., 2025; Yan et al., 2025; Gunnu
et al., 2025). However, they mostly evaluate single-turn settings, final artifacts, or flat constraint sets. Recent work such
as Inverse IFEval further shows that even strong LLMs can fail to override entrenched training conventions in order to
follow explicit user instructions (Zhang et al., 2025c). ANCHOR instead targets repository-grounded agentic coding,
where many requirements are trajectory-level and many must be interpreted jointly through ordering or priority relations.
The closest concurrent work is OctoBench (Ding et al., 2026), which studies scaffold-aware instruction following
in repository-grounded coding. We view the two benchmarks as complementary rather than competing. OctoBench
targets scaffold- and platform-level policies, whereas ANCHOR targets task-level engineering constraints specified
by the developer instruction itself. ANCHOR further contributes an explicit engineering constraint taxonomy and
structured composite relations, enabling direct evaluation of hierarchy, ordering, and precedence. Table 1 summarises
this positioning against prior instruction-following and coding benchmarks.

ANCHOR Construction Pipeline
ANCHOR draws repository-level coding environments from the multilingual benchmark SWE-Compass (Xu et al.,
2025), which is built from real GitHub issues and provides gold-standard patches with executable test environments
across Python, Go, Java, TypeScript, Rust, C, C++, and C#. We retain instances that satisfy four properties: (i) a usable
execution environment, enabling trajectory-grounded evaluation in a unified sandbox; (ii) sufficient task and repository
context to support downstream constraint selection; (iii) moderate patch complexity, excluding both trivial micro-edits
and long-horizon changes that are difficult to evaluate consistently; and (iv) broad coverage across programming
languages and repository types. The purpose of this filtering is not to favour easier tasks, but to ensure that each
retained instance can support realistic, task-grounded, and verifiable engineering constraints. Figure 4 summarizes how
ANCHOR converts a raw repository task into both a natural developer instruction and a structured constraint object that
can be evaluated after agent execution, through five explicit steps.

Step 1: Context collection and compression.
For each retained task, we gather the repository identifier, target language,
original problem statement, gold patch, and repository-level documentation from DeepWiki (Cognition AI, 2025). Raw
documentation is often too long and noisy to include directly in downstream prompts, so we compress it into a compact
project-context card that preserves repository purpose, technology stack, directory structure, engineering conventions,
testing practices, and version information, while discarding diagrams, verbose API documentation, illustrative code
examples, and marketing language. This is a targeted information-distillation step rather than mere length reduction:
the card supplies repository-level evidence for later decisions, such as whether linting, testing, or dependency-policy
constraints are meaningful for a given project.
Step 2: Leaf-category selection.
Given the 78 leaf categories, this stage retrieves a high-recall subset of potentially
relevant leaves for the task, based on three complementary evidence sources: task-type evidence (e.g., testing and
interface-compatibility constraints are natural in bug-fixing tasks), repository-context evidence (e.g., explicit formatter,
linter, or type-checking conventions make the corresponding categories meaningful), and modification-scope evidence
(e.g., tasks touching public interfaces, filesystem logic, or security-sensitive code raise different constraint families).
The selector deliberately avoids categories that are only theoretically applicable to almost any coding task, since these
tend to yield generic and weakly discriminative constraints later on.
Step 3: Atomic constraint instantiation and filtering.
Each selected leaf is instantiated into zero or more atomic
constraints—concrete, task-specific constraint statements grounded in the actual files, tools, and technologies involved.
The selection and instantiation prompts receive the gold patch as context, including affected modules and plausible
implementation concerns. They explicitly prohibit copying its exact file/line counts or restating its implementation as
a constraint; an engineering requirement should admit valid implementations beyond the reference patch. Because
instantiation and composition share a prompt, the patch is also visible at composition time. These safeguards reduce,
but do not rule out, indirect solution leakage. Every retained constraint must be naturalistic (plausibly stated by a
senior engineer assigning the task), non-blocking (constraining how the task is done without making it infeasible),
specific and verifiable (admitting an objective pass/fail judgement), task-grounded (referencing concrete task details),
and independent in content from the gold solution: the generator may inspect the patch for task context, but the final
constraint should not encode patch-specific file/line counts or implementation details. The generator is instructed to

Step 4: Composite construction.
Real developer instructions are often not flat lists of independent requirements; they
specify joint satisfaction, required execution order, or precedence among competing requirements. ANCHOR captures
this structure by composing task-grounded atomics into connected composite graphs whose edges carry one of three
typed relations: AND requires joint satisfaction; THEN requires both satisfaction and correct temporal order—reaching the
right end state in the wrong order is scored as a failure; and PRIORITY places two constraints intentionally in tension, and
a PRIORITY edge passes if and only if the higher-priority source constraint is upheld, regardless of whether the lower-
priority target is sacrificed to it. This edge-level rule does not waive other requirements in a mixed-relation composite.
Edge types may be mixed within a single composite, so multi-step and prioritised workflows can be expressed in one
graph. Composites are introduced only when the underlying relations are semantically natural and task-meaningful, and
atomics that do not admit such structure remain standalone instruction items. Each atomic constraint participates in at
most one composite, and the connected-subgraph formulation keeps each composite interpretable as a single instruction
unit rather than an arbitrary bundle of clauses.
The non-blocking criterion is a construction safeguard for individual constraints, not a formal proof that all constraints
can be jointly satisfied. AND and THEN require compatible requirements; PRIORITY intentionally introduces a conflict
together with an explicit precedence rule. Assigning an atomic constraint to at most one composite limits graph overlap,
but does not eliminate semantic interactions between distinct composites. Small completion-rate changes likewise
cannot establish satisfiability, since an agent can solve the task while ignoring a constraint. We therefore complement
these safeguards with a separate human audit: five senior engineers independently assessed the atomic constraints in
50 instances for feasibility, repository consistency, and realism, with reported validity rates of 94%, 94%, and 96%,
respectively. Section 4.1 provides the rubric and agreement statistics; these results characterize sampled constraint
quality rather than certify every full constraint set.
Step 5: Query synthesis.
The final stage renders the structured representation as a natural developer instruction in
two parts: a short task description rewritten in the voice of a developer assigning work, followed by a constraint list
of separable instruction items. Independent atomics become individual items, while each composite is rendered as
a single natural-language item that preserves the relation semantics among its members. Synthesis must preserve
specificity: exact file paths, command names, flags, module references, and behavioural conditions from the instantiated
constraints remain intact. It must also neither introduce new constraints nor leak gold-solution details—the query
expresses requirements, not answers.
This five-stage design preserves the natural surface form of developer instructions while grounding evaluation in an
explicit, machine-checkable representation of what the agent was required to do and in what relational structure. Detailed
filtering criteria, design rationales, prompt templates, and stage-specific schemas are provided in Appendix B and
Appendix C.1–C.4. Section 5 then operationalizes this structured representation into executable checklist items for code-
and trajectory-grounded evaluation.
4.1
Human Audit of Generated Constraints
This audit examines the generated requirements themselves, separately from the 480-item judge–human study in
Section 5.1. We sampled 50 benchmark instances. All five engineers independently labelled every atomic constraint in
these instances on three binary dimensions, without seeing one another’s labels. They were the same senior engineers
used in the judge study, with 6–12 years of experience: two Python/Go backend engineers, one infrastructure engineer
with Java/Bash and CI/CD expertise, one TypeScript/Rust full-stack engineer, and one research engineer with broad
open-source code-review experience.
The rubric was as follows. Feasibility: PASS if the requirement can be met in the given repository and task without
preventing completion; FAIL for an unsatisfiable or task-blocking requirement, such as restricting edits to a directory
that excludes the relevant files. Repository consistency: PASS if referenced paths, symbols, tools, dependencies, and
conventions agree with the repository; FAIL for hallucinated referents or an inapplicable toolchain. Realism: PASS if a
senior engineer could plausibly impose the requirement here; FAIL if it is artificial, trivially satisfied, or merely restates
the task or reference solution.

Evaluation Framework
Section 4 produces, for each task, a natural developer instruction paired with a structured constraint representation. We
now describe how that representation is operationalized into executable checks over the agent’s code diff and trajectory.
Figure 5 summarizes this process.
Checklist generation.
For each task instance, we generate a checklist: a structured set of evaluation items generated
from the constraint representation and checked against the final developer instruction, which is authoritative if the
two differ. This intermediate checklist layer is necessary because the construction-time representation is convenient
for instantiation and composition, but evaluation requires item-level pass conditions, judge assignments, and explicit
evidence targets. Only constraints preserved in the final instruction are retained. Verified atomic constraints yield atomic
items one-to-one, including atomics that participate in composites; each composite constraint additionally yields a
relation item that references its member atomic items as dependent checks and evaluates the higher-order property—joint
satisfaction, temporal ordering, or priority handling—on top of them. Each item contains a natural-language question, a
pass condition, a judge type with its parameters, and an evidence type specifying whether the item should be checked
against the code diff, the execution trajectory (including the final response), or commit messages. This design supports
fine-grained diagnosis of individual violations as well as explicit evaluation of structured constraint compliance.
Hybrid judging.
When the pass condition is reducible to symbolic checks, ANCHOR uses rule-based judges over
explicit evidence sources; Table 4 summarizes the rule templates. A single item may bind several rule checks
that must jointly hold—for example, verifying that one module’s import is absent while its replacement’s import is
present. Otherwise—especially for semantically complex atomic items and relation items involving THEN or PRIORITY—
ANCHOR uses an LLM judge, which receives the checklist question, the pass condition, and a task-relevant evidence
excerpt, and returns a binary PASS/FAIL decision with a brief justification. Evidence excerpts are used instead of
full raw trajectories whenever possible to reduce noise and context length. This hybrid split matters because many
engineering constraints are only partially observable from the final patch: scope, file-budget, and import restrictions are
often reducible to symbolic checks, whereas workflow order, reporting fidelity, and relations such as THEN or PRIORITY
require reasoning over temporally ordered evidence extracted from the trajectory. Prompt templates are provided in
Appendix C.5 and Appendix C.6.

Interpreting strict compliance.
FCCR answers whether every scored checklist item passes; it is neither a severity-
weighted risk score nor the rate of jointly successful and compliant task completions. A missed report item and an
API-breaking change both make FCCR zero for a task, although their engineering impact differs. ACR, CCR, and IPR
retain partial-compliance information, and task completion must be reported alongside them. FCCR also depends on
checklist length and the dependence between items, so a lower value on longer checklists alone does not establish a
coordination deficit.

6
Experiments
After summarizing the evaluation setup, we report three layers of findings. First, ANCHOR exposes a large and
systematic gap between task completion and engineering constraint compliance. Second, this gap is structured rather
than uniform: it concentrates in trajectory-grounded categories and in composite constraints that require temporal or
relational coordination. Third, trajectory-based error attribution most often labels failures as missed or deprioritized
constraints. These labels provide descriptive hypotheses about behavior, rather than a causal separation of model
capability and scaffold effects.
6.1
Experimental Setup
ANCHOR contains 358 tasks from 23 repositories spanning eight language groups (counting C and C++ together),
with 2,836 atomic constraints and 600 relation items across ten top-level categories and 78 leaves. We distinguish
three evaluation sets. The primary paired set contains seven foundation models evaluated under both OpenCode and
Cline, yielding 14 configurations: DeepSeek-V3.2(Liu et al., 2025a), GLM-5(Zeng et al., 2026), GLM-5.1(Z.AI, 2026),
GPT-5.3-Codex(OpenAI, 2026a), GPT-5.4(OpenAI, 2026b), Kimi-K2.5(Team et al., 2026), and Qwen-3.5-Plus. The
extended paired set also includes GPT-5.4-Mini and Qwen-3.5-Flash under both scaffolds, yielding 18 configurations.
The full evaluation set includes these 18 configurations and Claude Opus 4.8 under Cline, for 19 configurations spanning
ten models. All configurations use the same 358 tasks. Table 5 and the system-level scatter cover the full evaluation set;
diagnostic figures specify the corresponding paired set in their captions.
Each run starts from a clean repository checkout inside an isolated Docker sandbox. Agents may inspect files, execute
commands, and edit the repository through their scaffold interfaces; network access is restricted to dependency resolution
required by the original environment. Task completion is evaluated with the original repository test harness under a
fixed 30-minute timeout, and we record the full interaction trace for constraint evaluation. We report task completion
together with the four ANCHOR metrics from Section 5: ACR, CCR, IPR, and FCCR. Table 5 reports point estimates;
the category plot reports task-bootstrap 95% confidence intervals. These intervals address variation across sampled
tasks, not stochastic variation across repeated agent runs. To separate constraint following from raw task solvability,
we additionally evaluate a task-only setting in which the same agent receives the repository task objective without the
ANCHOR engineering constraints. Benchmark statistics are summarized in Figure 6.

6.2
Main Results: The Constraint–Completion Gap
Table 5 summarizes task completion and constraint compliance for all evaluated agent configurations. The main result is
a consistent gap between producing a functionally correct patch and following the engineering constraints that govern
how the patch should be produced.
Claude Opus 4.8 under Cline achieves the highest reported compliance scores: 70.1% ACR, 63.7% CCR, 69.0% IPR,
and 19.0% FCCR, with 43.6% constrained task completion. Its literal all-item FCCR is 7.0 percentage points higher
than GPT-5.4 under Cline (12.0%). Nevertheless, 81.0% of tasks still fail at least one checklist item. Completion and
FCCR are different marginal rates, not a measured joint success rate; their 24.6-point difference lower-bounds the share
of tasks that are completed without passing the entire checklist. The strict interpretation of FCCR, including overridden
lower-priority atomics, is specified in Section 5.2.
The task-only comparison is a calibration check. Across the primary paired set, the mean signed completion change
is +0.7 percentage points, while the mean absolute change is 1.9 points; individual changes range from −4.1 to +4.5
points. For Claude Opus 4.8, completion falls from 45.3% to 43.6%, a −1.7-point change. Across all 19 rows with
task-only values in Table 5, the mean signed change is approximately +0.1 percentage points. These differences do not
establish equivalence of task difficulty or joint satisfiability of constraints.
The compliance gap also persists under the same foundation model across scaffolds. OpenCode+GPT-5.3-Codex and
Cline+GPT-5.3-Codex differ by only 0.3 points in constrained completion (37.4% versus 37.7%), but by 5.0 points in
IPR (67.9% versus 62.9%) and 3.1 points in FCCR (12.3% versus 9.2%). Thus similar functional performance can
coexist with materially different compliance profiles.
The metric ordering is itself diagnostic. Agents satisfy isolated atomic items substantially more often than relation items,
with ACR exceeding CCR by 6.7 percentage points on average across the 19 configurations. FCCR is much lower
than both because it is a strict task-level metric: a single missed checklist item causes full compliance to fail. The four
metrics therefore distinguish average item satisfaction from passing every scored item jointly, subject to the severity and
priority limitations discussed in Section 5.2.

Compliance and Task Completion Are Distinct

Error Analysis
To understand where constraint failures come from, we analyze the attributed error labels produced by our failure-
analysis pipeline over the primary paired set. This yields 20,726 attributed failures in total: 16,700 from atomic checklist
items and 4,026 from composite relation items. We group them into six attributed behavioral patterns: E1 Not Perceived,
E2 Misunderstood, E3 Deprioritized, E4 Capability Limitation, E5 Scaffold Interference, and E6 Partial Compliance.
The attribution prompt used in this step is provided in Appendix C.7.
Figure 13 summarizes the attributed behavioral patterns. E1 Not Perceived accounts for 38.2% of failures, E3 Depriori-
tized for 21.9%, and E6 Partial Compliance for 14.5%; together they account for 74.6%, while E4 Capability Limitation
accounts for 5.2%. These are post-hoc labels inferred from constraint text and judge reasoning, not direct observations
of the model’s internal state or experimentally identified causes.
E5 Scaffold Interference accounts for 6.9% of attributed failures and covers recognizable interference such as context
truncation, conflicting system instructions, and tool/API limitations. This share does not bound the scaffold’s total effect:
different prompts, tools, and workflows can change whether a model notices or prioritizes a constraint, yielding behavior
labelled E1 or E3. Thus a small E5 share is compatible with the large scaffold–model interactions in Section 6.4. The
attribution data alone do not quantify those indirect pathways.
THEN failures skew toward E1/E6, whereas AND and PRIORITY failures more often receive E3. These patterns motivate
better workflow tracking, persistent constraint-state maintenance, and precedence reasoning as directions to test,
alongside improvements in coding capability and scaffold design.

Discussion and Limitations
7.1
Why Task Completion Is Not Deployment Readiness
Task completion is a necessary signal of coding ability, but it is not yet a sufficient signal of deployment readiness. In
real software engineering, the acceptability of a patch depends not only on whether it resolves the underlying issue, but
also on whether it respects the engineering constraints under which the task was assigned. Consider modification scope:
an agent may fix a bug in parser.py, yet also refactor adjacent modules despite an instruction to keep changes local.
The issue is resolved, but the patch becomes harder to review, riskier to backport, and less likely to be merged. Likewise,
an agent may produce a functionally correct patch while violating interface constraints, for example by changing a
public API when explicitly asked to preserve backward compatibility. In both cases, the artifact may satisfy a functional
oracle while failing the practical acceptance criteria imposed by the developer.
Process constraints create a second class of non-deployment-ready success. An agent may arrive at a correct fix without
first reproducing the failure, without adding a regression test, or without reporting the commands it ran. Such a patch is

7.2
Limitations
Evaluation cost.
Running each agent to completion on each ANCHOR task, and evaluating its trajectory against
the checklist, incurs significant compute cost. This makes large-scale model sweeps, repeated judge calibration, and
continual benchmark refreshes substantially more expensive than final-patch-only evaluation.
LLM judge reliability.
Although hybrid judging broadens coverage, LLM-based evaluation may still share systematic
biases with the evaluated models, particularly for models from the same vendor family as the judge. Future work
should investigate cross-vendor judge configurations and stronger human-audited judge calibration protocols. The
human alignment and subset-consistency checks do not substitute for controlled judge-provider or prompt swaps.
Error-attribution labels also rely on LLM interpretation and should not be read as causal measurements.
Generated-constraint validity and reference-patch exposure.
The five-engineer audit covers 50 instances rather than
the full benchmark, and evaluates atomics rather than complete interacting constraint sets. The audit reports high raw

agreement and Gwet’s AC1. Prompt instructions against copying the reference solution do not exclude indirect leakage,
since both selection and instantiation/composition receive the gold patch. A patch-blind construction ablation and a
full-set consistency audit remain open validation steps.
Strict metrics, coverage, and uncertainty.
FCCR is sensitive to any failed item, irrespective of severity, and to checklist
size. Under the literal definition, it also penalizes a failed lower-priority atomic even when the priority relation passes.
An applicability-aware variant needs explicit handling of overridden obligations and new scoring. Category imbalance
gives common constraints more weight in pooled metrics; the small environment, dependency, and security slices do not
support definitive category rankings. Category-specific IPR/FCCR would also require an attribution rule for relations
spanning multiple categories. Paired scaffold differences are descriptive comparisons without significance tests or
repeated-run uncertainty estimates.
Metric aggregation.
ACR, CCR, and IPR pool scored checklist items, so tasks and categories with more items
receive proportionally greater weight. FCCR and category-level Macro ACR expose complementary task-level and
category-level behavior. Applications may prefer other weighting schemes when particular engineering requirements
carry greater practical importance.
Scaffold scope.
We evaluate two open-source scaffolds. Their prompts, tools, and workflows can interact strongly with
a given model, as the paired comparisons show. Claude Opus 4.8 is evaluated under Cline only, and the results cannot
establish performance under untested scaffolds. The 6.9% E5 attribution share measures labelled interference, not the
scaffold’s total causal contribution.
Taxonomy coverage.
Our taxonomy was derived from grounded analysis of real developer interactions with coding
agents and the engineering requirements expressed in those tasks. Despite our best efforts at coverage, niche engineering
domains (e.g., embedded systems or hardware description languages) may still contain constraint types not captured in
the current 78 leaf categories.
Constraint interaction effects.
In ANCHOR, each composite constraint is treated as an independent subgraph. In
principle, constraints from different composites could interact—a PRIORITY relationship between atomics in different
composites is not currently modelled. Disjoint graph membership does not imply semantic independence, and the
current prompt-based non-blocking checks do not prove joint satisfiability. This is a known simplification.
7.3
Benchmark Maintenance and Community Plan
To ensure ANCHOR remains useful as models improve, we plan to maintain versioned benchmark releases, contami-
nation monitoring, and a documented expansion protocol for adding new task instances under explicit quality-control
requirements. Published results should always cite the version used so that future comparisons remain interpretable as
the benchmark evolves.
8
Conclusion
We presented ANCHOR, a benchmark that reframes evaluation in agentic coding from task completion alone to
task completion under explicit engineering constraints. By modelling task-level requirements as structured, often
trajectory-grounded constraints and evaluating them at multiple granularities, ANCHOR makes engineering constraint
following measurable in repository-grounded coding tasks. Across 19 configurations spanning two scaffolds and ten
models, the strongest measured system passes every scored checklist item on 19.0% of tasks, with 43.6% constrained
task completion. Human audits provide evidence about sampled constraint validity and judge agreement, while leaving
uncertainty about full-set consistency and difficult relational judgments. Compliance also depends substantially on
scaffold–model interactions. ANCHOR therefore supports evaluating task completion alongside atomic, relational, and
strict checklist compliance, with explicit attention to priority semantics, category coverage, and evaluation uncertainty.

Additional Methodological Details
B.1
Taxonomy Design Principles
The ANCHOR taxonomy was not designed purely from an a priori schema. Instead, we started from grounded open-label
annotation over real developer interactions with coding agents, including task instructions, inline review comments,
and post-hoc feedback on agent trajectories. Senior software engineers then iteratively clustered near-duplicate labels,
resolved boundary cases, and stress-tested the emerging hierarchy against held-out trajectories. The goal of this
refinement process was not merely descriptive coverage, but an operational taxonomy that could support scalable
instantiation, evaluation, and error analysis.
Five design principles guided this process. First, coverage: the taxonomy should cover the major engineering constraint
types that appear in practice, so that real developer instructions map into it with minimal residue. Second, semantic
exclusivity: leaf categories should be as disjoint as possible, reducing ambiguity during annotation and automatic
mapping. Third, operationalisability: each leaf should admit concrete, testable instantiations with stable pass conditions

ANCHOR.
The current release instantiates this design as a three-level hierarchy with 10 top-level categories, 34 mid-level sub-

behaviour: process- and trajectory-level constraints (C1–C2), patch- and implementation-level constraints (C3–C5),
environment and system-boundary constraints (C6–C8), and validation and reporting requirements (C9–C10). Leaf
categories are the smallest operational unit: each is intended to capture a semantically coherent developer requirement
that can be instantiated into task-grounded constraints and evaluated with relatively stable verification logic.
B.2
Environment Curation and Context Compression
The construction pipeline begins by selecting repository tasks that can support realistic and verifiable engineering
constraints. The filtering objective is not to privilege easier tasks, but to ensure that each retained instance admits
trajectory-grounded evaluation. In practice, we prioritise instances with (i) a usable execution environment, (ii) sufficient
task and repository context to support downstream constraint selection, (iii) moderate patch complexity rather than
trivial micro-edits or very long-horizon changes, and (iv) broad coverage across programming languages and repository
types.
For each retained instance, we collect the repository identifier, target language, original problem statement, gold patch,
and repository-level documentation from DeepWiki (Cognition AI, 2025). These artefacts provide complementary
signals for later stages: the problem statement and patch reveal the task objective and likely affected code regions, while
repository documentation provides project-level context such as architecture, tooling, testing practices, and engineering
conventions.
Raw repository documentation is often too long and noisy to include directly in downstream prompts. We therefore
compress it into a compact project-context card that preserves information useful for constraint construction, such as
repository purpose, technology stack, directory structure, testing practices, and version information, while discarding
low-value content such as diagrams, verbose API documentation, illustrative code examples, marketing language, and
redundant passages. This step is not merely length reduction: it is a targeted information-distillation stage that gives
later prompts repository-level evidence without overwhelming the context budget.
B.3
Subset Selection and Atomic Instantiation
Given the full taxonomy, the next challenge is deciding which leaf categories are relevant to a particular task. ANCHOR
treats this as a high-recall selection problem. The coarse selection stage receives the full taxonomy, the repository
identifier, programming language, problem statement, compressed repository context, and the gold patch. The prompt
permits the gold patch to inform task context and category selection, while explicitly forbidding requirements that copy
its exact counts or restate the reference solution. This is a prompt-level safeguard, not evidence that category selection is
independent of the patch.
Selection decisions are based on three complementary evidence sources. The first is task-type evidence: some categories
are more naturally associated with certain task types, such as testing or interface-compatibility constraints in bug-
fixing tasks. The second is repository-context evidence: formatter, linter, type-checking, or dependency-management
conventions make some categories more meaningful for a given project. The third is modification-scope evidence: tasks
touching public interfaces, filesystem logic, exception handling, or security-sensitive code naturally raise different
constraint families. At the same time, the selector avoids retaining categories that are only theoretically applicable to
almost any coding task, because these tend to yield generic and weakly discriminative constraints later on.
This stage is intentionally followed by an implicit precision filter during atomic instantiation. A selected category is
retained in the final benchmark instance only if it can yield one or more constraints that are naturalistic, non-blocking,
specific and verifiable, task-grounded, and independent of the reference implementation in content. Categories that
would only produce generic, overly restrictive, or weakly diagnostic constraints are dropped. In this sense, ANCHOR
uses a recall–precision cascade: coarse selection aims to avoid prematurely missing meaningful categories, while atomic
instantiation enforces quality control over what ultimately appears in the benchmark.

B.4
Composite Constraints and Query Synthesis
Real developer instructions are often not flat lists of independent requirements. They may specify joint satisfaction,
required execution order, or precedence among competing requirements. ANCHOR captures this structure by organising
selected subsets of atomic constraints into connected composite graphs. Edges carry one of three typed relations: AND
requires joint satisfaction, THEN requires both satisfaction and correct temporal order, and PRIORITY requires the source
constraint to take precedence over the target when the two are in tension.
Composite constraints are introduced only when the underlying relations are semantically natural and task-meaningful;
ANCHOR does not force unrelated constraints into a shared graph merely to increase structural complexity. Not all
atomic constraints must participate in composites, and standalone constraints remain as independent instruction items.
Edge types may be mixed within one composite, and each atomic constraint participates in at most one composite,
so composites partition the related atomics into disjoint, self-contained instruction units. This connected-subgraph
formulation keeps each composite interpretable as a single instruction unit rather than an arbitrary bundle of checklist
clauses.
The final query-synthesis stage converts the structured representation into a natural developer instruction suitable for
direct agent execution. Each query is written in two parts: a short task description rewritten in the voice of a developer
assigning work, and a constraint list composed of separable instruction items. Independent atomic constraints become
individual items, while each composite constraint is rendered as a single natural-language item that preserves the relation
semantics among its member atomics. A key requirement of this stage is specificity preservation: exact file paths,
command names, flags, module references, and behavioural conditions from the instantiated constraints must remain
intact. The synthesis step must also avoid introducing new constraints or leaking gold-solution details. Prompt templates
for these stages are provided in Appendix C.1–C.4.

## Error Categories (Rubrics)

### E1: Constraint Not Perceived
The agent did not notice or register the constraint at all. It shows no evidence of attempting to address this constraint in its
behavior.
- E1.1: Constraint buried in long context -- the constraint appeared in a less prominent position and was likely overlooked
- E1.2: Constraint expressed implicitly/indirectly -- the constraint was not stated as a direct instruction but implied
- E1.3: Context lost across turns -- the constraint was given earlier but forgotten in subsequent actions
### E2: Constraint Misunderstood
The agent noticed the constraint but interpreted it incorrectly. Its behavior shows an attempt to comply, but based on a wrong
understanding of what was required.
- E2.1: Scope misinterpretation -- misunderstood which files/modules/components the constraint applies to
- E2.2: Negation or conditional logic error -- misread "do not X" or "only if Y then X" type instructions
- E2.3: Technical term ambiguity -- interpreted a technical term or phrase differently from the intended meaning
### E3: Constraint Perceived but Deprioritized
The agent understood the constraint but chose to violate it in favor of another goal (e.g., making tests pass, simplifying code,
completing the task faster).
- E3.1: Functional correctness over constraint -- violated constraint to achieve a working solution
- E3.2: Efficiency/simplicity over constraint -- took a shortcut that conflicts with the constraint
- E3.3: Inter-constraint conflict -- two constraints conflicted and the agent sacrificed this one
### E4: Execution Capability Limitation
The agent understood the constraint and attempted to comply, but failed due to insufficient technical ability to carry out the
required action correctly.
- E4.1: Coding ability insufficient -- understood the requirement but produced incorrect implementation
- E4.2: Tool usage error -- attempted the right action but used tools/commands incorrectly
- E4.3: Multi-step execution gap -- planned correctly but missed steps during execution
### E5: Scaffold/Environment Interference
The constraint violation was caused or significantly contributed to by the scaffold framework, context management, or environment
limitations rather than the model’s own decision.
- E5.1: Context window truncation -- constraint was likely removed by the scaffold’s context management
- E5.2: System prompt override -- scaffold’s built-in instructions conflicted with the user constraint
- E5.3: Tool/API format limitation -- the scaffold’s tool interface made compliance difficult or impossible
### E6: Partial Compliance
The agent partially satisfied the constraint but not fully enough to pass the check.
- E6.1: Main logic compliant, edge case missed -- core behavior is correct but boundary cases violate
- E6.2: Direct compliance, indirect violation -- directly follows the rule but indirectly violates through side effects
- E6.3: Incomplete execution -- started to comply but did not finish for all required locations/cases
