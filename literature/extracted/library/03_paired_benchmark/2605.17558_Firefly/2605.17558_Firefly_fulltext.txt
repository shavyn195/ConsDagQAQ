Firefly: Illuminating Large-Scale Verified
Tool-Call Data Generation from Real APIs

Abstract
Training tool-calling agents requires large-scale trajectory data with verifiable la-
bels, yet existing approaches either synthesize environments that diverge from real
API behavior or generate tasks without ground-truth outcomes for verification. We
present FIREFLY, a pipeline for generating verified tool-call data from real-world
MCP servers. Our key insight is to invert the standard synthesis pipeline: rather
than generating tasks and hoping they are solvable, we first let a strong LLM ex-
plore real APIs along graph-guided DAG structures, then synthesize tasks back-
ward from observed outcomes, guaranteeing label correctness by construction. To
handle the scale of real-world tool spaces (∼1,000 tools), we build a pairwise
tool graph and sample sub-DAGs to focus exploration on semantically coherent
workflows. To address environment drift in live APIs, we construct a retrieval-
augmented simulator that caches all exploration results and replays them dur-
ing training and evaluation, enabling reproducible RL without live server access.
Applying this pipeline yields 5,144 verified tasks spanning 240 servers and 993
tools. A 4B-parameter model trained with GRPO on FIREFLY matches Claude
Sonnet 4.6 on our held-out test set and shows improvements on multiple tool-
calling benchmarks including Tau2-Bench, MCPMark, and MCP-Atlas. Code
is available at https://github.com/leoleoasd/firefly-neurips-2026/,
and data and model are available at http://firefly.hailab.io/.

Introduction
Tool-calling agents interact with external APIs to complete user intents, and they have become a
central paradigm for building AI systems that can act in real environments [19, 33, 2, 25]. However,
training such agents requires many tasks with correct intermediate tool calls and verifiable final
outcomes. Even data-efficient reinforcement learning recipes consume thousands of such tasks,
for example 2.4k training samples for a search agent [10], whereas recent agent benchmarks each
offer only tens to hundreds, such as 50 to 115 tasks per domain in Tau2-Bench [2], 127 tasks in
MCPMark [28], and 500 public tasks in MCP-Atlas [1]. Human annotation could close this gap,
but it is expensive, domain-specific, and difficult to scale to the long tail of real APIs [33, 14, 4, 6,
5]. Synthetic pipelines scale more easily, although each existing design gives up either realism or
verifiability. When they rely on purely simulated environments, an LLM invents tool responses that
often diverge from real API behavior [9]. When they instead generate a user task first and then ask
an LLM to produce a trajectory over real tools [21, 16, 31], the trajectory may be infeasible and the
final answer is often not tied to any observed state, so the task lacks a ground truth that could verify

offline, enabling stable RL training with binary rewards and improving tool-call ability.
correctness [31]. Moreover, even verified tasks over real tools are hard to train on, because live APIs
drift over time, become unavailable, and rate-limit the repeated calls of RL rollouts. As a result,
constructing training tasks that are scalable, realistic, and verifiable, together with an environment
that stays reproducible during RL, remains an open problem.
To address the verifiability problem, FIREFLY inverts the forward pipeline. Specifically, we first
explore real tools, record the states reached through actual execution, and only then synthesize tasks
backward from these observed outcomes. In this back-chaining process, every label is correct by
construction because it records a state that real tools actually returned. Concurrent work applies the
same trajectory-to-task idea in small or fixed tool spaces, where the set of possible tool chains can
be enumerated or manually constrained [25], so the open question is whether back-chaining works
at the scale of real-world MCP ecosystems.
Scaling back-chaining to real MCP servers introduces a challenge that small tool spaces avoid,
because the number of possible tool combinations grows quickly with the number of tools. In
our setting, hundreds of servers expose nearly one thousand tools across heterogeneous domains,
so naive exploration wastes most calls on semantically incoherent tool combinations. To make
exploration scalable, FIREFLY constructs a directed tool graph over all tools, where edges represent
pairwise input-output compatibility judged from tool schemas and descriptions. We then sample
sub-DAGs from this graph and let a strong LLM explore within these graph-guided neighborhoods.
The graph thus acts as a weak semantic prior that leaves the final task open while steering exploration
toward coherent multi-tool chains that are likely to produce useful, compositional trajectories.
A second challenge is the environment drift of live APIs, which makes real tools unstable training
environments. Many MCP tools depend on external data sources such as search indices, weather,
finance data, DNS records, package metadata, or live web services, so their outputs may change over
time, servers may become unavailable, and repeated calls during RL rollout may be rate-limited or
non-reproducible. FIREFLY addresses this drift by caching every tool call observed during explo-
ration, including the tool name, input parameters, and returned output. We then build a replay-based,
retrieval-augmented tool-call simulator that replaces live servers during training and evaluation. Un-
like purely simulated environments, this simulator grounds every response in real API outputs. For
exact matches it replays the cached response, and for near matches an LLM either returns the match-
ing cached response or generates one conditioned on the closest cached outputs, whereas for calls
that differ semantically from every cached call it returns an error. The error case is intentionally
conservative, because each ground-truth task was synthesized from a known trajectory, so calls far

Our contributions are threefold:
• We introduce FIREFLY, a large-scale verified tool-calling dataset grounded in real MCP
servers, together with a retrieval-augmented simulator that enables reproducible training
and evaluation without live servers3.
• We propose a scalable data-generation framework that combines graph-guided exploration
with back-chaining task synthesis, making it possible to construct verified trajectories
across hundreds of heterogeneous real-world API servers.
• We empirically show that RL training on FIREFLY substantially improves a 4B model on
in-distribution verified MCP tasks and transfers to out-of-distribution tool-calling bench-
marks such as Tau2-Bench [33, 2], MCP-Atlas, and MCPMark.

Related Work
2.1
Synthetic Data Generation
The paradigm of LLM training with synthetic data has evolved from general instruction tuning to
complex agentic tasks. Early works demonstrated the effectiveness of distilling strong models to
generate diverse instruction-following data, significantly improving the capabilities of smaller mod-
els [30, 23, 29]. Building on this success, recent research has pivoted towards synthesizing data
specifically for reasoning and planning, employing techniques such as Chain-of-Thought (CoT) ex-
pansion and process supervision to enhance model robustness [27, 15]. In the domain of tool-calling
agents, synthetic data is particularly critical due to the lack of high-quality, real-world API inter-
action logs. Pioneering works like ToolFormer [19] and ToolAlpaca [21] introduced self-instruct
mechanisms to generate API calls embedded within text. More recently, studies have focused on
scaling up these datasets to cover broader domains. For instance, APIGen-MT [16] and similar
frameworks [22, 17] utilize iterative verification processes to filter out invalid tool calls, aiming to
improve the executable rate of generated actions. Concurrently, datasets like Toucan [31] have at-
tempted to model complex tool dependencies by simulating multi-turn interactions. Despite these
advancements, existing synthetic frameworks face significant challenges regarding verifiability and
realism. Most prior approaches rely on ‘forward generation’, where the LLM is prompted to hallu-
cinate both the user query and the subsequent tool trajectory. This often leads to plausible-looking
but functionally incorrect calls, or ‘simulated’ environments that fail to reflect the stochasticity and
constraints of real-world servers. Furthermore, while execution-based filtering has been successfully
applied in code generation via unit tests [8, 12, 18], applying rigorous verification to general tool-
calling remains an open problem. Unlike coding tasks with deterministic outputs, tool interactions
often lack ground-truth states for verification. FIREFLY addresses these limitations by inverting
the synthesis process: instead of hallucinating queries, we employ a back-chaining strategy start-

2.2
Tool-Calling Benchmarks and Datasets
The transition of Large Language Models (LLMs) from static reasoning to interactive agentic be-
havior [26, 3, 13, 6, 24, 35, 5, 7] necessitates specialized benchmarks and datasets that accurately
reflect real-world tool-calling scenarios. Existing datasets for training and evaluating tool-calling
agents are primarily categorized into two approaches.
First, human-curated datasets are meticulously built by human annotators, exemplified by API-
Bank [11], which focuses on tool-calling planning, and the more recent Tau-Bench series [33, 2],
which aims for comprehensive coverage of diverse real-world APIs. While human annotation guar-
antees the semantic validity and naturalness of the user intent, this approach is inherently resource-
intensive, severely limiting scalability and making it difficult to maintain relevance across rapidly
evolving API schemas.
Second, automatically generated datasets have emerged to overcome these scale limitations, lever-
aging LLMs to synthesize tool-use instances. Early efforts, such as ToolAlpaca [21], focused on
generating tool-augmented instruction data, while advanced frameworks such as APIGen-MT [16]
and Toucan [31] use automated processes to synthesize tasks and expected trajectories. However,
these large-scale synthetic methods suffer from two critical shortcomings: the forward generation
paradigm leads to hallucinated tool calls and execution failures, requiring extensive filtering (as
discussed in Sec. 2.1); and many datasets are confined to simplified, simulated environments [16],
failing to capture the complexity, constraints, and dynamic states of real-world MCP servers.
In summary, existing tool-calling datasets present a trade-off where no single benchmark simultane-
ously achieves verifiability, realism, and scalability. FIREFLY closes this gap by grounding synthesis
in real-world MCP servers and inverting the generation order to guarantee correctness.
3
Method
Our pipeline constructs verifiable tool-use data in three phases: server collection (Sec. 3.1), task
synthesis (Sec. 3.2), and trajectory generation during evaluation and rollout (Sec. 3.3).
3.1
Server Collection
3.1.1
Scraping
We collect MCP servers from the Smithery registry4 using broad listing queries, prefix enumeration,
and domain-specific keyword searches. After deduplication and metadata fetching (tool definitions,
input schemas, connection configurations), we obtain approximately 3,000 unique servers, of which
roughly 900 expose at least one tool.
3.1.2
Filtering
Many scraped servers are unsuitable for verified data construction. We screen each server against
four criteria using an LLM evaluator: Statelessness (no session memory or cross-call state), No
user authentication (no OAuth, credentials, or user-owned keys), Schema clarity (explicit JSON
typing and parameter descriptions), and Non-triviality (no echo or diagnostic-only tools). A server
must meet all four. We spot-check a subset for alignment. 240 servers with 993 tools remain.
3.1.3
Tool Graph
The tool graph is the mechanism that makes multi-step tasks possible in FIREFLY. In an early
pilot without the graph, the exploring LLM sampled tools at random across the full tool space, so
successive calls were semantically unconnected and the output of one call was never usable as the
input of the next. As a result, essentially all tasks synthesized in that pilot collapsed to single-step
lookups. To obtain tool chains in which earlier outputs feed later inputs, we build a directed tool

graph G = (T , E) over all retained tools across all servers. Each node represents a tool and each
edge indicates that the source tool can be chained with the destination tool: the output of tool ti can
be transformed into or used as input to tool tj. Since schema-level type matching alone is too coarse
(e.g., two string fields may be semantically unrelated), we use an LLM to judge each candidate
pair based on tool descriptions and schemas, assigning a confidence level (high, medium, or low)
to each positive edge. The resulting graph contains approximately 83K directed edges (average
88 successors per tool), of which 64K are medium-or-higher confidence. The graph includes both
intra-server and cross-server edges.
3.2
Task Synthesis
3.2.1
DAG Exploration
With nearly 1,000 tools, undirected exploration would waste most calls on incoherent combinations.
We use the tool graph G to focus exploration on semantically valid workflows. For each exploration,
we select a starting tool with at least two high-confidence successors in G (enabling fan-out), then
let a strong LLM interactively build a tool-call DAG against the live server. At each round, the LLM
is offered a random subset of successors (from the union of all previously completed nodes in G,
filtered to medium-or-higher confidence). The LLM may call multiple tools in parallel (fan-out),
chain a single successor (sequential), or combine outputs from earlier nodes into one call (fan-in).
This process repeats until a specified tool-call budget is exhausted or no successors remain.
A completed exploration yields a DAG:
D = (V, ED),
V = {(tk, ak, rk)}m
k=1,
where each node records tool identity tk, input ak, and output rk, and each edge in ED indicates data
flow from parent to child. Because every node results from actual execution against a live server, all
states are guaranteed reachable. These DAGs provide raw material for task synthesis and are later
indexed by the retrieval-augmented simulator (Sec. 3.3).
3.2.2
Back-Chaining Task Synthesis
From each DAG D, the LLM selects a subset of nodes and constructs a natural-language task around
them. The task embeds the information needed to populate tool-call inputs (names, parameters,
constraints), while the ground-truth answer is extracted from the selected nodes’ outputs. Remaining
nodes serve as distractors or irrelevant exploration paths. Each generated task includes a structured
answer schema (a JSON template with named placeholders) and an answer template (a natural-
language sentence with the same placeholders). This structured format enables automated evaluation
via field-level comparison rather than free-form text matching.
This backward construction guarantees both reachability and label correctness. To maximize diver-
sity, we vary which subsets are selected and prompt the LLM to vary phrasing, yielding multiple
tasks of different complexity from a single DAG.
3.2.3
Task Validation
An LLM judge evaluates each task–trajectory pair on five criteria: Verifiability (answer is objec-
tively checkable), Well-specifiedness (exactly one correct answer), Interpretability (outputs are
human-readable, not opaque IDs), Realism (score ≥5 on a 0–10 scale), and Difficulty calibration
(stated difficulty matches trajectory complexity). Tasks failing any criterion are removed. This stage
filters out approximately half of candidates. Appendix D reports a human audit of this filtering.
3.3
Scalable and Verifiable Evaluation and Rollout
Real-world tools depend on external data sources that change over time (weather, stock prices,
search indices), and live servers may become unavailable or rate-limited. Directly using live MCP
servers for RL rollout or evaluation is therefore neither reproducible nor scalable. We construct a
retrieval-augmented tool-call simulator that replaces live servers entirely, so that both RL training
and evaluation run without live server access.

3.3.1
Retrieval-Augmented Tool-Call Simulator
The simulator indexes every tool call (tk, ak, rk) recorded during exploration and resolves each tool
call that the agent issues during RL rollout or evaluation in two stages. In the first stage, a rule-based
retriever looks up the call input in the cache. When the input is byte-identical to a cached input, the
retriever returns the cached output unchanged, and when the cache holds no similar call, the retriever
rejects the call with a tool error. Otherwise, the retriever passes the most similar cached calls to the
second stage, in which an LLM resolves the call against these retrieved examples. The LLM returns
a retrieved real output unchanged when it judges the agent’s call semantically identical to a cached
call, for example when the two calls differ only in the plural form of a search term. When the agent’s
call differs from a cached call only in a minor detail, such as requesting CSV where the cached call
requested JSON, the LLM generates a new response grounded in the retrieved outputs. When the
agent’s call differs semantically from every retrieved call, the LLM rejects it with a tool error.
Table 1 reports how often each outcome occurs during evaluation. We verified every delivered
response byte by byte against the cache of real API outputs and found that 78.9% of the responses
reaching the agent are byte-identical replays of real API outputs. Among the synthesized responses
with JSON-shaped output, 0.65% fail to parse (34 of 5,270). When none of the retrieved calls
applies, the simulator returns an explicit error instead of inventing a response, so uncertain calls
reach the agent as error signals and fabricated observations stay out of the rollout.
During retrieval, the cached calls from the current task’s ground-truth trajectory are ranked ahead
of other cached calls. The prioritization keeps the simulator consistent with the world state from
which each label was extracted, which matters since many tools are non-deterministic. Weather
and stock tools, for example, return different outputs for the same input over time, and some tools,
such as fortune-telling tools, return a random output on every call. Each ground-truth answer was
extracted from one specific observed response, so without the prioritization such tasks would no
longer be verifiable against their own labels. To check that the prioritization does not leak answers,
we used Claude Sonnet 4.5 to classify every evaluation tool call by its deviation from the cached
calls. In successful trajectories, 75.8% of calls exactly match the ground-truth calls, whereas in
failed trajectories, 66.8% of calls deviate majorly. If the prioritization leaked answers, calls with
major deviations would succeed spuriously, and the observed pattern shows the opposite.
The simulator design guarantees two properties. Reproducibility: tool responses are either replayed
from the cache or grounded in it, so they do not depend on the time of the call or on the state of live
servers. Verifiability: ground-truth labels were extracted from exploration outputs that are indexed
in the simulator, so the responses needed to derive each label are always available via exact match.
3.3.2
RL Rollout and Evaluation
During RL training, the agent interacts with the simulator rather than live servers. Given a task
description and tool schemas, the agent generates tool calls that are intercepted and resolved by
the simulator. The binary reward (correct/incorrect) is computed by first attempting exact field-
level match against the structured answer schema; if that fails, an LLM judge evaluates semantic
equivalence. The same simulator serves as the evaluation environment, ensuring that training and
evaluation use identical tool behavior. The simulator therefore enables unlimited rollouts at scale
without API costs or availability concerns. Since the policy collects fresh rollouts from the simulator
at every training step, the learning setting is online RL, and only the environment is cached. We
therefore refer to the training as simulator-based online RL.

4
Dataset Analysis
We apply the full pipeline to construct FIREFLY, a large-scale dataset of verifiable tool-calling
tasks grounded in real MCP servers. Starting from approximately 3,000 servers discovered on the
Smithery registry, the filtering stage retains 240 servers exposing 993 tools. Tool-chain exploration
produces 9,749 DAG trajectories, from which back-chaining synthesis generates 9,275 candidate
tasks. After LLM-based validation, 5,144 tasks pass all quality criteria. We hold out 200 tasks as a
fixed test set and use the remaining 4,944 for training. Each task is accompanied by its ground-truth
trajectory, answer schema, and the full set of tool-call responses needed for offline replay.
Example task.
As a concrete illustration, consider the following task from FIREFLY:
“Which domain was registered first, amazon.com or netflix.com, and how many
years apart were they registered?”
The ground-truth trajectory makes two calls to a whois lookup tool (from the networkcalc-mcp
server): one for amazon.com and one for netflix.com. The expected answer is:
{"first_registered_domain": "amazon.com",
"amazon_registration_year": "1994",
"netflix_registration_year": "1997",
"years_apart": "3"}
This task was synthesized by back-chaining from the two outputs observed during exploration, and
is verifiable because the simulator can replay the exact same responses at evaluation time.
Task characteristics.
Tasks span three difficulty levels: easy (19.5%), medium (77.0%), and
hard (3.5%). Ground-truth trajectories require on average 3.0 tool calls (range 1–10), with answer
schemas containing 4.6 fields on average, reflecting multi-faceted information needs rather than
single-value lookups. The test set alone covers 98 distinct servers and 221 distinct tools. Approx-
imately 38.5% of tasks require tools from multiple servers, exercising cross-server composition, a
capability absent from most existing benchmarks that confine tasks to a single API provider. The
average realism score assigned by the LLM judge is 7.8/10, indicating that the majority of tasks
reflect plausible real-world use cases rather than contrived synthetic scenarios.
The retrieval-augmented simulator indexes all tool calls from the exploration DAGs. During the
full training run, the retriever returns 42.2% of agent tool calls from the exact cache and passes the
remaining 57.8% to the LLM stage, and it rejects no call for lack of similar cached calls. The LLM
stage can still reject a call, and Table 1 reports the final outcomes during evaluation, including the
34.7% of calls that the LLM rejects. The absence of retriever rejections shows that the exploration
phase covers every tool that the agent calls during training, so trajectories can be collected without
live server access.
The entire dataset is generated using Claude Sonnet 4.5 via AWS Bedrock batch inference. The
full pipeline consumes approximately 23.5 billion tokens (21.4B input, 2.0B output) at a total cost
of approximately $47K. This one-time investment produces a reusable dataset and simulator that
enable unlimited simulator-based RL training without further API costs.
4.1
Comparison with Existing Datasets
Table 2 highlights the key differentiators of FIREFLY: it is the only dataset that simultaneously
provides multi-step trajectories, verifiable ground-truth labels, and grounding in real (not simulated)
API servers. Existing datasets either rely on simulated environments (APIGen-MT, Tau2-Bench),
lack verifiable supervision (Toucan), or are limited to single-turn interactions (ToolAlpaca).

5.1
Setup
Model.
We train Qwen3-4B [32], starting from Qwen3-4B-Thinking-2507.
Training.
We use GRPO [20] with dynamic filtering [34] on the 4,944 training tasks from FIRE-
FLY. During RL, the agent interacts with the retrieval-augmented simulator: at each step it selects
and calls tools, receives simulated responses, and produces a final answer. We use a binary reward:
we first attempt structured field-level exact matching against the answer schema; if that fails, an
LLM judge (Qwen3-30B-A3B-Thinking-2507) evaluates semantic equivalence. The same model
also serves as the LLM backend for the tool-call simulator. Appendix C shows that the training
curve and the RL gain are preserved when both roles are taken over by Qwen3-235B-A22B or by
Claude Sonnet 4.5.
We sample 8 rollouts per prompt with temperature 1.0 and apply dynamic filtering [34]. Prompts
where the model achieves reward 1.0 on all 8 rollouts are permanently removed from the training
set, as the model has already mastered them. To avoid premature exclusion early in training when
rewards may be noisy, we only begin removing mastered prompts once more than 10 accumulate
within a single rollout batch. Prompts where all rollouts fail are not excluded, as the model may
solve them after further training. This curriculum-like mechanism progressively focuses training on
the shrinking set of prompts the model finds challenging.
We train for 300 steps with a global batch size of 16 (≈5 epochs with filtering). Key hyperparameters
are provided in Appendix A. Training uses the Slime framework with 16 GPUs for the actor model
and 16 GPUs for the asynchronous rollout engine.
Evaluation.
We evaluate on four benchmark suites: FIREFLY test set (200 held-out tasks;
pass@k for k ∈{1, 4, 8, 16} over 16 independent rollouts per task), Tau2-Bench [33, 2] (Re-
tail, Airline, and Telecom), MCP-Atlas, and MCPMark (File System, Postgres Easy, and Postgres
Std). For the FIREFLY test set, we use the offline simulator with all DAG tools available and an
LLM judge for answer comparison; we also evaluate Claude Haiku 4.5, Sonnet 4.6, and Opus 4.7
under the same protocol as proprietary baselines.

Public Benchmarks
FIREFLY is constructed as a single-turn, multi-step tool-calling dataset: each task contains one user
message, but solving it requires the agent to plan and execute multiple tool calls before producing the
final answer. We evaluate whether supervision from this format transfers to public benchmarks that
differ substantially from FIREFLY in tool source and environment design. Specifically, MCPMark
and MCP-Atlas evaluate tool use on MCP servers outside FIREFLY, whereas Tau2-Bench evaluates
multi-turn user-agent interactions.
As shown in Table 4, FIREFLY RL improves Qwen3-4B across all evaluated public benchmarks.
On Tau2-Bench, the model improves from 0.491 to 0.627 on Retail, from 0.365 to 0.525 on Airline,
and from 0.189 to 0.204 on Telecom. On MCP-Atlas, accuracy improves from 19.4% to 26.0%.
On MCPMark, the model also improves across all evaluated subsets, from 40.0% to 60.0% on File
System, from 70.0% to 80.0% on Postgres Easy, and from 9.5% to 13.3% on Postgres Standard.
These consistent gains suggest that the model does not merely memorize cached trajectories from
FIREFLY. Instead, training on verified single-turn multi-step tasks appears to improve transferable
tool-use behaviors, including selecting relevant tools, grounding arguments in observations, chaining
intermediate outputs, and deriving final answers from structured tool responses. The improvements
on MCPMark show transfer to real MCP execution environments, while the gains on MCP-Atlas
show transfer to manually designed MCP-style servers. Most notably, the improvements on Tau2-
Bench indicate that single-turn multi-step supervision can also benefit multi-turn tool use: although
Tau2-Bench requires interaction across multiple user turns, many of its core difficulties still involve
robust tool selection, state tracking, API grounding, and multi-step reasoning. Overall, these results
support the claim that FIREFLY provides broadly useful supervision for tool-calling agents beyond
its own data distribution.
To compare RL with supervised learning on the same tasks, we also fine-tune the same Qwen3-4B
base model on trajectories that Claude Sonnet 4.5 generates for the training tasks and that reach
correct answers. Supervised fine-tuning on these Claude-generated samples improves pass@1 on
the FIREFLY test set from 28.1% to 38.5% after three epochs, and RL on FIREFLY reaches 41.5%,
outperforming the best supervised configuration by 3.0 points (Table 6 in Appendix B). Appendix B
also compares our model with models trained on the Toucan dataset [31], and our model achieves
higher scores on all three Tau2-Bench domains.

6
Conclusion
We presented FIREFLY, a pipeline for generating large-scale, verified tool-call training data from
real-world MCP servers. By inverting the standard synthesis pipeline (explore first, then back-
chain tasks from observed outcomes), FIREFLY makes label correctness a property of data gen-
eration rather than post-hoc filtering. A pairwise tool graph scales exploration to nearly 1,000
tools, while a retrieval-augmented simulator enables reproducible simulator-based online RL train-
ing and evaluation despite environment drift in live APIs. The resulting dataset of 5,144 verified
tasks across 240 servers enables a 4B model to match Claude Sonnet 4.6 on our held-out test set,
and the same model improves on multiple out-of-distribution tool-calling benchmarks, although
our comparison with Claude Sonnet 4.6 is limited to the held-out test set. We release the code
at https://github.com/leoleoasd/firefly-neurips-2026/ and the data, simulator, and
model at http://firefly.hailab.io/ to support scalable, verifiable agent learning.
7
Limitations
Model scale.
Due to computational constraints, we only train and evaluate a 4B-parameter model.
While the results demonstrate clear gains from FIREFLY’s verifiable supervision, larger models are
likely to benefit even more: the modest gap between pass@1 and pass@16 (41.5% vs. 57.0%)
suggests that the 4B model lacks the capacity to solve many harder multi-step tasks regardless of
sampling budget. Scaling to larger models (e.g., 30B+ parameters) would likely raise both the
pass@1 ceiling and the pass@16 coverage, as larger models can internalize more diverse solution
strategies from the training trajectories.
Single-turn interaction.
All tasks in FIREFLY follow a single-turn format: the user issues one
request and the agent completes it through multi-step tool calls. Real-world tool-use scenarios often
involve multi-turn conversations where the user provides clarifications, changes requirements, or
builds on previous results. Extending the pipeline to generate and validate multi-turn dialogues with
interleaved user messages is an important direction for future work.
Conservative simulator errors.
The simulator returns a tool error for calls that differ semantically
from every cached call, so an agent that finds a valid path outside the explored trajectories during
RL receives an error for that path, which may narrow the policy toward explored paths. To bound
this truncation risk, we classified every evaluation tool call as an exact, minor, or major deviation
from the nearest cached call and related the classes to task success. In successful trajectories, about
24% of calls deviate from the cached ground-truth path (13.8% with major and 10.4% with minor
deviations) and still lead to full reward, so alternative paths can pass through the simulator. In failed
trajectories, 66.8% of calls deviate majorly, so the errors fall mostly on semantically wrong calls,
such as calls with wrong entities or query scope, and seldom on valid reformulations. After an error,
the agent can retry with corrected arguments within its round budget, as it would after a real API
returns a client error. Moreover, the untrained base model shows the same relation between deviation
and failure, so the errors do not selectively shape the trained policy.
Generation cost.
Generating FIREFLY costs approximately $47K in API usage (Sec. 4), which
may limit how easily smaller teams can regenerate the dataset around their own tools. The total
amounts to about $9 per verified task, and each task comes with a ground-truth trajectory, an answer
schema, and a replayable environment. Since we release the dataset, the simulator, and the trained
model, downstream users can train and evaluate without API costs, and teams with proprietary tools
can start from the released model instead of regenerating a dataset.
Number of servers.
FIREFLY covers 240 servers because the four filtering criteria in Sec. 3.1.2
retain only 240 of roughly 3,000 scraped servers, so the supply of qualifying public servers limits the
dataset’s scale more than the pipeline does. The pipeline itself is registry-agnostic, and new servers
can be added incrementally. New tools join the graph through pairwise judgments against existing
nodes, and exploration extends to their neighborhoods without re-processing existing servers.

asks whether the task text together with the tool input schema suffices to construct the tool call.
Answer uniqueness asks whether exactly one answer is defensible. Label correctness asks whether
every field of the recorded answer is supported by a tool output and not only by a tool input. Realism
is rated on a scale from 1 to 5.
As shown in Table 9, tasks that passed the judge satisfy all three binary criteria 78.0% of the time,
compared with 38.0% for rejected candidates, and the difference is statistically significant (χ2 =
16.4, df = 1, p < 0.001).
