###### ABSTRACT


######## Tool-using language models are increasingly deployed in conversational settings,


######### yet most large-scale tool-use benchmarks focus on isolated requests. We introduce


######## ToolTurns, a benchmark of 2,620 problems spanning 1,827 tools and 11,004 API


######## endpoints across 47 categories. Each dialogue begins with an intentionally under-


######### specified request and continues through two context-dependent follow-ups, testing


######## clarification, tool use, and retention of conversational context. We also introduce


######## an open-source user simulator that reveals withheld context through dialogue and


######### generates follow-up requests, with a checker–fixer pipeline for improving its turns.


######### Across nine language models, the best agent resolves 69.6% of individual requests


######## but completes only 39.8% of full dialogues. Under this evaluation protocol, every


######## evaluated model receives lower success scores on follow-up requests than on the


######### initial request, and dialogue-quality rubric scores and task success can rank models


######## very differently. Paired turn-level evaluation shows that the checker–fixer reduces


####### detected dialogue defects, and blind human evaluation favors the revised turns.


####### ToolTurns provides a testbed for evaluating whether agents sustain task success


######## across multi-turn dialogue with tools.


###### 1


###### INTRODUCTION


######## A tool-using assistant must do more than answer an initial request. A user asking “What games are


####### happening this weekend?” may omit the sport or location, then ask follow-up questions about the


####### results. The assistant must elicit missing information, use the available APIs, and carry relevant


####### context into subsequent requests. These decisions shape the conversation itself: an assistant’s


######## clarification or answer changes what the user says next. Evaluating this behavior therefore requires


######## following the agent through an interaction, including the requests that arise after its first answer.


####### Existing benchmarks capture different aspects of this challenge (Table 1). ToolBench (Qin et al.,


####### 2024) provides broad API coverage, while ToolDial (Shim et al., 2025) evaluates conversational


####### tool-use capabilities from recorded dialogue histories. Interactive benchmarks such as τ-bench


####### (Yao et al., 2024) and ToolSandbox (Lu et al., 2025) evaluate agents within stateful application


######## environments; τ 2-bench (Barres et al., 2025) further tests coordination when users can also act on the


######## environment. We study the combination of broad API coverage and adaptive, end-to-end dialogue


######### evaluation: whether agents can clarify underspecified requests and resolve related follow-ups across


######## diverse tool sets.


####### We introduce ToolTurns, a benchmark of 2,620 initially underspecified problems spanning 1,827


####### tools and 11,004 API endpoints across 47 RapidAPI categories (§ 3; statistics in Table 2). Each


######## problem exposes a fixed subset of endpoints—26.5 on average—and unfolds into an initial request


####### followed by two adaptively generated follow-up requests. A user simulator answers clarification


######### questions using withheld context and generates follow-ups from the user-visible conversation. Agents


######### interact with these users and a StableToolBench-based tool environment (Guo et al., 2024) (a cached,


######### LLM-simulated execution layer for the ToolBench APIs), producing 7,860 separately scored subtasks


######### per agent. This design combines API breadth with evaluation along each agent’s own conversational


######## trajectory.


######### Because the simulated user helps determine the evaluation trajectory, we also examine the quality of


####### its contributions. We develop a checker–fixer pipeline that revises candidate user messages before

###### RELATED WORK


######## The rise of tool-calling LLMs has led to two key directions in evaluation which intersect our work:


######## scaling to large, diverse sets of APIs, and supporting tool use in interactive, multi-turn dialogues.


####### Scaling Tool Evaluation Where early tool-calling evaluations focused on relatively small sets of


######## tools (Tang et al., 2023), recent efforts have aimed to scale this to larger, more diverse sets of tools


####### (Patil et al., 2023; Qin et al., 2024; Elder et al., 2026). Qin et al. (2024) provide one of the largest


######### such evaluations in ToolBench, evaluating LLMs on problems using over 16,000 APIs sourced from


####### RapidAPI. 1 While comprehensive in tool scope, each problem is designed for only a single-turn


####### interaction: missing real-world cases where the model must seek details or clarification from the


######### user, or respond to follow-ups. Our work aims to address this limitation by introducing ToolTurns, a


######## large-scale tool-calling evaluation for the multi-turn dialogue setting, where an agent must support


######## both clarification-seeking and follow-up requests. We build our evaluation upon the RapidAPI tool


######## set proposed in Qin et al. (2024).


######### Interactive Tool-Use Benchmarks Prior tool-use evaluations fall into three settings: broad API cor-


######### pora, recorded conversational evaluations, and interactive stateful environments (Table 1). ToolBench


####### gives one user instruction over a large RapidAPI catalogue, so later tool steps are not further user


######### turns; ToolDial, ToolTalk, API-Bank, and DialogTool instead score recorded or annotated dialogues,


######### executing tools only where the benchmark implements them (Qin et al., 2024; Shim et al., 2025; Farn


######## & Shin, 2023; Li et al., 2023; Wang et al., 2025). τ-bench, τ 2-bench, ToolSandbox, and VitaBench


######## keep an adaptive user inside a stateful application and grade environment outcomes or rubrics (Yao


######## et al., 2024; Barres et al., 2025; Lu et al., 2025; He et al., 2026).


####### ToolTurns evaluates clarification and successive requests over a broad API catalogue. τ-bench


####### and τ 2-bench emphasize domain policies, verifiable environment outcomes, and, for τ 2 telecom,


######### user–agent coordination. Our broader schema coverage does not establish stronger state modeling or


######## more reliable ground-truth evaluation. Two related settings sit outside the table. Wang et al. (2024)


######## evaluate multi-turn tool use in which the model executes Python tools and revises its solution using


####### language feedback. Wu et al. (2024) study tool planning for multi-granularity instructions; those


######## solution steps are successive tool calls for one instruction, not conversational turns.

######## PROBLEM DESIGN


######## A ToolTurns problem is a triple (qi, Ti, Gi), where qi is the user’s initial natural-language query, Ti


####### is a fixed set of callable tool endpoints and their schemas, and Gi = {(sij, vij)}mi


####### j=1 is the unseen


######## user’s goal, represented as a set of slot–value constraints. Each slot sij corresponds to an argument in


######## a tool schema, and vij is the value that the user has in mind but does not initially specify in qi.


####### The dialogue begins with qi. At each step t, conditioned on the dialogue history and the schemas


######## of Ti, the agent selects an action at ∈A(Ti) that either (1) invokes an endpoint and receives a tool


######## observation ot, (2) sends a message to the user and receives a user response ot, or (3) completes the


######## current request with a final answer yt. In response to a clarification request, the user simulator reveals


######## relevant slot values from Gi.

####### This design isolates two distinct skills: tool selection and use (the agent must combine endpoints


####### from the available set to satisfy a request) and clarification dialogue (the agent must elicit the


######## withheld context before it can call the right endpoint with the right parameters).


######### Tool catalogue. We use the RapidAPI tool collection released with ToolBench (Qin et al., 2024), in


######## which each tool is represented by its available endpoints and parameter schemas. StableToolBench


######### exposes the same collection during execution, allowing the sampled tool sets to be evaluated without


######## schema conversion.


######## Tool-set sampling. We draw seed tool sets from ToolBench’s three retrieval groups, which differ in


######## how the underlying tools relate to one another: G1 (single-tool sets), G2 (intra-category multi-tool


######### sets, where the tools share a RapidAPI category), and G3 (intra-collection multi-tool sets, which span


####### categories within a curated collection). Following ToolBench’s own filtering, we discard seed sets


######### with fewer than three endpoints. G1 always uses a single seed set per problem. For G2 and G3, with


######### probability 0.5 we sample two distinct seed sets and combine their endpoints; this produces problems


######## that may require tools from different categories.


######### Endpoint expansion. ToolBench’s seed sets identify a small number of representative endpoints, but


######### realistic requests may require other capabilities of the same tools. We therefore expand each sampled


######## set to include all endpoints belonging to its referenced tools.


####### Vague-query generation. For each expanded tool set, we prompt GPT-4o-mini to produce two


####### queries using a fixed template. The prompt instructs the model that queries must (a) read like a


######### natural request a human might make, (b) not mention tool or API names, (c) be answerable by some


######### combination of the provided endpoints, and (d) deliberately omit details that the agent would need to


######### actually make a call. For each query the model additionally returns 2–4 context keywords encoding


######## the omitted details as concrete values (e.g. Paris, December, Lakers) rather than type placeholders


######## (e.g. city, month, team_name); the prompt gives explicit good/bad examples to enforce this. These


######## keywords become the problem’s withheld context.


######## Example. Problem 2610 in ToolTurns has the initial query:

“I heard there’s a big game coming up soon. Can you tell me when it is?”

######## Its withheld context is NBA, Los Angeles, Lakers, and October, and its tool set exposes 48 endpoints


######## from an NBA data API, a web search API, and a geographic database. The agent must first clarify


####### the sport, team, and time frame before selecting among the available endpoints. §F.1 shows how


######## different agents handle this problem.

####### A dialogue is generated by alternating between an agent (the assistant under evaluation), a user


######## simulator (§3.3), and the tool environment provided by StableToolBench. For each problem, the


####### environment exposes only the sampled set of endpoints. Each problem (§3.1) yields exactly one


######## dialogue.

####### Agent turn structure. Within a single turn the agent runs a tool-using search loop. Two reserved


######## control tools terminate the turn: finish, which the agent calls when it has a final answer for the user,


######## and message_user, which the agent calls when it needs clarification or additional information before


####### it can proceed. The agent may call RapidAPI tools within a search loop capped at 15 messages,


######## followed by one final synthesis call if the budget is exhausted (Appendix C). Tool responses come


######### from StableToolBench’s cached RapidAPI pool where available and from an LLM-simulated response


####### otherwise. The resulting dialogue also depends on the simulator’s sampled replies and follow-up


######### requests. The user simulator never sees tool calls or tool responses. Each dialogue has three requests,


####### the initial query and two follow-ups; the message streams and the turn and search budgets are in


######## Appendix C.


######## 3.3


######## USER SIMULATION


######## The user simulator answers the agent’s clarification questions from the problem’s withheld context


######## and generates the follow-up requests that continue the dialogue. It is implemented as two separate


######### LLM-prompted generators that share the same backbone model and the same view of the conversation;


######## the active generator is chosen by whether the agent called finish or message_user.


######## Follow-up query generator. Active after the agent calls finish. The prompt instructs the simulator


######## to extend (not rephrase) the conversation: ask a creative follow-up that builds on what the assistant


######### already provided, explores a new facet of the problem, and is solvable by exactly one operation from


####### api_list. A strict anti-hallucination rule forbids the simulator from attributing facts (IDs, names,


######## numbers, dates) to the assistant or tools unless those facts appeared explicitly in the dialogue, while


######## still permitting the user to introduce their own preferences and constraints.


######## User-response generator. Active after the agent calls message_user. The prompt is the same anti-


####### hallucination contract as above, with one important addition: the generator receives the problem’s


######### withheld context (§3.1) and is instructed to weave relevant context keywords into the reply naturally


######## when answering the assistant’s clarification, rather than dumping all keywords up front. This is the


######### mechanism by which the user simulator reveals the deliberately omitted details (location, dates, entity


######## names, etc.) incrementally as the agent asks.


####### Backbone model. The simulator backbone is configurable to any OpenAI-compatible model; in


####### our main experiments (§ 4) we use Qwen3-32B-AWQ served via vLLM, an open-weight model


####### chosen for its balance of user-simulation quality and serving cost (§ B.2). As a user simulator,


######### GPT-4o-mini appears only as a closed-source comparison condition in the ablations of Appendix B.2


######## and Appendix B.4.


######## 3.3.1


######## CHECKER–FIXER PIPELINE


######### The simulator generates each user turn (follow-up question or response to the assistant) with a single


####### LLM call by default. When the optional checker–fixer pipeline is enabled, two further stages run


######## before the turn is committed.


######## Checker. A separate LLM call evaluates the generated message against a fixed set of rules over the


######### current dialogue history. The checker detects eleven violation types (Table 8). The checker returns a


######## structured report with a boolean has_issues flag and a typed list of detected violations.


####### Fixer. If has_issues is true, a second LLM call revises the user message. The fixer receives the


######### dialogue history, the original message, and the checker report, and is instructed to resolve all reported


######### violations while preserving the communicative intent and without introducing new violations (e.g. no


####### fabricating tool facts). The revised message replaces the original and is used as the next user turn;


####### if no issues are reported the original message is used as-is. The same LLM is used for generation,


####### checking, and fixing. Alongside the eleven LLM-judged violation types, a deterministic rule set


######### flags near-duplicate sentence frames, verbatim repetition of prior turns, and empty or non-advancing


######### messages; these rules require no model call and are reused as an independent measurement instrument


######## in Appendix B.2.3. The pipeline’s effect on turn quality is summarized in §4.2; the dialogue-level


######## comparison and the paired turn-level analysis are in Appendix B.2.

######## 3.4


######## EVALUATION DESIGN


######## We evaluate each generated dialogue along two axes: dialogue quality, measured by a five-aspect


######### LLM-judged rubric, and task success, a per-subtask binary judgment of whether the user’s informa-


######### tion need for that query was fully resolved. Both rely on LLM judges with structured function-calling


######## outputs and a fixed prompt set across conditions.


######## 3.4.1


######## DIALOGUE QUALITY RUBRIC


####### The dialogue quality rubric scores each generated dialogue across five aspects, one LLM call per


####### aspect: consistency, factual coherence between the assistant’s claims and tool outputs; relevance,


######## whether assistant turns address the user’s request; efficiency, economy of tool calls and turns; cor-


######## rectness, whether the final answer is factually right with respect to tool evidence; and adaptability,


######### handling of clarifications, corrections, and underspecified inputs. Each aspect is scored on a discrete


######## [0, 1] scale with five levels (0, 0.25, 0.5, 0.75, 1.0) and the judge additionally returns a brief justifica-


####### tion. Aspect scores are combined into a single weighted aggregate (correctness 0.30; consistency,


####### relevance, efficiency 0.20 each; adaptability 0.10). Because scores take only five discrete values,


######## mean differences at the second decimal place correspond to a one-level shift on a small fraction of


######## dialogues, so we do not read small second-decimal gaps as meaningful differences.


######## 3.4.2


######## TASK SUCCESS


######## Task success is determined by a hybrid evaluator that applies a deterministic hard-fail gate before


######### invoking an LLM judge. It scores each subtask of the dialogue (the initial query and each follow-up


######## query, §3.2) independently, rather than issuing a single judgment for the dialogue as a whole. The


####### gate handles failure modes that can be identified cheaply and with certainty, so the LLM judge is


######## reserved for cases where the outcome is uncertain.


####### Subtask segmentation. Each dialogue is split into its three main queries (one initial query and


######## num_follow_up_queries = 2 follow-ups), and the gate and LLM judge below are applied separately


######## to each subtask’s slice of the dialogue (its query, turns, tool calls, and tool responses).


####### Deterministic gate. A subtask fails without an LLM call when every substantive tool observation


######## is StableToolBench documentation-placeholder prose, a description of the API rather than live data


######## (for example, “The API call to . .. is designed to provide .. .”), and none of the observations yields


####### data-shaped output such as structured fields, lists, or typed scalars beyond bookkeeping keys like


######## status, success, or code. The gate is rarely decisive: it applies to only 20 of the 70,740 subtasks


####### across the nine agents in §4.1 (0.03%; at most five per agent), placeholder prose appears at all in


######### only 154 (0.2%), and no pooled subtask pass rate in Table 3 moves by more than 0.03 points with or


######## without it, so cache coverage does not account for the failure rates we report.


####### LLM judge. If the gate passes, a single LLM call decides semantic task completion for that


####### subtask via structured function-calling. The judge receives the subtask’s query and its slice of the


######### dialogue (turns, tool calls and their responses, and the assistant’s answer) and must return a boolean


####### task_succeeded with a brief justification. The system prompt instructs the judge to be strict on


####### wrong or missing answers; a subtask passes only if the user’s information need for that query was


######## fully met by the final outcome.


####### Dialogue-level score. A dialogue’s task-success score is the fraction of its subtasks that succeed,


####### success_count / total_subtasks (e.g. 2/3 if the initial query and one of the two follow-ups


####### succeed); a dialogue counts as fully successful only if every subtask succeeds. We report both


####### quantities in §4.1: the pooled subtask pass rate as the headline figure, and the stricter all-subtasks-


######## pass rate alongside it.

######## 4.2


######## VALIDATING SIMULATED USER TURNS


######### Because the simulated user shapes the evaluation trajectory, we validate its turn quality. On the turns


######## it rewrites, the revision pipeline removes 41.2% of automatically detected defects, and blind human


######### annotators prefer the revised turn 63.3% of the time. These measurements use 1,272 user turns from a


######### separate 322-dialogue single-call condition, rather than the 2,620-problem ToolTurns set. The checker


######### flags 543 turns (42.7%), and the fixer rewrites 536 (42.1% of all turns). On those 536 rewritten turns,


######## detected defects fall from 335 to 197; the paired within-turn change is −0.257 defects per turn (95%


######## bootstrap CI [−0.308, −0.207]). In the blind human comparison, the revised turn is preferred in 76


######## of 120 sampled pairs (p = 4.5 × 10−3). The gains concentrate on contextual unawareness, repetition,


######### and failure to advance the task rather than on templated phrasing, which is the most frequent trigger


####### but is indistinguishable from chance under human preference. Dialogue-level rubric scores are


####### insensitive to a turn-local intervention. The scores, violation-type breakdown, comparison against


######## human-written API-Bank dialogues, and detector calibration are reported together in Appendix B.


######## 4.2.1


######## HUMAN VALIDATION OF THE AGENT EVALUATORS


####### We validate the LLM Judge used in Table 3 through human annotation. For binary task success,


######## human and LLM judgments achieved substantial agreement (Cohen’s κ = 0.68), validating the use


######### of an LLM judge for evaluating agents for this task. Across the five dialogue-quality aspects, we see


######## moderate agreement, with a quadratic weighted Cohen’s κ = 0.53. While the agreement is lesser due


######## to the challenges of evaluating each quality dimension, we find agreement is still significant.


###### 5


###### CONCLUSION


######## We evaluate tool-using agents on ToolTurns: multi-turn dialogue over a broad API catalogue, with


####### clarification and follow-up requests scored along each agent’s own trajectory. Under the existing


####### evaluation protocol, no agent is scored as completing even two dialogues in five, and every agent


######## receives lower success scores on both follow-ups than on the initial request. Because rubric scores


######## rank models differently from completion (ρ = 0.23), progress in this setting has to be measured as


######## completion rather than inferred from dialogue quality.

######## B.1


######## USER SIMULATOR EVALUATOR


######## The dialogue quality rubric and task-success evaluator both target the agent: they assume a reasonable


######### user simulator and measure how well the assistant performs. To assess the simulator independently —


####### for example, when comparing user-simulator configurations with the agent held fixed — we use a


######## separate LLM judge that scores complete dialogues across seven dimensions on a continuous [0, 1]


####### scale. The judge receives the original query, the complete dialogue, and the final assistant answer;


######## for each dimension it returns a score and a brief justification. The dimensions and their weights in


######## the aggregate score are: realism (0.15) — whether the simulator’s behaviour and language feel like


####### a real user; contextual awareness (0.20) — whether messages are grounded in what the assistant


####### actually said; relevance (0.15) — whether follow-ups are useful and on-topic; natural language


####### (0.10) — whether phrasing is human-like and varied; conversational flow (0.15) — whether the


######### dialogue progresses naturally; clarity (0.10) — whether queries are clear and interpretable; and goal


####### progression (0.15) — whether user turns help resolve the original query. The overall score is the


######## weighted sum of the seven dimension scores.

######## RESULTS


######## Table 5 reports mean scores across 322 dialogues for each condition.


######### All three conditions score in a narrow band (0.858–0.871 overall), and the differences between them


######### are small relative to the resolution of the judge. The checker–fixer condition is nominally highest on


######### all seven dimensions and on the weighted overall score, and the open-weight simulator with revision


######### (0.871) is at least at parity with the GPT-4o-mini closed-source baseline (0.858). We deliberately do

####### works: dialogue-level aggregates are structurally insensitive to this intervention, because the fixer


######### rewrites only the minority of turns its checker flags and any effect is then averaged over the untouched


######### turns of the dialogue. Appendix B.2.3 therefore measures the intervention where it actually operates.


####### Aggregate parity conceals a difference in specificity. The near-identical overall scores of GPT-


####### 4o-mini and the open-weight conditions do not imply equivalent behaviour. Counting concrete


######### references per user turn — quoted names, identifiers, hashtags, CamelCase tokens, and proper-noun


####### spans, extracted by a deterministic parser — GPT-4o-mini produces 0.98 per turn against 1.98


####### for Qwen3-32B, at essentially the same turn length (40.2 vs. 42.1 words) , and 43.1% of its turns


######## contain no concrete reference at all against 19.3% for Qwen3-32B. The proprietary baseline attains


######## comparable rubric scores in part by asking vaguer questions, which are harder for a rubric judge to


######### penalise; a simulator that never commits to a specific entity cannot be marked down for misusing one.


######## This is a limitation of aspect-style rubric judging that we return to in Appendix B.3.3.


######## B.2.3


######## TURN-LEVEL INTERVENTION ANALYSIS


######## The checker–fixer is a turn-local mechanism: it inspects one candidate user message and, if flagged,


######### rewrites that message. Measuring it by comparing whole dialogues across two independently sampled


######### conditions dilutes the effect twice over — across the untouched turns of each dialogue, and across the


######### sampling variation between runs. We therefore evaluate the intervention directly, and pair at the level


######## at which it acts.


######## 13


--- PAGE 14 ---


######## Preprint


######### Protocol. We take all 1,272 user turns produced by the Qwen3-32B single-call condition. These are


######### unrevised drafts from the same backbone under the same prompts, so they are exactly the inputs the


######## pipeline would have received. Holding the preceding dialogue history fixed, we run the production


######### checker on each turn and, wherever it fires, the production fixer, using the same model and decoding


######### settings as the deployed system. Only the single user message is rewritten; no dialogue is regenerated


######### and no agent or tool call is re-executed, so the counterfactual differs from the observed draft in exactly


####### one respect. We then score the original draft and the rewritten message against each other under


######## identical history.


######## Coverage. The checker fires on 543 of 1,272 turns (42.7%), and the fixer alters the message on 536


######### of those (98.7% of firings; 42.1% of all turns). The most frequently reported violations in unrevised


######## drafts are templating (75.9% of firings, 32.4% of all turns), lack of progress (33.7% of firings), and


####### contextual unawareness (27.3%). Templating dominates, and 39.8% of firings report it as the sole


######### violation, so the modal intervention is a rewording that preserves the request while breaking a reused


####### sentence frame. Revised turns are correspondingly close to their drafts in content but not in form:


######### mean word-level overlap between draft and revision is 0.37. We state this explicitly because it bounds


######### what the pipeline should be credited with — it is predominantly a diversity and phrasing intervention,


######## not a hallucination filter.


####### Result. On the 536 rewritten turns, we count violations using the deterministic rule set of §3.3.1,


######### which is independent of any LLM judge. Revision reduces the total from 335 to 197 detected defects,


####### a 41.2% reduction. The paired within-turn change is −0.257 defects per turn (95% bootstrap CI


####### [−0.308, −0.207]); 167 turns improve, 37 worsen, and 332 are unchanged (two-sided sign test,


####### p = 6.4 × 10−21). Because the same detector is applied to the draft and its revision on identical


######### history, this comparison is unaffected by the detector’s absolute calibration: any constant bias cancels


######## within the pair.


####### The result establishes that revision repairs the turns it targets; it does not establish a proportional


######## improvement in end-to-end dialogue quality, which Table 5 shows to be small. An intervention that


####### fires on 42% of turns and repairs a subset of defects in those turns should be expected to move a


######## dialogue-level weighted average only slightly.


######## B.3


######## USER-SIMULATOR EVALUATION VS. HUMAN JUDGMENT


######### Appendix B.2.3 establishes the effect of the checker–fixer pipeline using a deterministic detector that


####### shares its rule vocabulary with the checker itself. That circularity is worth taking seriously, so this


######### section evaluates the same intervention against human judgment. Further analyses of the same labels


######## are in Appendix B.3.3.


######## B.3.1


######## EXPERIMENTAL SETUP


####### The checker–fixer acts on individual turns, so we annotate at that granularity. From the 536 turns


######### revised in Appendix B.2.3 we sampled 120 uniformly at random. For each we presented the preceding


######### dialogue history followed by the original draft and the revision as unlabelled candidates, in an order


######### randomised per item. Annotation was blind: system identities were withheld, as was any indication of


######### which candidate had been revised. The better user turn was selected under a rubric fixed in advance,


######### applied in priority order: grounding in what the assistant actually provided, contextual awareness, task


######## progression, avoidance of templated phrasing, and naturalness of user voice. Length was explicitly


######### excluded as a criterion, as was surface politeness unless it accurately reflected what the assistant had


####### said or done. No tie option was offered. These labels calibrate the automatic measure rather than


######## serve as ground truth.

######## B.3.3


######## FURTHER ANALYSES OF THE HUMAN TURN COMPARISON


######### A stylistic asymmetry that is a mechanism, not an artefact. Revised turns open with an acknowl-


####### edgment of the assistant’s previous message far more often than drafts (43.3% vs. 20.0%), and


####### the acknowledgment-bearing candidate was chosen in 41 of the 46 items where exactly one side


####### had one. Read in isolation this looks like a learnable cue that could substitute for judgment. It is


####### better explained as the repair itself. The 46 acknowledgment-asymmetric items more often carry


######## contextual-unawareness flags (50.0%, vs. 14.9% among the 74 matched items) or lack-of-progress


####### flags (67.4% vs. 18.9%). Conversely, templating is flagged more often among the matched items


####### (83.8%) than among the asymmetric items (56.5%). These percentages count any templating flag,


####### including flags that co-occur with other violations: 88 of the 120 items have a templating flag, but


######### only 47 have templating as their sole flag (Table 6). Opening a turn by registering what the assistant


####### just said is one way to repair a turn that ignored it, so conditioning on acknowledgment may also


######### remove part of the intervention’s effect. The acknowledgment-matched and templating-only subsets


######### therefore should not be treated as interchangeable. We report the asymmetry for transparency but do


######## not treat the matched-subset rate (56.8%, p = 0.30) as the corrected estimate.


####### The deterministic detector is directionally sound but under-sensitive. Human labels let us


####### calibrate the instrument used in Appendix B.2.3. Across the 120 annotated pairs the deterministic


######### count expresses a preference on only 47; on those it agrees with the human choice 68.1% of the time


####### (κ = 0.23) and favours the revision 36 to 11, matching the human direction. On the remaining 73


######## it is silent, yet the revision is preferred on 45 of them (61.6%, p = 0.06). The detector thus misses


######## roughly three fifths of the changes a human perceives while rarely pointing the wrong way.


####### Implications for how these measures should be used. Two conclusions follow, and together


####### they justify the design of Appendix B.2.3. First, an absolute defect rate from this detector is not


######## 15


--- PAGE 16 ---


######## Preprint


####### a trustworthy standalone quality measure, and we do not report one; it is silent on the majority of


######## changes a human notices. Second, weak absolute calibration does not preclude paired use: applied


####### to a draft and its revision under identical history, a constant bias cancels within the pair, leaving


####### the difference interpretable even though the levels are not. Since the detector is silent far more


####### often than it errs, that difference understates rather than inflates the effect — which is why the


######## automatic estimate (41.2% fewer defects) and the human estimate (63.3% preference) can both be


######### reported without conflict. More broadly, the specificity gap in Appendix B.2 — GPT-4o-mini making


######## half as many concrete references per turn while scoring comparably on the rubric — indicates that


####### aspect-style judges reward safe, underspecified user behaviour, and should be complemented by


######## measures sensitive to what a simulator actually commits to.

######## COMPARING THE USER SIMULATOR TO HUMAN-WRITTEN DIALOGUES (API-BANK)


####### The experiments in Appendix B.2 compared user-simulator configurations against each other; the


######### more fundamental question is whether the simulator behaves at all like a real user. We use API-Bank


####### (Li et al., 2023) as a source of human-written, multi-turn user–assistant dialogues with explicit


######### tool-use structure, and apply the same user-simulator evaluator (Appendix B.1) to both human-written

######## B.4.1


######## EXPERIMENTAL SETUP


######## Why API-Bank. API-Bank’s evaluation split provides annotated conversations that — unlike most


######### ToolBench-style corpora, which centre on RapidAPI tool definitions and synthetic or retrieved queries


######### — are closer to what we want for studying tool-using dialogue under a fixed task distribution. It is not,


######## however, RapidAPI-isomorphic: API-Bank names capabilities with short symbolic API names (e.g.


######### calendar or email operations), so it cannot be run directly against our StableToolBench environment


######## without a bridging step to real RapidAPI tool schemas.


####### Data preparation. We normalize API-Bank test data into a single repository layout: 622 JSON


####### files (one per dialogue) plus a global initial_queries.json index (622 rows; 522 multi-turn


####### level-1/2 scenes, 50 level-3 holistic scenes, 50 level-3 batch scenes). Each dialogue record carries


####### dialogue_messages (user / assistant roles), an initial_query, metadata.tools (distinct tool


######## names in first-seen order), an optional api_request_trace, and gold fields where the source provides


######### them (e.g. next API string vs. next utterance, depending on level). This format is stable for downstream


######## scripting and reusable for the LLM-judge comparison below.


######### Mapping API-Bank tasks to RapidAPI tools. Because our agent environment executes RapidAPI-


######### style tools indexed from a local ToolBench tree (category / tool / API JSON), we map each API-Bank


####### dialogue’s tool hints into a small set of concrete RapidAPI operations. We first collect the distinct


######## API-Bank tool names appearing in metadata.tools across the slice we use (68 unique names in the


######## full 622-dialogue set). For each name, we retrieve candidates from the local catalog via embedding


####### similarity over serialized tool+API descriptions, then optionally apply a single lightweight LLM


####### rerank that chooses a fixed number of candidates by index, so the model cannot invent tool names.


######## For each dialogue, we merge per-name lists in hint order, deduplicate by (category, tool, API),


######### and cap the number of exposed APIs (top 15), producing a merged query file aligned with our existing


######## dialogue runs (original_query, query_str, context, api_list).


######### Simulated dialogues. For each of the 622 API-Bank initial user goals we run our generative dialogue

###### DIALOGUE GENERATION DETAILS


######## Dual message streams. The runtime maintains two parallel message lists: search_messages is the


####### agent’s full view, including system prompt, tool calls, tool responses, and intermediate reasoning,

######## visible messages; if the cap is reached before the agent calls finish or message_user, the agent is


######## forced to conclude that subtask. The response generator may still emit the sentinel <STOP>, treated as


######## the user abandoning the current subtask early. A separate budget, max_search_messages = 15, caps
