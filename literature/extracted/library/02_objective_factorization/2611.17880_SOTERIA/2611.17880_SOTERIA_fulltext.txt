Abstract
LLM agents that execute multi-step tool calls must satisfy two objectives simul-
taneously: completing the user’s task (utility) and conforming to domain policies
and correctness constraints (safety). These objectives are in tension – blocking an
unsafe action prevents a violation but can leave the agent stranded with no prin-
cipled way to recover. Existing approaches sacrifice one objective for the other.
We introduce SOTERIA, a framework that reconciles safety and utility through
verified hierarchical planning and runtime enforcement of specifications. Before
execution, the agent generates a structured plan that is formally verified against
the specifications prior to any tool invocation. During execution, the verified plan
serves dual roles: it ensures that the agent takes specification-conformant trajec-
tories and provides guidance when unsafe actions are blocked. Across multiple
benchmarks covering a diverse range of tool-use tasks, SOTERIA achieves 1.7
times the average task success rate of the best baselines, with no violations of
policy specifications, demonstrating that safety and utility need not be traded off.

Introduction
LLM agents are increasingly deployed for complex, multi-step tasks — from software engineer-
ing [Jimenez et al., 2024] and scientific discovery [Novikov et al., 2025] to customer service [Su
et al., 2025] and enterprise automation [Zhou et al., 2023] — that require orchestrating many tool
calls whose real-world effects are difficult or impossible to reverse. In these domains, correctness
is not optional: an airline agent that cancels a reservation without verifying the passenger’s eligibil-
ity violates a policy specification; a retail agent that processes a return without first retrieving the
order details by passing fabricated data to downstream tools violates a tool data-flow specification.
Domain policies and tool contracts define what constitutes correct behavior of an agent, and the
challenge is ensuring agents satisfy these specifications without sacrificing utility.
Existing approaches to ensuring conformance rely on runtime guardrails, which take two forms.
LLM-based guardrails deploy a secondary model to judge each proposed action before it executes
[Rebedea et al., 2023, Gu et al., 2025]. They are easy to deploy but probabilistic, offering no
formal safety guarantees. Specification-based monitors provide stronger guarantees by checking
preconditions, postconditions, or trajectory invariants at runtime [Wang et al., 2025, Kamath et al.,
2025, Bhardwaj, 2026], but offer no verified recovery plan when a call is blocked. Recovering during
execution can degrade utility, especially when earlier actions have left the agent in a non-recoverable
state. Our key insight is that agents can achieve safety without sacrificing utility by constructing a
verified, specification-conformant plan a priori before any tool is invoked.
Building on this insight, we introduce SOTERIA, a framework that combines verified hierarchical
planning with runtime specification enforcement (Figure 1). In a one-time setup, SOTERIA uses
natural-language policy documents and tool definitions to produce policy specifications, tool con-
tracts, and sub-plans that describe standard procedures in the domain. The specifications and tool

Given a task, the SOTERIA Planner composes a hierarchical plan from a library of reusable, pre-
verified sub-plans and verifies it against the specifications. Plan verification checks: tool contracts
(every call satisfies its precondition), progress (the plan cannot get stuck), and policy compliance (ev-
ery execution conforms with policy rules). Failed checks produce targeted diagnostics that prompt
the planner to repair and re-verify within a fixed retry budget; when full verification is not achievable,
SOTERIA proceeds with the strongest partially verified plan as a fallback. To guarantee conformance
regardless of verification outcome or executor deviation, SOTERIA integrates a runtime SpecMonitor
that checks each proposed tool call against the specifications and blocks it if unsafe. When a call is
blocked, the executor consults the verified plan for alternatives and recovers along a guided path.
On 207 tasks across three challenging benchmarks, SOTERIA achieves 100% conformance across
all four models, while baseline conformance reaches at most 93%. SOTERIA also improves task
success by 4.7–43.9 percentage points over the best baseline (1.7 times on average) for each model–
benchmark pair, where the verified plan provides continuous guidance on the correct action sequence
even when the executor deviates.
Our results highlight two benefits of verified plans over runtime monitoring alone. First, they provide
global foresight: plan verification checks whether action sequences satisfy specifications, including
required future actions, before execution begins. Second, they provide recovery guidance: when
a call is blocked, the verified plan supplies an alternative path toward task completion. SOTERIA
combines both benefits by using the verified plan as an execution roadmap and a recovery guide
when the SpecMonitor blocks a call.
Contributions.
• We introduce SOTERIA, a framework that achieves both safety and utility for LLM agents through
verified hierarchical planning and runtime specification enforcement.
• We propose a verified planning approach (§2) that composes reusable sub-plans into hierarchical
plans and statically verifies them against tool contracts, progress, and policy specifications using
a verifier-in-the-loop that steers the planner toward correct plans.
• We propose plan-guided runtime enforcement (§3), where a SpecMonitor blocks specification-
violating tool calls before execution, and the verified plan provides the executor with a concrete
recovery path.
• We evaluate SOTERIA on 207 tasks across three benchmarks and four LLMs (§4). SOTERIA
achieves 1.7 times the average task success rate of the best baselines, with zero specification
violations (100% conformance).

execution trace that records each tool invoked, its arguments, and the returned result. We provide a

Tool contracts. A payment tool, for instance, may require that the amount is positive and the pay-
ment method is valid (precondition), and guarantees that a confirmation ID is returned (postcondi-
tion). In general, each tool has a contract defined by a precondition on its inputs and a postcondition
on its outputs. Each contract constrains individual tool calls, independently of the rest of the trace.
Policy specifications. Domain policies, such as airline cancellation or retail return policies, define
correct agent behavior for standard procedures. SOTERIA formalizes these as policy specifications,
where each specification encodes required constraints over tool call sequences.

Each specification is a first-order formula over the agent’s execution trace. The first row encodes
the policy that a reservation may only be cancelled if no flights have been flown. The formula
quantifies over all calls c to cancel reservation and requires that each be preceded (≺) by a call c′ to

an existing reservation. It uses a value-flow predicate c′.r ⇝c.⃗xamount, asserting that the refund
amount passed to the refund tool depends on data from the output of a prior reservation lookup c′.
Formalization workflow. To formalize the domain policies and tool contracts from natural language
documents and comment blocks, we follow a two-step auto-formalize then validate workflow. First,
we obtain a cold-start set of tool contracts and policy specifications using SOTERIA’s LLM-based
auto-formalizer (Figure 1, left). It takes the natural-language policy and tool definitions (input/out-
put types and docstrings) and produces per-tool pre/postconditions and specifications capturing the
constraints under which tools can be used. We then manually inspect and validate the generated
specifications. When some cases are missing, we manually formalize the policy specifications. This
manual pass also performs a coverage check: we go through the policy clause by clause and check
that every state-changing (e.g., writing to a database) rule enforceable over the tool-call trace maps
to at least one specification. The validated specifications are reused across tasks in the same domain.
Successful execution. A successful execution must satisfy two criteria: (1) utility: the environment
reflects the intended outcome of the task; and (2) conformance: all tool calls satisfy their contracts
and all policy specifications hold over the trace. SOTERIA addresses utility through verified hier-
archical planning (§2.2) and conformance through the combination of static verification (§2.4) and
runtime enforcement (§3).
2.2
Hierarchical Plans
Prior work has shown that committing to a plan before acting improves utility by giving the agent
concrete steps to follow [Wang et al., 2023, Erdogan et al., 2025]. However, naively applying plan-
ning to complex domains is difficult: real-world tasks involve many tools and multi-step proce-
dures, often spanning multiple standard operations (e.g., cancellation, refund, booking). An LLM
must generate a plan that correctly encodes all required steps, their ordering, and every specification
simultaneously. This becomes increasingly error-prone as task complexity grows.
To decompose complex tasks, SOTERIA exploits the procedural structure present in domain policies.
Each standard procedure maps to a sub-plan annotated with a contract describing what it expects
(inputs) and what it guarantees (the request is completed or safely denied). A sub-plan can therefore
be invoked like a tool, and the planner can compose sub-plans into larger plans without re-encoding

SOTERIA represents plans as
Guarded Transition Systems (GTS), directed graphs whose nodes
are states representing steps or stages in the standard procedure and
whose edges are transitions representing tool calls. Each transition
is gated by a guard: a Boolean condition over data collected dur-
ing execution (e.g., the result of a prior tool call) that determines
whether the transition may fire. This representation makes branch-
ing, sequencing, and data-dependent decisions explicit and machine-
checkable, enabling the static verification described in §2.4.
Example. Consider the task “Cancel reservation RES123.” The do-
main policy requires, among other rules: (φ1) Before cancelling a
reservation, the agent must verify that no flights have already been
flown. (φ2) A reservation may be cancelled only if the booking was
made within 24 hours.
Figure 3 shows a GTS for this task using tools for looking up reser-
vations, cancelling them, checking flown status, and computing time
differences. The contract (dashed boxes) specifies a precondition (a
valid reservation ID) and a postcondition guaranteeing either that the
reservation is cancelled or unchanged if the request is not permitted.
The plan looks up the reservation, checks the time since booking, and
branches: cancelling if within 24 hours, denying otherwise. How-
ever, this plan is incorrect: it skips the flown-status check required
by φ1. Because the plan is a formal artifact, SOTERIA detects this
violation statically before any tool is invoked; its plan verifier (§2.4) rejects the plan and steers the
planner to repair it.

2.4
Static Plan Verification
A plan generated by an LLM can be incorrect. For example, it can include tool calls that violate
policy specifications. To catch such errors before execution, SOTERIA verifies three properties of
every plan: (1) tool contract satisfaction: every call to tool a meets its precondition Pa; (2) progress:
the plan cannot get stuck at any intermediate state; and (3) policy compliance: every possible ex-
ecution trace satisfies all policy specifications. SOTERIA encodes these as verification conditions
(VCs) [Hoare, 1969] and discharges them using Dafny [Leino, 2010], an automated verifier.
Tracking symbolic state in Plan. All three checks reason about what is known about plan variables
at each point in the plan. SOTERIA tracks this by propagating a symbolic state Σ(s): at each state
s, Σ(s) is a predicate over plan variables that summarizes every valuation reachable from the initial
state. For a transition from s to s′ with guard g, the symbolic state propagated along this edge
is: Σs→s′(s′)

Tool Contract Checking. To avoid invoking tools with invalid arguments, SOTERIA checks that
every tool call in the plan satisfies the tool’s precondition. For each transition calling tool a with
arguments ⃗v under guard g at state s, the VC requires: Σ(s) ∧g ⇒Pa(⃗v). A violation of this VC
means the plan may invoke a tool with invalid arguments. For example, the call to Cancel-Resv on
line 23 of Figure 4 is checked against Σ(DO_CANCEL) ⇒PCancel-Resv.
Progress. SOTERIA verifies that the plan can always advance toward a terminal state without getting
stuck by checking two properties:
• Reachability. Σ(s) must be satisfiable for every non-terminal state s; a failure indicates that there
exists a dead branch that can never execute.
• Guard feasibility. Σ(s) ⇒(g1∨· · ·∨gn) must be valid at every non-terminal state with outgoing
guards g1, . . . , gn; a failure indicates a dead-end where no transition can fire.

Policy Compliance. SOTERIA rejects plans that may violate any policy specification by encoding
each ϕ ∈Φ as a VC. To encode ϕ, SOTERIA maintains a ghost state alongside Σ, consisting of:
(a) a monotonic step counter incremented after each action; (b) per-action call logs, recording the
step, typed inputs, and result of each call; and (c) a provenance map tracking which action out-
puts contributed to a variable’s current value. Specification predicates are encoded over this ghost
state: quantifiers range over call-log indices, temporal predicates (≺) become step comparisons, re-
lational predicates become assertions over call-record fields, and value-flow predicates (⇝) become
provenance-map membership checks. The resulting assertions are placed at each terminal state and
must hold for all paths reaching it.
Modular verification. When verifying a plan that invokes sub-plans, SOTERIA treats each sub-plan
as a tool call whose behavior is characterized solely by its contract (precondition and postcondition).
The parent plan’s VCs thus reason about sub-plan interfaces rather than their internal logic.
3
Runtime Enforcement
A fully verified plan guarantees that any execution following it satisfies all specifications. In practice,
however, two factors can compromise this: verification may be incomplete (some specifications
remain unverified after the retry budget is exhausted), and the executor (an LLM agent) may deviate
from the plan due to its stochastic nature. Either factor can lead to specification violations at runtime.
SOTERIA addresses this gap with a SpecMonitor that checks each proposed tool call against tool
contracts and policy specifications, blocking its execution if a violation would result.
Using the Plan as Guidance. To maintain progress toward task completion, SOTERIA presents the
plan to the executor as a worklist: a flowchart that is progressively simplified as tool results arrive,
showing only the remaining steps and their guard conditions (Figure 5). When a result resolves
a guard, the worklist collapses the decided branch and advances, keeping the executor focused on
what to do next. The executor retains full discretion over tool selection; the worklist guides but
does not constrain. For high-stakes workflows where deviation is unacceptable, SOTERIA also sup-
ports a strict plan-enforcement mode that permits only transitions whose guard and precondition are
satisfied (Appendix A.4).
Conformance checks via SpecMonitor. To guarantee conformance to tool contracts and policy
specifications, SOTERIA interposes a SpecMonitor before every tool execution. First, it checks the
tool’s precondition against the inputs. If the precondition is not satisfied, the call is blocked before
execution, preventing invalid invocations. Then, SpecMonitor evaluates each specification con-
cretely: it takes the current trace prefix (all committed tool calls so far), extends it with the proposed
call and its arguments, and checks whether any specification would be violated (Appendix A.5). If
so, the call is blocked before it executes, guaranteeing conformance regardless of whether the plan
was fully verified. When a tool call is approved and executed, SpecMonitor checks the tool results
against the tool’s postcondition. If this check fails, the execution is aborted because a postcondition
violation means the tool contracts are unsound, and results of plan verification cannot be trusted.
Recovery from blocked actions. When a tool call is blocked by the SpecMonitor, the executor
must recover. The worklist shows the current plan state and remaining transitions, allowing the
executor to select an alternative action that keeps the task on track. For a fully verified plan, a
block means the executor deviated; the worklist shows the plan’s intended next steps. For a partially
verified plan, specifications that were not successfully verified are surfaced as explicit warnings in

4
Evaluation
We evaluate SOTERIA on three tool-calling benchmarks across four backbone LLMs. Our experi-
ments address the following research questions:
• (RQ1) Does SOTERIA improve task success and conformance over alternative approaches? (§4.1)
• (RQ2) How does each component of SOTERIA contribute to the overall results? (§4.2)
• (RQ3) What is the effect of sub-plans on plan generation and verification? (§4.3)
Benchmarks. τ 2-Airline [Barres et al., 2025] (50 tasks) and τ 2-Retail [Barres et al., 2025] (114
tasks) from the τ 2-bench suite test airline reservation management and retail order handling, respec-
tively. Toolathlon [Li et al., 2025] (43 of 108 tasks) tests long-horizon tool calling with complex
multi-step procedures. We selected tasks in the domains of terminal interaction, filesystem manage-
ment and document editing. The selected tasks are evaluated via local MCP servers.
Specification authoring efforts. We formalized each benchmark’s policy documents using the
workflow described in §2.1. This effort took a few hours on each of τ 2-Airline, τ 2-Retail, and
Toolathlon, dominated by reading the policy and checking the generated output. The resulting spec-
ification sets are relatively compact (24, 33, and 41 formulas, respectively; Appendix C.2). While
auditing the results, we corrected mis-encoded policy specifications and added missing ones.
Setup. We evaluate four backbone LLMs: GPT-5.4-mini [OpenAI, 2026], Gemini 3 Flash [Google,
2025], Claude Haiku 4.5 [Anthropic, 2025], and Claude Opus 4.6 [Anthropic, 2026] with tem-
perature 0.0 and pass@1 (single attempt per task). SOTERIA uses a budget of 8 planning retries.
We compare against four baselines: No Guardrail (backbone LLM with tools and policy in nat-
ural language, no enforcement), NeMo Guardrails [Rebedea et al., 2023] (per-action LLM judge
via Colang input rail), AgentSpec [Wang et al., 2025] (specification-based runtime monitor with
action-trigger-predicate rules), and Agent Behavioral Contracts (ABC) [Bhardwaj, 2026] (runtime
checking of behavioral contracts). All methods use the same backbone LLMs (reasoning effort: low,
where applicable), tools, and domain policy. Full setup details are in Appendix B.1.
4.1
Main Results
To answer (RQ1), we compare SOTERIA with four baseline approaches across all benchmarks
and models (Table 2). Each row reports raw utility (task completion regardless of conformance)
narrowed to conformance-gated success (Util.→Succ.), the fraction of tasks with zero violations
(Conf.), the total violation count (#Viol.), and average API cost per task in USD. For instance, No
Guardrail with GPT-5.4-mini on τ 2-Airline completes 48% of tasks but only 34% without a viola-
tion, with 64% conformance and 29 violations across all tasks.
Conformance. SOTERIA achieves 100% conformance with zero specification violations across all
models and all three benchmarks. No baseline achieves full conformance. On τ 2-Airline, the best
baseline conformance is 90.0% (ABC, GPT-5.4-mini) with 5 violations. On τ 2-Retail, ABC with
Gemini reaches 93.0% conformance, but still incurs 8 violations; baseline violation counts range
from 8 to 28. High conformance alone does not imply task completion: on τ 2-Retail with Gemini 3
Flash, all baselines achieve more than 90.0% conformance, but their raw utility and task success are
less than 50.0% and 40.0%, respectively. Even Claude Opus 4.6 incurs 11 violations on τ 2-Airline
without guardrails, achieving 82.0% conformance despite 64.0% raw utility. SOTERIA provides
a hard conformance guarantee regardless of model capability or task complexity, with negligible
runtime overhead (Appendix B.3, B.4).
Success rate: verified plans improve utility. SOTERIA consistently achieves the highest success
rate across all model–benchmark pairs. On τ 2-Airline, SOTERIA outperforms the best baseline for
each model by 10–40 percentage points; on τ 2-Retail, by 7.0–43.9 percentage points. Claude Opus
4.6 reaches 88.0% on τ 2-Airline and 90.4% on τ 2-Retail with SOTERIA, compared to 56.0% and

Liveness enforcement. SOTERIA’s plan-based enforcement checks liveness obligations before ex-

On single-turn Toolathlon tasks, where only one plan is needed, SOTERIA can be more cost-effective
than baseline approaches. The plan provides structured guidance that reduces wasted steps, and plan
verification blocks spec-violating calls early, cutting token consumption on long-running tasks.

4.3
Ablation on Sub-plans
To answer (RQ3), we compare two configurations on τ 2-Airline (GPT-5.4-mini, 8 retries): the full
system with a sub-plan library and a variant where the planner must produce a single monolithic
plan at each planning turn. Sub-plans reduce the median plan size from 11 states to 8 (Figure 6a,
top), since complex sub-tasks are encapsulated in pre-verified fragments rather than replicated. This
simplification nearly doubles the number of verified plans (65 of 68 planning turns vs. 38 of 60), with
48.5% verifying on the first attempt vs. 23.3% without sub-plans (Figure 6b). The dominant failure
mode shifts accordingly: without sub-plans, specification failures persist across retries because they
require plan redesign; with sub-plans, residual failures are parse and compile errors that the retry
loop can address with syntactic fixes. These results validate the modular verification design (§2.4):
factoring policies into independently verified sub-plans reduces the planner’s burden and transforms
failures into incrementally fixable ones, enabling 95.6% of plans to verify within the retry budget.
5
Related Work
Planning for LLM agents. LLM+P [Liu et al., 2023] delegates planning to a classical PDDL
planner [Aeronautiques et al., 1998, Helmert, 2006], obtaining sound plans but remaining lim-
ited to predicate-based state without rich data types or runtime enforcement.
VeriPlan [Lee
et al., 2025] checks LLM-generated schedules against LTL constraints via the PRISM model
checker [Kwiatkowska et al., 2002], but its plans are flat linear step sequences without branching
or conditional logic. It has an LLM-based NL-to-LTL translation procedure, but it has no runtime
enforcement or monitoring for the translated specifications. SOTERIA’s guarded transition systems
support branching, hierarchical sub-plans, and multiple paths to terminal states, enabling verification
of real-world policies where the correct action depends on runtime conditions. SOTERIA combines
a verifiable plan representation, static verification, and runtime enforcement, which is a combination
absent from prior work.
Runtime guardrails for LLM agents. AgentSpec [Wang et al., 2025] and ProbGuard [Wang et al.,
2026] monitor tool calls against trigger-predicate rules, with ProbGuard adding proactive viola-
tion prediction via a learned Markov chain. Agent-C [Kamath et al., 2025] supports temporal and
data-flow constraints; Agent Behavioral Contracts [Bhardwaj, 2026] adapts design-by-contract with
preconditions, invariants, and governance constraints. NeMo Guardrails [Rebedea et al., 2023] and

GuardAgent [Xiang et al., 2025] use a secondary LLM for compliance checking, inheriting proba-
bilistic failure modes. These approaches monitor execution at runtime; they do not statically verify
a structured plan against the specifications before execution or use such a plan to guide recovery.
Structured agent frameworks. ReAct [Yao et al., 2022] and Chain-of-Thought [Wei et al., 2023]
structure LLM reasoning but produce no externally verifiable artifact. Plan-and-Solve [Wang et al.,
2023] and Plan-and-Act [Erdogan et al., 2025] separate planning from execution but lack formal
plan semantics or verification. VeriMAP [Xu et al., 2025] attaches LLM-generated assertions to a
subtask DAG, but checks are post-execution with no formal guarantees. StateFlow [Wu et al., 2024]
and LangGraph [LangChain, 2025] use state machines to structure agent workflows but carry no
formal semantics amenable to formal verification.
6
Conclusion
We presented SOTERIA, a framework that enables verification and runtime enforcement of plans for
LLM-based agentic systems. By representing plans as guarded transition systems with hierarchical
sub-plans, SOTERIA formally verifies LLM-generated plans against policy specifications, covering
temporal, relational, and value-flow constraints, before any tool is invoked. At runtime, the veri-
fied plan guides the executor, while the SpecMonitor blocks specification violations and the plan
provides recovery guidance. Our evaluation shows that SOTERIA achieves 100% conformance with
zero specification violations across all models, while improving task success by 4.7–43.9 percentage
points over the best baseline.
Limitations and future work. First, SOTERIA requires a set of formalized specifications as inputs,
which are currently obtained through a semi-automated workflow that combines LLM-based auto-
formalization with manual validation. In future work we aim to investigate how auto-formalization
(e.g., An et al. [2026]) could help reduce this manual effort. Second, SOTERIA’s plan verification
assumes that tool contracts faithfully model tool behavior and postconditions are satisfied at run-
time. Furthermore, SOTERIA leverages automated theorem provers Leino [2010], De Moura and
Bjørner [2008] that support limited first-order theories and may not complete verification in prac-
tice. Sub-plans are currently generated with LLM assistance and iterative verification; automatically
extracting and evolving a sub-plan library and specifications from policy documents and agent ex-
perience is a promising direction. Finally, reducing the planning-time token overhead through plan
caching and reuse across tasks of the same type would further improve practical efficiency.

A.1
Problem Setting
An LLM agent A is defined as a tuple (M, T , E, Φ), where M is a backbone LLM, T is a set
of tools, E is the state of the external environment the agent interacts with, and Φ is a set of
specifications that define correct agent behavior. Each tool a ∈T is annotated with a contract
Ca = (Pa, Qa), where Pa is a precondition on the inputs to a and Qa is a postcondition on the
inputs and outputs of a.
Given a user task τ described in natural language, the agent produces an execution trace σ =
⟨(a1, ⃗x1, r1), . . . , (ak, ⃗xk, rk)⟩, where each element records a tool invocation ai ∈T , its argu-
ments ⃗xi, and the returned result ri. Each tool call may read from or write to the environment E,
producing a result ri and transitioning E to a successor state E′ (with E′ = E for read-only tools).
A specification ϕ ∈Φ is a first-order logic formula over traces that characterizes safe executions.
For example,
ϕ ≜∀c1:(Cancel-Resv, (x, reason), r). ∃c2:(Get-Resv, x′, r′). c2 ≺c1 ∧x = x′
states that every call to Cancel-Resv on a reservation x must be preceded by a call to Get-Resv on
the same reservation, where c2 ≺c1 denotes the standard happens-before relation [Lamport, 1978].
A successful execution must satisfy two objectives simultaneously:
• Utility. Each task τ is associated with a predicate Uτ over the final environment state. An exe-
cution is useful if Uτ(Ek) holds—i.e., the environment reflects the intended outcome of the task
(e.g., a reservation is cancelled, the correct refund is issued).
• Conformance. An execution is conformant if (1) σ |= ϕ for every ϕ ∈Φ, and (2) for every
(ai, ⃗xi, ri) ∈σ, Pai(⃗xi) holds —i.e., the trace satisfies all specifications and every tool call
satisfies its precondition.

A.3.1
Ghost State Construction
To reason about the execution trace within the plan’s transition system, SOTERIA maintains a ghost
state alongside the symbolic state Σ. The ghost state is not part of the runtime execution; it exists
only in the verification encoding. It consists of three components:
1. Step counter (step : Z). A monotonically increasing counter, incremented after each action.
Provides a total ordering over tool calls that encodes the happens-before relation.
2. Call logs (La : seq⟨CallRecorda⟩, one per spec-referenced action a). Each call record stores:
• step: the step counter at call time,
• in_p for each parameter p of a: the typed argument value,
• out_result: the typed return value.
Only actions referenced by at least one specification receive a call log; other actions update only
the step counter and provenance map.
3. Provenance map (prov : map⟨string, set⟨string⟩⟩). Maps each plan variable name to the set of
action-result tags that contributed to its current value. Tags identify actions: different calls to the
same action share a tag, since any output satisfying the specification’s constraints may be used
as an input. When a transition binds variable v from the result of action a, the provenance entry
becomes prov[v] := {“a.result”}. For a variable update v = e, the entry is replaced by the union
of the provenance of the variables referenced in e:
prov new[v] :=

prov old[w].
Here, FV(e) is the set of variables occurring in the right-hand-side expression, evaluated using
the context before the update. A constant assignment clears the entry; the old provenance of v is
retained only if v occurs in e. This transitively tracks dependencies of the current value without
retaining dependencies from overwritten values.

A.3.3

Plans are self-contained: SOTERIA verifies each plan independently against its own specifications.
At the call site, the parent plan checks only the sub-plan’s contract: the precondition must hold at
the invocation point, and the postcondition is assumed in the continuation. This means the parent
plan’s VCs never inspect the sub-plan’s internal states, keeping verification modular and scalable.

A.3.5
Assumptions
Verification is sound assuming:
1. Tool contracts (Pa, Qa) faithfully model tool behavior: the actual tool satisfies Qa whenever Pa
holds on the inputs.
2. llm_eval postconditions are satisfied at runtime. Outputs are retried up to a bounded number of
attempts; if retries are exhausted, the transition fails and the execution halts safely.
3. The plan is acyclic. SOTERIA rejects plans with back edges (cycles), since the flat state-machine
encoding requires a finite, topologically ordered traversal.
A.4
Plan-Guarded Agentic System (PGAS)
This section describes the runtime enforcement of the Plan-Guarded Agentic System (PGAS)
through a concrete execution trace of the cancellation plan from Figure 7 (corrected to include the
No-Flown check).
A.4.1
PGAS Mode vs. Worklist Mode
SOTERIA offers two enforcement strategies:
• PGAS (strict). Only plan-enabled transitions may fire; all others are blocked via INV-GUARD.
Appropriate for high-stakes workflows where deviation from the verified plan is unacceptable.
• Worklist (guided). The plan is presented as a progressively simplified flowchart (§3). The ex-
ecutor retains full discretion over tool selection; conformance is guaranteed by the SpecMonitor
regardless of whether the executor follows the plan.
Example: worklist allows, PGAS rejects.
Consider a user who says “Cancel reservation RES123
and also look up reservation RES456.” When the plan reaches DO_CANCEL, before cancellation
executes, the LLM calls Get-Resv("RES456") — a read-only lookup unrelated to the cancellation.
In PGAS mode, no transition at DO_CANCEL has action Get-Resv, so INV-GUARD blocks the call:
the plan permits only Cancel-Resv at this state. In worklist mode, the SpecMonitor evaluates the
call against all specifications. Since Get-Resv is read-only and violates no spec, the call is approved
and executed. The LLM satisfies the user’s secondary request without deviating from the safety
guarantees, even though it deviates from the plan’s intended action sequence.

A.4.5
Exceptional Rules
The trace above illustrates the common path. Three additional rules handle exceptional cases:
• CALL-REJECTED. In worklist mode, the policy α is instantiated as the SpecMonitor. If a staged
action would violate a specification, α returns rejected(reason): the pending action is cleared, the
rejection reason is fed back, and the LLM retries.
• POST-FAIL. If a tool executes but its result violates the postcondition (e.g., Cancel-Resv re-
turns a reservation whose status is not cancelled), the system halts with Halt⊥. This indicates
unsound tool contracts.
• EXEC-FAIL. If a tool call is approved but execution fails at runtime (e.g., a network timeout), the
error is fed back and the LLM remains at the same state to retry.
A.4.6
Rule Priority and Two-Phase Commit
At each step, the system applies the first applicable rule in priority order: pending-action resolu-
tion (CALL and its variants) ≻DROP at accepting states ≻LLM interaction (STEP/INVOKE/INV-
GUARD) ≻CONTINUE (synthesize a continuation prompt when In is empty at a non-accepting
state).
The INVOKE/CALL split implements a two-phase protocol: INVOKE stages a proposed call by
matching it against the plan; on the next step, CALL commits after policy approval. This ensures the
approval oracle can inspect resolved arguments before the tool modifies the environment.
A.5
Details of SpecMonitor
The SpecMonitor is SOTERIA’s runtime specification guard. It maintains the execution trace as a
growing list of committed tool calls and checks every proposed action against the policy specifica-
tions before execution, blocking calls that would cause a violation.
A.5.1
Operation
The SpecMonitor exposes two operations, called in sequence for each tool invocation:

1. Pre-execution check (check_proposed_action). Given a proposed action f with arguments
¯V , the SpecMonitor constructs a tentative trace step with the action and arguments but no result
(the tool has not executed yet). It appends this tentative step to the current trace and evaluates all

and a rejection reason is returned; otherwise the call is approved.
2. Post-execution commit (commit_action). After the tool executes and returns a result r, the
SpecMonitor appends the completed trace step (with r) to the trace. It then re-evaluates any
safety specifications that depend on the result value and were not fully checked pre-execution.
At task completion, a liveness check (check_liveness) evaluates all specifications — including
liveness obligations — against the final trace.

A.5.3
Specification Classification
Not all specifications are relevant to every action. The SpecMonitor builds an action index at initial-
ization: for each specification, it collects the action names referenced by the spec’s quantifiers and
classifies them:
• Safety: the spec constrains whether this action may be called (e.g., ϕ1 is a safety spec for
Cancel-Resv— adding a Cancel-Resv call can cause a violation). These are checked pre-
execution.
• Liveness: the spec requires that this action eventually be called (e.g., “a confirmation must follow
every write”). These are checked at task completion.
• Irrelevant: the spec does not mention this action; no check is needed.
This indexing ensures that each proposed action triggers only the relevant subset of specifications,
keeping the per-call overhead low.
A.5.4
Concrete Trace Evaluation
Specification checking at runtime uses concrete evaluation over the trace, not SMT solving. Each
spec is evaluated by pattern-matching over the committed trace steps:
• Quantifiers (∀c:a, ∃c:a) iterate over trace entries with action a.
• Temporal predicates (ci ≺cj) compare trace positions (step indices).
• Relational predicates (c.⃗xp = c′.r) access concrete argument and result values from the trace
entries.
• Value flow (ci.r ⇝cj.⃗xp) checks a provenance chain: each trace step records which input vari-
ables contributed to the output (provenance metadata), and value flow is verified by checking that
the source action’s output appears in the transitive provenance of the target’s input variable.

All baselines use identical model configurations (same backbone LLM, temperature,
and reasoning effort) and receive the same tool definitions and domain policy document:
• No Guardrail. The LLM receives the task, tool definitions, and domain policy as a natural-
language system prompt. No guardrail mechanism intercepts tool calls.
• NeMo Guardrails. NVIDIA’s NeMo Guardrails framework [Rebedea et al., 2023] is configured
with a Colang input rail that intercepts every tool call. The rail passes the proposed action, its
arguments, and the full domain policy document to the backbone LLM, which judges whether the
call is compliant. Non-compliant calls are blocked with an explanation.
• AgentSpec. AgentSpec [Wang et al., 2025] enforces runtime rules expressed as action–trigger–
predicate tuples. We translate our specifications into AgentSpec’s rule format. Before each tool
call, the monitor evaluates the relevant rules and blocks calls that violate any predicate.
• Agent Behavioral Contracts (ABC). ABC [Bhardwaj, 2026] specifies preconditions, hard and
soft invariants, and governance constraints. Its runtime monitor evaluates constraints against the
observed state and tracks compliance and behavioral drift.
Metrics.
We report the following metrics:
• Utility (Util.) is the fraction of tasks completed according to the benchmark evaluator, regardless
of specification violations.
• Success rate (Succ.) is the fraction of tasks where the agent both completes the intended task
and satisfies all specifications. The Util.→Succ. column shows the reduction due to specification
violations; for SOTERIA, the two rates are equal and shown as a single number.
