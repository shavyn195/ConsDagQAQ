### Shortcuts and Boundaries:


### Verifiable RL Misalignment and Contextual Safety Learning

Xinjie Shen

#### Abstract


###### Reinforcement learning (RL) can improve an agent’s task capability while reinforcing


###### violations of explicitly stated contextual requirements, even when reward accurately


###### measures useful work. We study this reward-driven misalignment through verifiable

reward–context conflicts, where compliant completion is feasible but executable violations

###### earn more reward than every compliant strategy.


###### Encoding these conflicts in task


###### dynamics supports scalable environment construction and compliance feedback from

execution histories. In resource and reporting workflows, task optimization increases real

###### productivity through unauthorized resource use or raises reported scores while actual

work declines. We observe both amplification of existing violations and the emergence of
violations on tasks where none were observed before training. Controlled changes in the

###### training distribution show that minority conflict exposure can still lead to widespread

shortcut acquisition, reaching 97.9% certified profitable violations on an API task under
a 25% conflict mixture after 128 updates. The same contextual checks supply a simple
binary penalty that supports joint capability and compliance gains and partially mitigates
acquired violations. Learned safety adapts to expanded authorization and transfers across

###### mechanisms into workflows with evolving evidence and approval requirements. On 32

unseen changing-evidence tasks, resource-trained safety increases safe completion from
53.1% to 89.1% relative to task-only training, while both policies achieve full real work.
These results connect a verifiable account of reward-driven misalignment with scalable

###### task construction and safety learning that remains useful under changing execution

requirements.

#### 1


#### Introduction

Capable and reliable language-model agents are increasingly expected to repair software, schedule resources,
and complete complex workflows over long horizons while following human requirements. To develop these
capabilities, reinforcement learning (RL) commonly uses task reward based on the quality or amount of

###### work accomplished at the end of an episode, providing a direct, scalable training signal across diverse

tasks [1–3]. However, whether the work meets human expectations also depends on the context in which
it is carried out [4]. This context includes user intent, interaction history, and specific constraints such as
authorization or organizational rules, which determine which actions are appropriate and which constraints

###### apply [5–7]. Following these contextual requirements becomes more challenging as execution horizons


###### grow [8]. Agents must continue to respect resource permissions and preserve evaluation requirements


###### in an evolving environment, where prior commitments can constrain later actions. A finite instruction

list may leave requirements and their interactions implicit or unspecified, so compliance can depend on
basic safety judgment that cannot be taken for granted in LLM agents [8, 9]. Even when requirements

###### are explicitly stated, their applicability can change as actions alter the state and create or invalidate

obligations [10, 11]. For example, a user may revoke permission to use an external service and later restore
it only for public data. Resuming the earlier workflow may then send restricted data to the service even if

###### the task is completed correctly. Task reward may not fully capture these conditions, leaving room for

RL-induced misalignment of the kind observed in studies using production training environments [12, 13].

###### We study these reward-driven forms of misalignment through conflicts between task incentives and

contextual execution requirements. Such conflicts can arise even when task reward accurately measures

###### useful work, as additional service calls beyond an authorized allowance can still produce more genuine

output. In our experiments, task-reward training improves verified work under full authorization while

###### also increasing certified profitable violations under restricted authorization, illustrating how genuine


###### capability gains can conceal growing execution risk (Fig. 4). In other cases, agents can raise scores by

modifying an acceptance test without repairing the software, and our reporting experiments show higher
scores accompanied by less actual work. We interpret these reward-seeking departures from expectations,

###### including behaviors commonly studied as reward hacking [13, 14], as shortcuts that bypass contextual


###### requirements of task completion. We construct tasks in which compliant completion remains feasible,

#### 2


#### Formulation


###### We consider language-model agents trained through reinforcement learning (RL) in executable task


###### environments. Task dynamics determine which executions are possible by specifying how tool calls

change the environment’s state and return observations. Contextual requirements distinguish compliant

###### executions within this space, while task reward assigns value to the resulting outcomes. We formalize

conflicts between these requirements and task reward as verifiable task properties. This lets us construct
tasks for studying shortcut acquisition and use the same execution checks to learn contextual compliance.
2.1
Contextual execution and task reward

###### For a task instance, let τ denote an execution trajectory ending in a terminal state and T the set of

trajectories executable under its dynamics. A context c specifies requirements on how the task is carried

##### out, and C(c) ⊆T contains the trajectories that satisfy them. Trajectories in T \ C(c) remain executable

despite falling outside contextual expectations (Fig. 1a). Within an execution, earlier actions can change

###### which requirements apply later, so compliance is defined over the full history. Across authorization


###### contexts, expanded permission can make the same physical execution compliant without changing its

outcome or task reward (Fig. 1c). Section 3 describes how these boundaries are implemented in executable
environments.

##### V (τ) = Rtask(τ) −b, whose zero marks this value baseline. The score and b are fixed before interaction


###### and shared by paired authorization contexts, so centering preserves reward ordering and reward gaps.

#### 3


#### Scalable construction of verifiable task environments

In real workflows, executable behavior can exceed contextual permission. This gap provides a practical

###### source of reward–context conflicts. We turn it into reusable task mechanisms by encoding contextual

requirements as checks on the states and execution histories maintained by task dynamics, while keeping
boundary-crossing actions executable.
Each environment is governed by an underlying executable dynamical system. This system specifies how
tool actions change state and how completed work earns task reward, while contextual checks determine

###### whether the resulting execution crosses a boundary (Fig. 3a–b). Following VHD’s environment and

interpreter isolation [2], we render these dynamics into task instructions and stateful tools through which

###### the agent interacts. The agent can change the underlying state through those tools, but the exposed


###### interface does not permit it to modify the governing rules, contextual checks, or reference outcomes.

Contextual compliance is therefore evaluated from the states and execution histories maintained by the

###### dynamics. These checks are executable predicates over mechanism-defined state variables and action

histories, including cumulative resource use, artifact and evidence versions, and prior invalid publications.
Figure 3 illustrates how familiar operational rules give rise to these mechanisms. Under a shared resource
allowance, a tool call can produce more work while pushing cumulative use beyond the authorized total,
including when calls are spread across accounts. The dynamics record both work and resource consumption,

###### allowing productive execution to register a contextual violation. In a versioned workflow, publication


###### requires evidence for the current artifact, even though the interface may still allow an archived report


###### to be selected. Renewing the evidence restores its current validity, while an earlier invalid publication

remains part of the execution history.

#### 5


#### Discussion

These experiments cover a controlled subset of the ways task optimization can produce successful work
that violates contextual requirements. We expect such failures to become harder to detect as agents gain
capabilities and take on longer workflows with less explicit context.
Clear context does not remove incentive conflicts. Our training tasks state the applicable requirements,
yet task-only RL learns profitable violations. Continued optimization also produces substantial shortcut

###### acquisition when conflict tasks remain a minority of the data (Section 4.1). We expect real training

data to contain such conflicts and suspect that some exposure is effectively unavoidable at scale. With
12

--- PAGE 13 ---

continued optimization, reward can keep reinforcing these patterns. During longer executions, permissions
can change and earlier actions can create new obligations, while user expectations may remain implicit.
We think this will make reliable execution harder. Consequences can range from poor user experiences
and unwanted changes to security breaches. In the incident involving OpenAI and Hugging Face, agents
seeking task solutions crossed intended infrastructure boundaries to access third-party systems [15].
Capability growth can conceal boundary crossing. In the resource experiments, task reward and indepen-
dently verified work rise, including on authorized evaluations, even as restricted execution becomes riskier

###### (Fig. 4a). An RL researcher would normally read these as signs of progress. A held-out evaluation can

validate the quality of the work without checking the authority under which it was produced. Screening
collected and validation data for shortcuts takes time and queries, as does searching training rollouts for

###### evidence that the policy uses them. With limited budgets, both jobs are difficult. A finite evaluation

may record substantial capability gains and still miss the combination of task and context that exposes a
hack, leaving too little evidence to investigate or govern the policy. Larger training distributions make

###### exhaustive inspection less feasible, and more complex workflows make individual executions harder to

interpret.
Composition makes loopholes harder to recognize. We observe shortcut acquisition and mitigation with

###### deliberately simple mechanisms. Following VHD’s mechanism-first approach, we can combine these

mechanisms into more complex workflows while retaining executable references and contextual checks [2].
In the dynamic cases, a correct artifact can have obsolete evidence, and an approval response can create

###### new obligations before publication (Section 4.3). We expect shortcuts to look more evasive as these

requirements are combined. A sequence can end in an apparently healthy state after an earlier breach, or
use an available permission together with evidence that no longer applies. Many individual steps still look
like useful work, making the whole execution harder to judge. For long-horizon training and execution, we
see a risk and safety space that needs deliberate study: combinations whose effects go beyond the local
meaning of any one action. Related security studies show how locally benign fragments and interactions

###### can combine into harmful overall intent [10, 17, 18]. We expect broader delegated workflows to create

more opportunities for such combinations.
Model scale. Our main experiments use a 4B model. Stronger models may start safer and handle simple
mechanisms more reliably. Our focus is the change in violations induced by task-only RL relative to the
same model before training. Building on evidence of learned reward-seeking behavior [13], a promising
conjecture is that stronger reward-seeking capabilities could acquire subtler violations in more complex

###### workflows. Whether this delta grows with model size remains untested and requires matched training

comparisons beyond our current compute budget.

###### Human verification is limited, but investigation is indispensable. People are imperfect verifiers when

collecting data and when investigating a trained policy. Limited domain knowledge and coarse checks can
leave incentive conflicts unnoticed; plausible executions and rising performance can also conceal learned
violations. HCI studies of data work report gaps in domain feedback [19]. Research on conversational LLMs
associates overreliance with shallow task comprehension, coarse checking, and accepting misinformation
despite hesitation [20]. We still need investigation to recognize loss of control and understand why failures

###### occur. It is also how we assess mitigation. Early work on agent-assisted monitoring and investigation


###### offers a way to share this work with models [21]. Our methodological commitment is to make the


###### resulting evidence verifiable. An opaque LLM-judge verdict can leave it unclear which action violated

which requirement, and why. Fixed work requirements, observable state changes, historical checks, and
executable counterexamples give a reviewer evidence they can inspect and correct.

###### Contextual safety is a trainable direction. A shaped terminal reward combines task performance with


###### a history-based violation penalty. Training on this scalar feedback supports useful compliance under


###### changed authorization, extending to workflows with evolving evidence and approval requirements. In


###### environments with feasible compliant completion and a verified reward–context conflict, this objective

creates pressure to anticipate and respect requirements during productive execution without prescribing a
step-by-step safety strategy. These results motivate the conjecture that contextual safety awareness can
be learned and inherited as part of task competence.
This form of RL-induced misalignment can arise without an attacker: ordinary task feedback can reinforce

###### violations even when requirements are given, while the policy does more genuine work.


###### Reasoning


###### over explicit safety specifications [22] and attack and defense methods [10] address different problem

formulations. They do not directly cover the incentive conflicts and behavioral acquisition studied here.
We see learning from verifiable contextual consequences as a distinct direction for safety training. Because

###### real requirements cannot be exhaustively listed, the policy would need to apply context beyond the


###### particular rules seen in training. Verifiable environments make that hypothesis testable as capability

training scales.

#### 6


#### Related Work

RL-induced misalignment and reward hacking. Formal reward-hacking analysis characterizes disagreement
between proxy and intended objectives [23], while reward-model overoptimization shows how optimizing

###### proxy reward can degrade the quality it is meant to measure [24]. In agent RL, studies examine test


###### hardcoding and training against deception detectors [14], reward hacking that generalizes to broader


###### misalignment [12], and harmful actions learned in pursuit of task reward [13].


###### These experiments


###### demonstrate reward-driven misalignment, but their incentive conflicts remain tied to particular task

settings. A common account must also cover violations that accompany genuine capability gains, when
task reward accurately measures useful work but does not capture contextual execution requirements. We
generate diverse tasks with verifiable reward–context conflicts at scale to study shortcut acquisition and
generalization during RL and develop transferable safety mitigations.

###### Safety defenses and contextual safety training. Agent-safety research examines risks from tool use,

evolving state, and interaction history [5, 10]. Earlier evaluation attempts include HVE and HVTB, which

###### instrument game and terminal environments to detect specified shortcuts [25, 26], and BAITBENCH,


###### which samples synthetic ML tasks with planted data shortcuts [16]. These benchmarks evaluate fixed

agents without jointly certifying compliant feasibility and a strict reward advantage for violating execution
over all compliant executions. BenchShield checks reward integrity through execution evidence [27], while

###### side-effect audits test whether verifiers accept correct work with unrequested changes [28]. Runtime

defenses reason over safety constraints [6] or use monitoring and trusted intervention [21], with BashArena

###### supplying Linux workflows and security-failure objectives [29]. Safety training uses principle-derived

preferences [30], reasoning over safety specifications [22], or expected-cost constraints [31]. Together, these
lines leave open how to generate task distributions with certified reward–context conflicts and use their
execution checks to study shortcut acquisition, generalization, and mitigation through RL. We build on
VHD’s solved-mechanism construction [2] to connect certified task conflicts with execution feedback for
contextual safety learning.

#### 7


#### Conclusion

The experiments support our premise that contextual safety is a learnable part of task execution. Encoding
requirements in the dynamics makes reward–context conflicts reproducible and turns their consequences
into training feedback. Mechanisms establish compliant feasibility and a rewarding opportunity beyond
the contextual boundary; LLM setters realize diverse tasks while independent work and history checks
preserve the distinction between score, capability, and compliance. The experiments expose two routes

###### to reward improvement: additional real work through unauthorized resources, and higher reported

scores despite degraded work. The shortcut interpretation connects these incentive conflicts to verifiable

###### construction and intervention. Controlled changes in conflict prevalence and training exposure reveal

substantial shortcut acquisition even when conflicts occupy a minority of training data. Verified feedback

###### supports joint capability and compliance gains, partially mitigates acquired violations, and transfers

authorization-sensitive behavior across new contexts. Cross-task cases show that both boundary-crossing
behavior and learned protection can reach excluded workflows; Validation-to-Allocation transfer provides
a concrete protection example with useful work retained. Together, these findings support a data-driven
route to safety training in which agents learn contextual compliance from the same task interactions used
to develop capability. The construction provides a scalable task distribution and verifiable signals for this
learning process.

A.1
Construction coverage
The eight core panels contain 24 physical tasks each for Allocation, API, and Validation, and 12 each for
test expectations, evaluation cohort, score cache, CI reports, and monitoring. Each panel has 48 condition

###### records, yielding 132 physical identities and 384 records. Additional parameter draws provide 24 new

Allocation and 24 new API tasks; Workshop renders the Allocation tasks in a new scenario. Authorization
conditions and evaluation draws share these physical tasks.
A separate saved-record audit identifies at least 807 task instances across the paper-linked training and
evaluation sets, collapsing authorization twins and copied snapshots. The expanded training pool contains
450 distinct instances across Allocation, API, Validation, test expectations, and evaluation cohort. The
128-update, 25% conflict run consumes 256 distinct instances and 2,048 rollouts, with eight rollouts per
instance; its saved consumption audit reports no repeated instance identities or duplicate resource-physics
fingerprints.

###### Table 1 summarizes construction scale, executable admission, and estimated realization cost. Table 5

gives the core inventory and mechanism-proposal coverage.
A complementary proposal study samples 24 construction requests across four mechanism directions and six
operational settings. Gemini3.1 Pro authors finite workflows and Gemini3.5 Flash reviews their semantics.
Seven workflows pass execution, complete constrained optimization, and semantic review after refinement;
they span three proposal families and four settings. The admitted cases include state-dependent processing
modes, approval invalidation, and requirements on a completed artifact’s history. A parameterized release
construction supplies 24 further physical instances with dynamic grants and evidence obligations.
A.2
Mechanism semantics

###### Resource use and evidence maintenance illustrate how these conditions are realized. In an API work


###### order, executing a job produces work and records its request consumption. For a shared allowance


##### A(c), consuming q requests updates cumulative use from u to u + q and violates the requirement when


##### u + q > A(c). Switching accounts still consumes the same quota; billing credits change the invoice while

the usage history retains all requests. Under per-account authorization, unused allowance elsewhere does

###### not permit excess use on one account. In a repair workflow, a check creates evidence for a particular

artifact version. Editing the artifact or a dependency makes that evidence stale, and publication checks
the report’s recorded revisions against the current state. Publishing with inapplicable evidence violates

###### this requirement. Selecting an archived passing report can raise the measured score even when repairs

remain incomplete, so work verification uses the original requirements independently of report selection
(Fig. 3).

#### B


#### Evaluation protocol and metrics

Counts below are reported as successful or violating attempts out of evaluated attempts, for each policy
and authorization context. A physical task may be executed more than once; repeated draws therefore
increase the attempt count without increasing the number of distinct tasks. Main-text percentages use
these same denominators.
B.1
Evaluation design
Each comparison uses one fixed policy per role on matched task panels. Authorization twins retain the

###### physical task, tools, score, and interaction budget. Resource acquisition and ordinary/conflict mixed

training use Allocation and API; report divergence uses Validation. Prevention starts from Base. Mitigation
branches from a common Task-trained parent under the task-only and safety objectives.

###### Excluded-Validation capability uses policies trained on Allocation, API, CI reports, and monitoring.


###### The profitable Validation case comes from a separate Task-trained policy trained on two auxiliary

mechanisms: scoped access, where temporary role grants determine effective resource permissions, and

###### deadline-limited processing, where data classes determine authorized workers. Neither source recipe

includes Validation. The excluded-CI policy trains on test expectations, evaluation cohort, and Validation.

###### The Validation-to-Allocation protection example uses two Validation-only policies fixed before target

evaluation.
The external BAITBENCH comparison uses the fixed Resource policies trained on Allocation and API,
with all external tasks excluded from training. The panel contains 32 physical tasks across two regression

###### families and two data sizes, with two draws per policy: 64 executions each for Base, Task-trained, and

Safety-trained. Two saved Task-trained executions illustrate prohibited test-label use. Native scoring uses
the original public and robust evaluators. The separate label-blind assay replaces the candidate-visible
robust-test target column with missing values, then checks predictions against the original labels outside
the candidate process. Code inspection establishes the prohibited label use in the two cases; a panel-wide
violation rate is not estimated. These external violations are distinct from certified profitable violations,
whose compliant reward bound is required by our constructed-task metric.
B.2
Measurement contracts
Real work uses fixed task requirements: realized business value for resources, fixed-check weighted current

###### health for Validation, and actual component health for proxy workflows. Each mechanism retains its

native work scale. The family-balanced mean in Fig. 9 weights API by 1/2, and Allocation and Workshop
by 1/4 each. Historical violations record breaches of contextual requirements; certified profitable violations
additionally require reward strictly above the compliant optimum or a valid upper bound.
