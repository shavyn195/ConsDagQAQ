##### Multi-Turn Tool Agents via Reinforcement Learning


###### Zhexi Lu1, Subhajit Chaudhury2, Tejaswini Pedapati2,

###### Abstract

Reinforcement learning has improved the tool-
use capabilities of large language models. How-
ever, better task performance can coincide with
increased tool hallucination. Reliable tool use
requires decisions to follow the current task
state: available information, tool capabilities,
and task progress. Our analysis shows that
agents sometimes execute when they should
ask for information, retrieve it, or decline an in-
feasible request, even when reasoning identifies
missing information. We introduce StateAlign,
combining task-state construction with state-
contrastive reinforcement learning. The data
cover five task conditions and pair states with
different action requirements.
Outcome re-
wards guide task completion; token-level con-
trasts compare the same generated reasoning
and actions under paired states to train outputs
that fit the current state. Experiments across
five base models from three families show im-
provements on BFCL v4 multi-turn, ToolSand-
box, and When2Call. Ablations show that state
construction improves performance and reli-
ability under different reward designs. The
complete method further reduces tool hallucina-
tion across three Qwen3 sizes. On Qwen3-8B,
StateAlign improves BFCL v4 multi-turn accu-
racy from 45.5% to 55.2% and reduces no-tool
hallucination on SimpleToolHalluBench from
62.2% under outcome-only training to 56.1%.
Behavioral analyses show more consistent deci-
sions, more complete multi-call execution, and
stronger recovery after tool errors.

###### Task States and Agent Decisions

Task State.

(T , H) containing tool definitions T and interac-
tion history H. For a user goal, we define the
task state as the task-relevant conditions specified
by the tools and evidenced by the history that con-

availability: what information needed for the task
is available, what is missing, and how it can be ob-
tained; (ii) tool capabilities: which operations the
tools support; and (iii) task progress: what is com-
plete and what remains. User replies, tool results,
and tool-availability changes can update these con-
ditions and require different actions. Prior work

Decisions across Task States.
We compare
Qwen3-8B’s responses to paired task states follow-
ing the protocol in Appendix D. The states differ
in one relevant condition: one allows execution,
and the other requires clarification, retrieval, or de-
clining an infeasible request. Figure 2a shows that
target-function selection reaches 97–98% when ex-
ecution is appropriate, but choosing the required
action under the contrasting conditions is less reli-
able. In the missing-information condition, 95% of
responses identify the missing value in reasoning,
but only 65% ask the user for it. Figure 2b shows
the model ending its reasoning with a decision to
ask for the user’s phone number, then calling the
tool with a number absent from the context. The
final call contradicts both the available information
and the decision expressed in reasoning.
The training problem is therefore to make reason-
ing and actions follow the conditions of the current
task. We construct training states with different
action requirements and pair states that differ in
a relevant condition. For example, reasoning that
assumes a required value is available may fit a state
that permits execution but conflict with a state re-
quiring clarification. The same generated content
can then be evaluated under both states. StateAlign
combines this supervision with feedback on inter-
action outcomes to train reasoning and actions that
fit the current state.

###### StateAlign: State-Aware Reinforcement


###### Learning

We illustrate StateAlign in Figure 3. Given context
h, the policy πθ generates reasoning followed by
tool calls or a user reply. Interaction outcomes train
task completion; token-level state contrasts train
reasoning and actions to fit the current conditions.
3.1
Constructing Paired Task States
We construct data from ToolMind (Yang et al.,
2025b) and LoopTool-23k (Zhang et al., 2026a).
Structural checks remove invalid calls and incon-

sistent histories. We use Qwen3.8-27B to filter
calls in ToolMind’s synthetic demonstrations that
do not serve the request or contain unsupported ar-
guments. The same model rewrites user messages
and synthesizes retrieval steps.
For each selected call, we identify its re-
quired tools and information, then modify the
tool definitions or history to construct five types
of states.
EXEC supplies the information and
tools for execution. NEED_USER removes a re-
quired user-provided value or retains a clarification
turn, requiring the agent to ask before executing.
NEED_FETCH removes a relevant tool result or
introduces a lookup for a required identifier, so a
tool can obtain the missing information. INFEA-
SIBLE removes the required tool and its identified
alternatives. STOP includes a result completing the
request and requires a reply without further calls.
Each non-EXEC instance is paired with an EXEC
counterpart from the same source trajectory when
available. Source calls and observations provide ex-
ecution checks and interaction feedback; unpaired
instances receive outcome supervision alone. Re-
sampling by condition yields approximately 30k
instances. Appendix A details construction and
annotation, with prompts in Appendix F.
3.2

user information; retrieval receives recorded ob-
servations when function names and designated
arguments match. The policy acts on the updated
history. If a continuation is recorded, successful
target execution is followed by tool results and one
further policy step, checked against the requirement
to continue or stop. For a trajectory τ requiring ex-

###### Experiments

4.1
Experimental Setup
Base Models.
We train Qwen3-4B/8B/14B
(Yang et al., 2025a), Granite-4.2-8B (IBM Re-
search, 2026), and Llama-3.1-8B-Instruct (Dubey
et al., 2024) to evaluate StateAlign across model
sizes and families.
Baselines.
Comparisons include ToolRL (Qian
et al., 2025), LoopTool (Zhang et al., 2026a), AWM
(Wang et al., 2026a), and the base models. ToolRL
uses Qwen3-8B trained on RLLA-4k; LoopTool
and AWM use released models. Each retains its
own training data. Single-step binary GRPO on our
constructed states compares training objectives.
Benchmarks.
BFCL v4 (Patil et al., 2025) mea-
sures multi-turn tool-use accuracy. ToolSandbox
(Lu et al., 2025) measures task progress through
trajectory similarity. When2Call (Ross et al., 2025)
measures macro accuracy across calling, clarifica-
tion, and infeasibility. SimpleToolHalluBench (Yin
et al., 2026) measures hallucination with no avail-
able tool (NTA) or only an irrelevant tool (DT).
Implementation Details.
We train with LoRA
(Hu et al., 2022) on eight NVIDIA H100 80GB
GPUs with λ = 0.1. Qwen3 component compar-
isons use the step-400 checkpoint. Tables 1 and 2
report evaluation means, with BFCL standard de-
viations in Table 2. Appendices B and C provide
training and evaluation settings.

###### Related Work

Tool
Learning.
Synthetic
datasets
provide
demonstrations of API calls, multi-turn interac-
tions, and reasoning traces (Liu et al., 2025; Prab-
hakar et al., 2025; Yang et al., 2025b).
Task
construction extends this coverage to ambiguous,
changing, and infeasible requests (Wang et al.,
2026b). RL methods improve tool use through re-
ward design (Zhang et al., 2026b; Qian et al., 2025),
adaptive data refinement (Zhang et al., 2026a),
and interactive training environments (Wang et al.,
2026a). ARTIST trains interleaved reasoning and
tool use (Singh et al., 2025), and MUA-RL incor-
porates simulated users into policy rollouts (Zhao
et al., 2025). Step-level credit assignment (Feng
et al., 2025), rewards for information acquisition
(Kong et al., 2026), and self-distillation under
privileged contexts (Zhao et al., 2026) provide
more fine-grained training feedback. SIPO con-
trasts contexts containing correct and incorrect
answers (Yue et al., 2026); CC-OPD compares
full instructions with contexts that omit individ-
ual constraints (Zheng et al., 2026). RC-GRPO
uses reward-conditioned sampling to increase re-
ward diversity within rollout groups (Zhong et al.,
2026). StateAlign contrasts task states that each
have a valid action requirement, making their dif-
ferences a source of supervision for how behavior
should change.
Reliable Tool Use.
Prior work combines rea-
soning with actions and observations (Yao et al.,
2023), incorporates dialogue state tracking into
tool-use training (Acikgoz et al., 2025), and sep-
arates state interpretation from action generation
(Guo et al., 2026). However, stronger reasoning
can accompany increased tool hallucination (Yin
et al., 2026). TRUST addresses decision reliabil-
ity through uncertainty-aligned rewards at key in-
teraction turns (Zhou et al., 2026). Proxy state-
based evaluation uses inferred environment states
to simulate interactions and assess task comple-
tion (Chuang et al., 2026). We use paired states
with different action requirements as supervision.
StateAlign compares the same generated reasoning
and actions under both states and their reference
paths to train behavior that fits each state.

###### 7


###### Conclusion

We presented StateAlign, combining task-state con-
struction with state-contrastive reinforcement learn-
ing. Our diagnosis shows that agents can violate
current information and tool conditions even af-
ter stating them in reasoning. Constructed states
improve task performance and reliability under
different reward designs. On the same data, the
complete method further reduces tool hallucination
compared with outcome-only training across three
Qwen3 model sizes. Experiments across five base
models show improved tool use, and behavioral
analyses show more consistent decisions, more
complete multi-call execution, and stronger recov-
ery after tool errors.

###### Limitations

StateAlign is trained on five types of constructed
task states through short interactions with recorded
feedback. Training feedback is limited to the inter-
actions covered by the source trajectories. Extend-
ing this setup to longer workflows with changing
user goals or tool behavior is a direction for fu-
ture work. We evaluate five base models ranging
from 4B to 14B parameters on text-based tool-use
benchmarks. The effectiveness of the approach at
larger scales and in multimodal tool environments
remains to be studied.

###### A


###### Training Data

Data construction.
We apply structural checks
and Qwen3.8-27B filtering to remove low-quality
source examples. The same model rewrites user
messages, synthesizes retrieval steps, and checks
the resulting states. Missing-value rewrites pre-
serve the request and other supplied information;
validation removes cases where the omitted value
remains inferable.
Retrieval examples require
a lookup before execution, and tool-availability
checks account for alternative tools that could ful-
fill the request. Construction uses temperature 1.0,
top-p 0.95, and top-k 20. Selected prompts are
provided in Appendix F.
Training data.
The training pool contains ap-
proximately 30k instances covering all five task
states, with 55% linked to a paired counterpart. Ta-
ble 5 reports their distribution alongside existing
tool-use datasets.
Dataset comparison.
We estimate each exter-
nal dataset’s distribution from 1,000 reference re-
sponses classified by Qwen3.8-27B using the tools,
history, and reference response; StateAlign uses its
construction labels. Direct execution accounts for
approximately 87% of LoopTool-23k and RLLA-
4k. When2Call mainly covers clarification and in-
feasibility, and retrieval and clarification are the
largest categories in APIGen-MT-5k. Our data
cover all five conditions and provide explicit state
pairs.
The constructed collection is checked for ques-
tion overlap with BFCL multi-turn and When2Call
using normalized exact matching and n-gram com-
parisons. No question matches are detected under
these checks.

Source-data filtering
You check training data for a tool-calling assistant. Each case shows the tools the assistant can
use, the conversation so far, and the assistant’s next step (one or more tool calls). Judge that
next step using only what the case shows, and answer six yes/no questions:
J1 user_voice: Is the last user message written from the user’s side (a request, or information the
user provides), rather than in the assistant’s voice (offering help, announcing an action,
presenting results)?
J2 relevance: Does every call in the next step serve something the user asked for in this
conversation that has not already been done?
J3 support: Is every argument value in the next step one of these: stated in the conversation;
returned by an earlier tool result; a default or allowed value from the tool description; a standard
conversion of such a value (units, formats, dates relative to today); common public knowledge (for
example a company’s ticker or a city’s coordinates)? Answer no if any ID, account or order number,
e-mail, URL, file name or personal detail appears to be made up.
J4 completeness: Does the next step pass every value the user gave for this request to the matching
parameter, unchanged?
J5 better_tool: Is there another tool in the list that clearly fits the user’s request better than
the tool(s) called?
J6 timing: At this point, should the assistant call a tool, rather than first ask the user for
missing information or answer from what is already in the conversation?
Reply with one JSON object and nothing else:
{"J1": "yes|no", "J2": "yes|no", "J3": "yes|no", "J4": "yes|no", "J5": "yes|no", "J6": "yes|no",
"reason": "<one short sentence about every failing answer (J1-J4 or J6 no, J5 yes); empty if none>"}

ANSWER: {"J1": "yes", "J2": "yes", "J3": "yes", "J4": "yes", "J5": "no", "J6": "yes", "reason": ""}
